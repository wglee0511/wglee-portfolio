## 큰 그림

### Q1. 서버 상태와 클라이언트 상태를 왜 나누나요?

**답변 (이 질문이 상태 관리 파트의 뿌리입니다)** `🌐 개념 정리`
> **성질이 다르기 때문**입니다.
> 클라이언트 상태는 **내가 소유**합니다. 내가 바꾸면 그게 곧 진실입니다.
> 서버 상태는 **주인이 서버**입니다. 내 화면에 있는 건 사본이라, 언제든 낡을 수 있습니다.
>
> 그래서 서버 상태에는 따로 풀 문제가 생깁니다.
> **얼마나 들고 있을지, 언제 다시 가져올지, 같은 요청이 겹치면 어떻게 할지, 낡은 값을 일단 보여줄지** 같은 것들입니다.
> 이걸 Redux 같은 클라이언트 상태 도구로 다루면 **전부 직접 짜야 합니다.**
> 요청마다 액션 3개(요청/성공/실패)씩 만드는 반복 코드가 그래서 생긴 겁니다.

**30초 버전** — "클라이언트 상태는 내가 주인이고, 서버 상태는 서버가 주인인 사본이라 낡을 수 있습니다. 캐시 유지·재요청·중복 요청 같은 문제가 따라오니까 전용 도구로 따로 다룹니다."

**꼬리 질문 대비**
- **"그럼 Redux로 서버 상태를 다루면 안 되나요?"** → 안 되는 건 아니고, 캐시·재요청·중복 제거를 **직접 짜야 한다**는 비용 문제라고 답합니다. 페이히어에서 Redux로 요청/성공/실패 액션을 반복해 만들던 경험(Q12)으로 잇습니다.

**포인트** — "React Query가 편해서"가 아니라 **"문제의 성질이 다르다"** 로 시작하세요.

### Q2. 그럼 React Query와 Zustand를 어떻게 나눠 쓰나요?

**답변** `📁 내 경험`
> 제 기준은 단순합니다.
> **서버에서 온 것은 React Query가 갖고, 스토어에 복사하지 않습니다.**
> Zustand에는 **서버가 모르는 것**만 둡니다. 필터·정렬 조건, 온보딩 진행 상태, 사용자 설정 같은 것들입니다.
>
> 가장 흔한 실수가 `onSuccess`에서 받아온 걸 스토어로 옮겨 담는 건데,
> 그 순간 **같은 데이터가 두 곳에 생기고, 둘을 계속 맞춰줘야 합니다.** 버그 대부분이 여기서 나옵니다.

**30초 버전** — "서버에서 온 건 React Query만 들고 있고, Zustand에는 필터·온보딩·설정처럼 서버가 모르는 것만 둡니다. 같은 데이터를 두 곳에 두면 맞추는 데서 버그가 나기 때문입니다."

**꼬리 질문 대비**
- **"서버 데이터를 가공해서 써야 하면요?"** → **꺼내 쓸 때 selector에서 계산하고**, 따로 저장하지 않습니다. 저장해두면 원본이 새로 들어왔을 때 그 값만 옛날 걸로 남습니다.

## React Query

### Q3. staleTime과 gcTime(cacheTime)의 차이는?

**답변 (자주 헷갈리게 만드는 질문입니다)** `🌐 개념 정리`
> **staleTime은 "이 데이터를 신선하다고 믿을 시간"** 입니다. 이 시간 안에는 다시 안 가져옵니다.
> **gcTime은 "아무도 안 볼 때 캐시를 얼마나 들고 있을 시간"** 입니다.
>
> 즉 staleTime은 **서버에 다시 물어볼지**를 정하고, gcTime은 **메모리에 얼마나 남겨둘지**를 정합니다.
> gcTime은 그 데이터를 보는 화면이 하나도 없어진 순간부터 센다는 게 포인트입니다.

**30초 버전** — "staleTime은 다시 물어볼지를 정하는 신선도 시간이고, gcTime은 아무도 안 볼 때 캐시를 메모리에 남겨둘 시간입니다."

**꼬리 질문 대비**
- **"staleTime 기본값이 0인 이유는?"** → **틀린 데이터를 보여주는 것보다 한 번 더 요청하는 게 안전하다**는 기본 입장입니다. 그래서 데이터 성격에 맞게 올려야 하고, 자주 안 바뀌는 설정값에 0을 두면 요청만 늘어납니다.

### Q4. staleTime은 어떤 기준으로 정하나요?

**답변** `🌐 개념 정리`
> **"이 데이터가 몇 초 낡아 있어도 사용자가 손해를 안 보는가"** 로 정합니다.
> 코드 테이블이나 프로필처럼 거의 안 바뀌는 건 길게 잡고,
> 잔액이나 재고처럼 **낡은 값을 보면 잘못 판단하게 되는 데이터는 0에 가깝게** 둡니다.
> 숫자를 먼저 정하는 게 아니라 **틀렸을 때의 비용**을 먼저 봅니다.

**30초 버전** — "숫자보다 틀렸을 때의 비용을 먼저 봅니다. 거의 안 바뀌는 건 길게, 잔액·재고처럼 낡으면 손해인 건 0에 가깝게 둡니다."

**꼬리 질문 대비**
- **"길게 잡았는데 데이터가 바뀌면요?"** → 바뀌는 시점을 아는 경우(내가 수정한 직후 등)엔 그때 invalidate로 다시 가져오게 합니다. Q6으로 잇습니다.

### Q5. 낙관적 업데이트(Optimistic Update)는 어떻게 구현하나요?

**답변 (순서를 정확히 말해야 합니다)** `🌐 개념 정리`
> 낙관적 업데이트는 서버 응답을 기다리지 않고 **일단 성공했다고 치고 화면을 먼저 바꾸는 것**입니다.
> ① `onMutate`에서 **그 데이터를 가져오는 중인 요청이 있으면 먼저 취소**합니다.
> 안 하면 늦게 도착한 옛날 응답이 방금 바꾼 값을 덮어씁니다.
> ② **바꾸기 전 값을 따로 복사해두고,**
> ③ 화면에 보이는 값을 원하는 결과로 미리 바꿉니다.
> ④ `onError`, 그러니까 실패했을 때는 복사해둔 값으로 **되돌리고,**
> ⑤ `onSettled`에서 **invalidate** — 이 데이터는 못 믿으니 다시 가져오라고 표시하는 것 — 해서 서버 기준으로 맞춥니다.
>
> ①을 빼먹는 실수가 정말 흔합니다.

**30초 버전** — "진행 중인 요청 취소 → 이전 값 백업 → 화면 먼저 변경 → 실패하면 되돌리기 → 끝나면 invalidate로 서버와 맞추기, 이 순서입니다. 첫 단계 취소를 빼먹으면 늦게 온 응답이 값을 덮어씁니다."

**꼬리 질문 대비**
- **"언제 쓰면 안 되나요?"** → **실패해서 되돌아가면 사용자가 혼란스러운 경우**입니다. 좋아요 토글은 되돌아가도 괜찮지만, 결제나 전송처럼 **"됐다"고 보여줬다가 뒤집히면 안 되는 건** 쓰지 않습니다.

### Q6. invalidateQueries와 setQueryData는 언제 나눠 쓰나요?

**답변** `🌐 개념 정리`
> **서버에 다시 물어봐야 확실하면 invalidate**, 즉 다시 가져오게 하고,
> **응답만 봐도 결과를 이미 알면 setQueryData**로 그 값을 바로 넣습니다.
> 예를 들어 수정 API가 수정된 결과를 그대로 돌려주면, setQueryData로 바로 반영해서
> 서버에 한 번 더 다녀오는 걸 아낍니다.
> 반대로 합계나 정렬 순서처럼 **서버에서 다른 값까지 같이 바뀌면** invalidate가 안전합니다.

**30초 버전** — "응답만으로 결과를 알면 setQueryData로 바로 넣고, 서버에서 다른 값까지 같이 바뀔 수 있으면 invalidate로 다시 가져옵니다."

**꼬리 질문 대비**
- **"둘 다 쓰면요?"** → 낙관적 업데이트(Q5)가 그 경우입니다. 먼저 setQueryData로 화면을 바꾸고, 끝나면 invalidate로 서버 기준으로 다시 맞춥니다.

### Q7. React Query 때문에 리렌더가 많아진 적이 있나요?

> ### ⚠️ 표현 주의
> React Query의 `select` 옵션은 **코드에서 쓰이는 곳이 없습니다.**
> "React Query에 selector를 전면 적용했다"고 하면 확인당했을 때 어긋납니다.
> **Zustand 쪽 부분 구독**과 **파생 상태 정리**로 말하세요. 그건 실제로 있습니다.

**▶ 내 경험** `📁 내 경험`
> 있습니다. 다만 정확히 말하면 **같은 값을 여러 번 저장하던 게 원인**이었습니다.
> 스토어가 21개인 구조였는데, 루틴 스토어는 원본 말고도
> **정렬한 목록과 날짜별로 펼친 목록을 따로 저장**하고 있었습니다.
> 목록이 하나 바뀌면 **저장이 세 번** 일어나고, 그때마다 구독자에게 알림이 갔습니다.
>
> 그래서 **원본만 저장하고 나머지는 계산해서 쓰도록** 바꿨습니다.
> 정렬 목록을 따로 저장하던 setter를 아예 없앴고, 원본을 저장하면 계산값이 같이 들어가게 했습니다.
>
> React Query 쪽은 **서버에서 온 데이터는 여기만 들고 있는다고 정해둔 것**이 컸습니다.
> 서버 데이터를 스토어로 복사하지 않으면, 둘을 맞추느라 생기는 저장·리렌더 자체가 안 생깁니다.

**⚠️ 표현 주의** — **"구독 범위를 좁혔다"·"스토어를 통합했다"는 말하지 마세요.**
좁은 구독은 원래 그 저장소의 기본 스타일이었고, 스토어 통합은 근거가 없습니다.
(오히려 구독 상태를 별도 스토어로 **분리**한 작업이 있었습니다.)
그리고 "원본이 바뀔 때만 다시 계산된다"도 말하지 마세요. `keys` 옵션이 없어서 **저장될 때마다 다시 계산**됩니다(Q22).

**30초 버전** — "React Query보다는 루틴 스토어가 같은 목록을 원본·정렬·날짜별로 세 번 저장하던 게 원인이었습니다. 원본만 저장하고 나머지는 계산값으로 바꿔서 저장을 한 번으로 줄였습니다."

**꼬리 질문 대비**
- **"리렌더가 얼마나 줄었나요?"** → **렌더 횟수는 따로 재지 않았다**고 그대로 말합니다. 확인한 건 저장 호출 3회 → 1회와 손으로 맞추던 코드가 사라진 것까지입니다(Q21).

## Zustand

### Q8. Zustand는 왜 Context보다 리렌더가 적나요?

**답변** `🌐 개념 정리`
> Context는 **값이 하나라도 바뀌면 그걸 쓰는 컴포넌트가 전부 다시 그려집니다.**
> "나는 이 값만 볼래"가 안 됩니다.
> Zustand는 스토어를 React 바깥에 두고, `useSyncExternalStore` 계열로 변경 알림을 받습니다.
> 그래서 **selector로 꺼낸 값이 실제로 바뀐 컴포넌트만** 다시 그립니다.
> 큰 스토어 하나를 여러 화면이 같이 써도 서로 영향을 덜 받습니다.

**30초 버전** — "Context는 값 하나만 바뀌어도 쓰는 곳이 다 다시 그려지지만, Zustand는 selector로 꺼낸 값이 바뀐 컴포넌트만 다시 그립니다."

**꼬리 질문 대비**
- **"그럼 selector를 잘못 쓰면요?"** → **매번 새 객체를 돌려주면 소용없습니다.** `state => ({a: state.a, b: state.b})` 는 안의 값이 같아도 매번 새 객체라 바뀐 걸로 보입니다. 그래서 **값을 하나씩 따로 꺼내거나, 안쪽 값끼리 비교하라고(shallow 비교) 알려줘야** 합니다.

### Q9. Zustand에서 파생 상태는 어떻게 다루나요?

**답변** `🌐 개념 정리`
> 파생 상태는 다른 값에서 계산해낼 수 있는 값인데, **저장하지 않고 그때그때 계산합니다.**
> 스토어에 따로 넣어두면 원본만 바뀌고 이건 안 바뀌는 순간이 반드시 생깁니다.
> 계산이 무거우면 selector 안에서 결과를 기억해두거나, 계산 전용 계층을 따로 둡니다.

> ### ⚠️ 사실관계 — 이건 "설계했다"까지만 말하세요
>
> 링 버퍼 200개와 18개월 윈도우는 **설계 문서까지 나왔지만 코드에는 반영되지 않았습니다.**
> 어느 브랜치에서도 구현이 확인되지 않습니다.
> **"제한했습니다"라고 말하면 안 됩니다.** 아래처럼 설계 단계로 말하세요.

**▶ 내 경험 (설계 사례로)** `📁 내 경험`
> 루티너리에서 **메모리가 시간에 따라 계속 오르는 문제**를 분석한 적이 있습니다.
> Xcode Instruments로 보고 원인을 좁혔더니 **성격이 다른 두 가지**가 나왔습니다.
>
> 하나는 **타이머 활동 로그가 한도 없이 계속 쌓이는 것**이었습니다.
> 알림이 올 때마다 뒤에 붙는데 비우는 곳은 타이머 시작 시점 한 군데뿐이었고,
> 저장까지 되는 값이라 **껐다 켜도 안 없어지고 계속 쌓였습니다.** 정작 쓰는 곳은 개발자용 디버그 화면 하나뿐이었고요.
>
> 다른 하나는 **루틴 이력을 화면에 쓰기 좋게 펼치면서 기본 메모리가 올라가는 것**이었습니다.
> 이력마다 시작일부터 오늘까지 **하루에 객체 하나씩 만드는 구조**라, 오래 쓴 사용자일수록 비례해서 커졌습니다.
>
> 그래서 **최근 200개만 남기고 오래된 건 밀어내는 링 버퍼**와,
> **원본 이력은 그대로 두고 메모리에 펼치는 범위만 18개월로 끊는** 방향으로 설계했습니다.
> 원본을 지우지 않은 건 **통계·달력 데이터가 손실되면 안 되기 때문**입니다.
>
> 다만 **이건 설계·제안까지였고 실제 반영은 안 됐습니다.**

오히려 "왜 반영이 안 됐나요?"에 담담히 답하는 게 신뢰를 줍니다.

### Q10. persist 미들웨어를 쓸 때 주의할 점은?

**답변** `🌐 개념 정리`
> **hydration — 저장해둔 값을 다시 불러와 스토어에 채우는 과정 — 이 한 박자 늦게 끝난다는 점**입니다.
> 다 채워지기 전에 화면이 먼저 그려지면 **잠깐 초기값으로 보였다가 바뀝니다.**
> 로그인 상태를 그렇게 다루면, 로그인해둔 사용자에게 로그인 화면이 한 번 깜빡입니다.
> 그리고 **마이그레이션 — 저장 형식이 바뀌었을 때 옛 데이터를 새 형태로 옮기는 작업 — 이 도는 순서**도 중요합니다.
> 값이 다 채워지기 전에 마이그레이션이 먼저 돌면 빈 데이터를 놓고 작업하게 됩니다.

**▶ 내 경험 (두 층의 마이그레이션이 있었습니다)**
> 루티너리에는 마이그레이션이 두 종류 있었습니다. 저장소는 기기 저장소 **MMKV**를 persist에 연결해 썼습니다.
>
> ① **스토어마다 저장 형식이 바뀔 때 옮기는 것** — persist에 `version`과 `migrate`를 두고,
> 저장 구조가 바뀌면 옛 데이터를 새 형태로 바꿔줍니다. 타이머·루틴·리뷰 같은 스토어에 걸려 있습니다.
>
> ② **상태 관리 라이브러리 자체를 갈아탄 것** — MobX에서 Zustand로 옮기는 작업이었습니다.
> 이건 **딱 한 번만 돌아야 해서**, 끝났다는 표시를 따로 저장해두고 매번 확인합니다.
>
> ②의 원칙은 **실패해도 앱이 죽지 않게 하는 것**이었습니다.
> 이미 서비스 중인 앱이라 마이그레이션이 터지면 그 사용자는 앱을 아예 못 씁니다.
> 그래서 실패해도 앱을 멈추지 않고, 에러만 보고하고 넘어갑니다.
> 그리고 옮기기 전에 **남아 있던 예전 데이터를 먼저 비웁니다.** 섞이면 충돌이 나서요.

**⚠️ 표현 주의** — `onRehydrateStorage`로 순서를 보장하는 코드는 없습니다.
"hydration 완료 콜백으로 순서를 잡았다"고 말하지 마세요.
스토어 간 값 전달은 **구독으로 즉시 반영되게** 처리돼 있습니다.

**⚠️ 작성자 주의** — ① 중 본인 작업은 **routineStore v1 → v2 한 건**입니다(아래 표). ②의 `src/stores/migration.ts`는 현재 저장소 이력상 **다른 팀원 커밋으로만** 남아 있습니다(2025-08 src 이관 이전 이력은 없음). 직접 짰는지는 [ MobX→Zustand 마이그레이션 본인 참여 범위 ] — 확인 전엔 "팀에서 이렇게 했다"로 말하세요.

**30초 버전** — "hydration이 늦게 끝나서 초기값이 잠깐 보이는 깜빡임과, 마이그레이션이 hydration보다 먼저 도는 순서 문제를 조심합니다. 루티너리는 스토어별 version·migrate와 MobX→Zustand 일회성 마이그레이션 두 층이 있었고, 실패해도 앱은 뜨게 하는 게 원칙이었습니다."

**꼬리 질문 대비**
- **"깜빡임은 어떻게 막나요?"** → 일반적으로는 hydration이 끝났는지 확인한 뒤 화면을 그리는 방식입니다. 다만 루티너리에서 hydration 완료 콜백으로 순서를 잡은 코드는 없으니, **개념으로만** 말합니다.

### Q11. 스토어는 하나로 두나요, 여러 개로 나누나요?

**답변** `🌐 개념 정리`
> **다루는 주제별로 나누되, 서로 자꾸 들여다보면 합칩니다.**
> 나누는 목적은 파일을 작게 만드는 게 아니라 **바뀌는 이유가 다른 것끼리 떼어놓는** 것입니다.
> 다만 나눠 놓고 A 스토어가 B 스토어를 계속 읽고 있으면, 그건 원래 하나였어야 하는 겁니다.

**▶ 내 경험**
> 루티너리는 기능 단위로 스토어가 21개였고, 저는 개수를 바꾸기보다 **루틴 스토어 안에서 같은 목록이 세 번 저장되던 걸** 걷어냈습니다.
> 옛 스토어 몇 개를 관련 스토어 안으로 합친 건 **다른 팀원이 먼저 한 작업**입니다.

> ⚠️ 이전 버전의 "중복된 스토어를 통합했다"는 근거가 없어 고쳤습니다. 통합은 2025-11 팀원 커밋입니다(아래 사실관계 표, Q17).

**30초 버전** — "바뀌는 이유가 다른 것끼리 나누고, 서로 계속 읽으면 합칩니다. 루티너리 21개 스토어에서 제가 한 건 개수 조정이 아니라 루틴 스토어 안의 중복 저장 제거였습니다."

**꼬리 질문 대비**
- **"21개면 너무 많지 않나요?"** → 숫자 자체보다 **서로 다른 이유로 바뀌는지**를 봤다고 답하고 Q16·Q31로 잇습니다.

## Redux

### Q12. Redux를 써본 경험은? 왜 지금은 Zustand를 쓰나요?

**답변 (Redux를 깎지 마세요)** `📁 내 경험`
> 페이히어에서 **Redux를 Thunk와 Saga로 같이 썼습니다.**
> 결제 앱이라 **단계가 길고 중간에 취소하거나 다시 시도하는 흐름**이 많았는데, 그런 건 Saga가 잘 맞습니다.
> 무슨 일이 어떤 순서로 일어났는지 기록이 남아서 **"결제가 어느 단계에서 멈췄나"를 따라가기 좋았습니다.**
>
> Zustand로 옮긴 건 Redux가 나빠서가 아니라 **풀어야 할 문제가 달랐기 때문**입니다.
> 루티너리는 서버에서 온 데이터를 React Query가 맡아서, 전역 스토어가 다룰 게 **화면 설정 수준으로 작았습니다.**
> 거기에 액션·리듀서 같은 단계를 얹으면 얻는 것 없이 손만 더 갑니다.

**30초 버전** — "페이히어 결제 앱에서는 취소·재시도가 많은 흐름이라 Redux Saga가 잘 맞았습니다. 루티너리는 서버 데이터를 React Query가 맡아 전역 상태가 작았기 때문에 더 가벼운 Zustand를 썼습니다."

**꼬리 질문 대비**
- **"Redux Toolkit을 쓰면 반복 코드가 줄지 않나요?"** → 맞다고 인정하고, 그래도 선택 기준은 **전역 상태의 크기와 흐름의 복잡도**라고 답합니다.

**포인트** — **"도구 취향"이 아니라 "문제의 크기"** 로 답하는 게 핵심입니다.

### Q13. Thunk와 Saga의 차이는?

**답변** `🌐 개념 정리`
> **Thunk는 액션 대신 함수를 던져서 그 안에서 비동기 처리를 하는 것**이라, 간단한 요청에 잘 맞습니다.
> **Saga는 제너레이터 — 중간에 멈췄다 이어 갈 수 있는 함수 — 로 흐름 전체를 시나리오처럼 써 내려가는 방식**이라,
> **중간에 취소하기, 연타 무시하기, 순서대로 또는 한꺼번에 돌리기, 특정 동작이 올 때까지 기다리기** 같은 걸 깔끔하게 표현합니다.
> 대신 익히는 데 시간이 걸리고, 단순한 요청에 쓰면 과합니다.
> 저는 **"기다리고 취소하는 시간 흐름이 있으면 Saga, 아니면 Thunk"** 로 나눴습니다.

**30초 버전** — "Thunk는 함수 하나로 하는 간단한 비동기 처리, Saga는 취소·대기·연타 무시 같은 시간 흐름을 시나리오처럼 쓰는 방식입니다. 그런 흐름이 있으면 Saga, 없으면 Thunk를 씁니다."

**꼬리 질문 대비**
- **"Saga로 실제 어떤 흐름을 짰나요?"** → 페이히어 결제 단계의 취소·재시도 흐름(Q12)으로 잇되, 구체 코드는 [ 페이히어에서 Saga로 짠 실제 흐름 예시 ]만큼만 말합니다.

### Q14. Redux에서 상태 정규화란?

**답변** `🌐 개념 정리`
> 정규화는 겹겹이 중첩된 데이터를 **id로 찾는 표 하나와 id 목록으로 펼쳐서 저장하는 것**입니다.
> 같은 데이터가 여기저기 복사되는 걸 막아서, **한 곳만 고치면 쓰는 데 전부 반영**됩니다.
> 안 하면 같은 사용자 정보가 세 군데 있고 하나만 갱신되는 상황이 생깁니다.

**30초 버전** — "중첩 데이터를 id로 찾는 표와 id 목록으로 펼쳐 저장해서, 한 곳만 고쳐도 전부 반영되게 하는 겁니다."

**꼬리 질문 대비**
- **"React Query를 쓰면 정규화가 필요 없나요?"** → React Query는 쿼리 단위로 캐시해서 정규화를 안 합니다. 같은 데이터가 여러 쿼리에 있으면 invalidate로 같이 다시 가져오게 맞춥니다.

> 예전에 따로 있던 루틴 이력 스토어, 타이머 버그 추적용 스토어 같은 걸 관련 스토어 안으로 옮겼습니다.
> 방식은 **새 스토어의 migrate 안에서 옛 저장 키를 읽어 옮겨 담고, 옛 키는 지우는 것**이었습니다.
>
> 제가 한 건 그렇게 합쳐진 **루틴 스토어 안에서 같은 목록이 세 번 저장되던 걸** 걷어낸 겁니다.

**30초 버전** — "스토어 통합은 팀원이 먼저 한 작업이고, 저는 합쳐진 루틴 스토어 안에서 같은 목록이 세 번 저장되던 걸 없앴습니다."

**꼬리 질문 대비**
- **"팀원 작업인데 어떻게 그렇게 잘 아세요?"** → 같은 스토어의 migrate를 고치면서(v1 → v2) 옛 키를 옮기는 코드를 같이 읽었기 때문이라고 답합니다.

**포인트** — 팀원 작업을 알고 있다는 것 자체가 **코드베이스를 넓게 봤다**는 신호가 됩니다. 억지로 내 것으로 만들지 마세요.

### Q18. 스토어를 크게 합치면 리렌더 범위가 넓어지지 않나요?

**답변** `📁 내 경험`
> Zustand는 **selector로 꺼낸 값이 바뀐 컴포넌트만** 다시 그리기 때문에, 스토어 크기와 리렌더 범위가 바로 연결되지는 않습니다.
> 실제로 정렬된 루틴 목록은 화면·훅 29곳에서 `state => state.sortedRoutineList` 처럼 **그 값 하나만** 꺼내 씁니다.
> 같은 스토어의 알람 소리 설정이 바뀌어도, 이 목록 참조가 그대로면 그 화면들은 다시 그려지지 않습니다.

**30초 버전** — "Zustand는 꺼낸 값이 바뀐 곳만 다시 그려서 스토어 크기와 리렌더 범위가 바로 묶이지 않습니다. 루틴 목록은 29곳에서 그 값 하나만 구독합니다."

**꼬리 질문 대비**
- **"참조가 그대로라는 건 어떻게 보장하나요?"** → 계산값을 넣기 전에 이전 값과 한 단계 안쪽까지 비교해서 같으면 이전 배열을 둡니다. Q23으로 이어집니다.

### Q19. 파생 상태가 뭐고, 따로 저장하면 뭐가 문제인가요?

**답변 (실제 사례로)** `📁 내 경험`
> 파생 상태는 **다른 값에서 계산해낼 수 있는 값**입니다.
>
> 루틴 스토어에는 원본인 루틴 목록 말고도 두 개가 더 저장돼 있었습니다.
> - **정렬된 목록** — 순서·시작 시각·제목 순으로 정렬하고, 보관·삭제된 건 뺀 것
> - **날짜별 활성 목록** — 루틴마다 날짜별로 켜져 있는지 펼쳐둔 것
>
> 둘 다 원본에서 계산할 수 있는데 따로 저장하니까, **원본을 바꿀 때마다 나머지 둘도 직접 맞춰줘야** 했습니다.
> 루틴 하나를 추가하는 코드에서도 날짜별 목록을 손으로 다시 만들어 끼워 넣고 있었습니다.
> **한 군데라도 빠뜨리면 원본과 화면이 어긋나는** 구조였습니다.

**30초 버전** — "원본에서 계산할 수 있는 값입니다. 루틴 스토어가 정렬 목록과 날짜별 목록을 따로 저장해서, 원본을 바꿀 때마다 손으로 맞춰야 했고 하나만 빠져도 화면이 어긋났습니다."

**꼬리 질문 대비**
- **"실제로 어긋난 버그가 있었나요?"** → 있었다면 [ 실제로 어긋났던 버그 사례 ], 없으면 "어긋날 수 있는 구조였다"까지만 말합니다.

### Q20. Zustand에는 computed가 없는데, 어떻게 구현하셨나요?

**⚠️ 가장 나올 확률이 높은 질문입니다.**

**답변** `📁 내 경험`
> **`zustand-computed`라는 미들웨어**를 썼습니다.
> 스토어에 값이 저장될 때마다 계산 함수를 돌려서, 그 결과를 상태에 합쳐 넣어줍니다.
> 화면 쪽에서는 **보통 필드처럼 꺼내 쓰면** 됩니다. 쓰는 쪽 코드는 거의 안 바뀌었습니다.
>
> 계산값이 디스크에 같이 저장되면 안 되니까, persist의 **`partialize` — 저장할 필드만 고르는 옵션 — 로 계산값 두 개를 저장 대상에서 뺐습니다.**

**30초 버전** — "`zustand-computed` 미들웨어로 저장될 때마다 계산값을 상태에 합쳐 넣었고, 계산값은 `partialize`로 디스크 저장에서 뺐습니다."

**꼬리 질문 대비**
- **"selector나 useMemo로 계산하면 되지, 왜 라이브러리를 썼나요?"** → **React 바깥에서 이 값을 읽는 코드가 있었기 때문**입니다. 위치 기반 알림·위젯·백그라운드 처리 코드는 `getState()`로 스토어를 직접 읽어서, 컴포넌트 안에서만 생기는 값으론 안 됩니다. 스토어 안에 있으면 **어디서 읽든 같은 값**을 봅니다. 그리고 selector 안에서 정렬하면 **구독하는 29곳이 각자 정렬**합니다.

### Q21. set 호출이 3회에서 1회로 줄었다는 건 무슨 의미인가요?

**답변** `📁 내 경험`
> 전에는 목록이 바뀌면 **원본 저장, 정렬 목록 저장, 날짜별 목록 저장**을 차례로 불렀습니다.
> 그러면 세 가지 문제가 있었습니다.
> - 저장할 때마다 구독자에게 알림이 가니까 **그리기 판단이 세 번** 일어납니다.
> - 첫 번째와 세 번째 사이에 **원본은 새 것, 정렬 목록은 옛것인 중간 상태**가 잠깐 생깁니다.
> - persist가 붙어 있어서 **디스크 쓰기도 세 번** 일어납니다.
>
> 지금은 원본만 저장하면 나머지가 같이 계산돼 들어가서 한 번으로 끝납니다.
> 그런데 제가 가장 크게 본 건 횟수보다 **빠뜨릴 수 없게 됐다**는 점입니다. setter 두 개를 아예 지웠으니까요.

**30초 버전** — "목록 하나 바꿀 때 저장을 세 번 하던 걸 원본 한 번으로 줄여서, 알림·중간 상태·디스크 쓰기가 한 번이 됐습니다. 더 큰 건 setter 두 개를 지워서 빠뜨릴 수 없게 된 점입니다."

**꼬리 질문 대비**
- **"리렌더가 실제로 얼마나 줄었나요?"** → **렌더 횟수를 따로 재지는 않았습니다.** 확인한 건 저장 호출 횟수와, 손으로 맞추던 코드가 사라진 것까지입니다.

**포인트** — 수치가 없는 건 **없다고** 말하세요. 지어내면 다음 질문에서 무너집니다.

### Q22. 저장할 때마다 다시 계산하면 오히려 비용이 늘지 않나요?

**⚠️ 약점이 있는 질문입니다. 먼저 인정하는 편이 낫습니다.**

**답변** `📁 내 경험`
> **이 부분은 지금 다시 보면 아쉬운 점이 있습니다.**
>
> 라이브러리에 **"이 키가 바뀔 때만 다시 계산하라"는 `keys` 옵션**이 있는데 그걸 안 줬습니다.
> 그래서 루틴 목록과 상관없는 값, 예를 들어 알람 소리 설정이 저장될 때도 계산이 다시 돕니다.
>
> 정렬은 루틴이 수십 개 수준이라 가볍습니다.
> 문제는 날짜별 활성 목록입니다. **루틴마다 날짜 수만큼 객체를 만들어서** 오래 쓴 사용자일수록 무거워집니다.
> (Q9의 메모리 분석에서 나온 그 구조입니다.)
>
> 다시 한다면 **`keys`에 루틴 목록·하루 마감 시각·활성 이력 세 개만 지정**하고,
> 두 계산이 서로 다른 값에 의존하니까 **계산 함수도 둘로 나눌** 겁니다.

**30초 버전** — "네, 아쉬운 점입니다. `keys` 옵션을 안 줘서 상관없는 값이 저장될 때도 재계산되고, 특히 날짜별 목록이 무겁습니다. 다시 하면 의존하는 세 키만 지정하고 계산 함수도 둘로 나누겠습니다."

**꼬리 질문 대비**
- **"그럼 왜 그때 안 넣었나요?"** → 지어내지 말고 [ 당시 keys를 안 넣은 실제 이유 ]만큼만 말하고, 바로 고칠 방법으로 넘어갑니다.

**포인트** — 약점을 먼저 꺼내고 **고칠 방법까지** 말하면 오히려 점수가 됩니다.
코드 주석의 "의존성 변경 시에만 재계산"을 그대로 믿고 말하면, 면접관이 라이브러리를 알 경우 바로 틀립니다.

### Q23. selector가 매번 새 배열을 돌려주면 리렌더가 계속 일어나지 않나요?

**답변** `📁 내 경험`
> selector **안에서** 정렬하면 그렇습니다. 부를 때마다 새 배열이 나오니까요.
> Zustand v5에서는 이게 **무한 리렌더 경고**로까지 이어집니다.
>
> 지금 구조에서는 selector가 **스토어에 이미 들어 있는 배열을 꺼내기만** 합니다.
> 그리고 이 라이브러리는 새로 계산한 값을 넣기 전에 **이전 값과 한 단계 안쪽까지 비교**합니다.
> 정렬 목록은 안에 든 루틴 객체들이 그대로면 **이전 배열을 그대로 둡니다.**
> 그래서 참조가 유지되고, 목록을 보는 화면은 다시 그려지지 않습니다.

**30초 버전** — "selector 안에서 정렬하면 그렇지만, 저희는 스토어에 이미 계산된 배열을 꺼내기만 하고, 라이브러리가 한 단계 안쪽까지 비교해 같으면 이전 배열을 유지해서 참조가 안 바뀝니다."

**꼬리 질문 대비**
- **"날짜별 목록도 그런가요?"** → 안쪽에 객체가 한 겹 더 있어서 **계산할 때마다 새 참조**가 됩니다. 다만 컴포넌트가 구독하지 않고 `getState()`로만 읽어서 리렌더 문제로는 번지지 않았습니다. **비용은 리렌더가 아니라 계산 쪽**입니다(Q22).

### Q24. 계산 중에 에러가 나면 어떻게 되나요?

**답변** `📁 내 경험`
> 날짜별 목록은 **루틴 하나씩 따로 감싸서**, 한 루틴이 실패하면 그 루틴만 빈 값으로 두고 나머지는 계속 계산합니다.
> 실패한 건 Sentry로 보고합니다.
> 계산값은 저장이 일어날 때마다 돌기 때문에, 여기서 에러가 밖으로 새면 **스토어 저장 자체가 깨집니다.**
> 그래서 계산 함수 안에서 반드시 막아야 했습니다.

**30초 버전** — "계산이 저장마다 돌아서 에러가 새면 저장 자체가 깨집니다. 그래서 루틴 하나씩 감싸 실패한 루틴만 빈 값으로 두고 Sentry로 보고합니다."

**꼬리 질문 대비**
- **"빈 값이면 사용자에겐 어떻게 보이나요?"** → 그 루틴 하나의 날짜별 값만 비고 나머지 루틴은 정상으로 계산된다고 답하고, **스토어 저장 전체가 깨지는 것보다 낫다**는 판단이라고 말합니다.

### version · migrate

### Q25. version과 migrate가 왜 필요한가요? 없으면 어떻게 되나요?

**답변** `🌐 개념 정리`
> 앱을 업데이트해도 **디스크에는 옛 코드가 저장한 모양 그대로** 데이터가 남아 있습니다.
> 새 코드가 그걸 그대로 읽으면 없는 필드를 찾거나, 이제 안 쓰는 필드를 끌고 다니게 됩니다.
>
> persist는 저장할 때 버전 번호를 같이 적어둡니다.
> 불러올 때 **저장된 번호와 코드의 번호가 다르면 migrate를 불러서** 옛 모양을 새 모양으로 바꿀 기회를 줍니다.

**30초 버전** — "업데이트해도 디스크엔 옛 모양 데이터가 남아 있어서, 저장된 버전과 코드 버전이 다르면 migrate로 새 모양으로 바꿔줍니다."

**꼬리 질문 대비**
- **"버전만 올리고 migrate를 안 쓰면요?"** → 저장된 데이터를 **못 옮긴다고 보고 버립니다.** 사용자 입장에선 루틴이 사라진 것처럼 보이니, 버전을 올리면 migrate는 반드시 같이 있어야 합니다.

### Q26. 실제로 어떤 구조 변경이 있었고, migrate는 어떻게 짰나요?

**답변** `📁 내 경험`
> computed로 바꾸면서 **정렬 목록과 날짜별 목록이 더 이상 저장 대상이 아니게** 됐습니다.
> 그런데 기존 사용자 디스크에는 두 값이 그대로 남아 있습니다. 특히 날짜별 목록은 꽤 큽니다.
>
> 그래서 루틴 스토어 버전을 **1에서 2로 올리고**, migrate에서
> **저장된 버전이 2보다 작으면 두 필드를 지우게** 했습니다.
>
> 사실 저장 대상에서 뺐으니 다음 저장 때 자연스럽게 빠지긴 합니다.
> 그래도 버전을 올린 건 **그 전까지 안 쓰는 큰 데이터를 계속 읽는 걸 막고, 구조가 바뀌었다는 걸 코드에 남기려고**였습니다.

```ts
version: 2,
migrate: (persisted, version) => {
  if (version < 2) {
    delete persisted.sortedRoutineList;
    delete persisted.routineActiveList;
  }
  return persisted;
},
```

**30초 버전** — "computed로 바꾸며 계산값 두 개가 저장 대상에서 빠져서, 루틴 스토어를 v1에서 v2로 올리고 `version < 2`면 옛 계산값을 지우게 했습니다."

**꼬리 질문 대비**
- **"partialize로 뺐으면 migrate 없이도 빠지지 않나요?"** → 다음 저장 때 빠지긴 하지만, **그 전까지 큰 옛 데이터를 읽는 걸 막고 구조 변경을 코드에 남기려고** 올렸다고 답합니다.

### Q27. 사용자가 여러 버전을 건너뛰고 업데이트하면요? (v1 → v4)

**답변** `🌐 개념 정리`
> migrate에는 **사용자 디스크에 저장된 버전**이 들어옵니다. 그래서 조건을 `===`가 아니라 **`<`로** 씁니다.

```ts
if (version < 2) { /* 1 → 2 */ }
if (version < 3) { /* 2 → 3 */ }
if (version < 4) { /* 3 → 4 */ }
```

> 이렇게 쌓아두면 v1 사용자는 세 단계를 **차례로 다 거치고**, v3 사용자는 마지막 것만 거칩니다.
> `version === 1` 처럼 쓰면 v1 사용자가 한 단계만 옮겨지고 멈춥니다.

**30초 버전** — "migrate엔 디스크에 저장된 버전이 들어오니까 `<` 조건을 차례로 쌓아서, 건너뛴 사용자도 모든 단계를 순서대로 거치게 합니다."

**꼬리 질문 대비**
- **"루티너리 코드는 어떻게 돼 있나요?"** → 루틴 스토어는 `<`로 돼 있고, 다른 스토어 중엔 `=== 0`인 곳이 있어 다음 버전이 생기면 깨질 모양이라고 답합니다(아래 포인트).

**포인트** — 루틴 스토어는 `<`로 짜여 있습니다. 같은 코드베이스의 다른 스토어 중엔 `=== 0`으로 된 곳도 있는데,
지금은 단계가 하나라 괜찮지만 **다음 버전이 생기면 깨지는 모양**입니다. 물어보면 이 차이를 말할 수 있으면 좋습니다.

### Q28. migrate가 실패하면 어떻게 되나요?

**답변** `📁 내 경험`
> persist는 migrate가 에러를 던지면 **저장된 값을 못 불러오고 초기값으로 시작합니다.**
> 더 위험한 건 그다음입니다. 초기값인 상태에서 **다음 저장이 한 번 일어나면 디스크의 원래 데이터까지 덮어씁니다.**
> 사용자 데이터가 실제로 날아가는 겁니다.
>
> 그래서 루틴 스토어에서는 **옛 저장 키를 읽어 옮기는 부분처럼 실패할 수 있는 곳을 try로 감싸고**,
> 실패하면 그 단계만 건너뛰고 Sentry로 보고한 뒤 나머지는 그대로 돌려줍니다.
> 필드를 지우는 부분은 실패할 일이 없어서 감싸지 않았습니다.
>
> MobX에서 Zustand로 옮기는 마이그레이션도 같은 원칙이었습니다. **실패해도 앱은 뜨게 하고, 보고만 합니다.**

**30초 버전** — "migrate가 실패하면 초기값으로 시작하고, 다음 저장 때 원래 데이터까지 덮어써서 데이터가 날아갑니다. 그래서 실패할 수 있는 부분만 try로 감싸 그 단계만 건너뛰고 Sentry로 보고합니다."

**꼬리 질문 대비**
- **"try로 감싼 부분이 실패하면 그 데이터는요?"** → 옛 키를 옮기는 단계만 건너뛰고 옛 키도 안 지워지니(지우는 코드가 같은 try 안), 원본은 디스크에 남는다고 답합니다.

### Q29. 저장할 필드는 어떻게 고르셨나요?

**답변** `📁 내 경험`
> **"다른 곳에서 다시 만들 수 있는 건 저장하지 않는다"** 가 기준이었습니다.
> - 계산값 두 개 — 원본에서 다시 계산되니까 빼고,
> - 하루 마감 시각 — 이 값의 주인은 사용자 스토어라서 뺐습니다. 루틴 스토어엔 정렬에 쓰려고 **받아오기만** 합니다.
>
> 두 곳에 저장하면 어느 쪽이 맞는지 다시 따져야 하니까요.

**30초 버전** — "다시 만들 수 있는 건 저장하지 않았습니다. 계산값은 원본에서, 하루 마감 시각은 주인인 사용자 스토어에서 받아오기만 합니다."

**꼬리 질문 대비**
- **"받아오는 건 어떻게 하나요?"** → 스토어 간 값 전달은 **구독으로 즉시 반영**되게 돼 있다고 답합니다(Q10 표현 주의).

### Q30. 스토어가 21개면 버전도 21개를 따로 관리하나요? 스토어끼리 데이터를 옮기면요?

**답변** `📁 내 경험`
> 네, 버전은 **스토어마다 따로** 있습니다. 대부분은 한 번도 안 올라간 상태고, 구조가 바뀐 스토어만 올립니다.
>
> 스토어끼리 데이터를 옮길 때는 **받는 쪽 스토어의 migrate에서 옛 저장 키를 직접 읽어오고, 다 옮긴 뒤 옛 키를 지우는** 방식이었습니다.
> 옛 키를 지워야 다음 실행 때 두 번 옮겨지지 않습니다.

**30초 버전** — "버전은 스토어마다 따로 있고 구조가 바뀐 곳만 올립니다. 스토어 간 이동은 받는 쪽 migrate에서 옛 키를 읽어 옮기고 옛 키를 지웁니다."

**꼬리 질문 대비**
- **"그 방식의 함정은요?"** → **받는 쪽 버전을 안 올리면 migrate 자체가 안 돕니다.** persist는 버전이 다를 때만 migrate를 부르니까요. 실제로 같은 코드베이스에 **버전 없이 migrate만 적힌 스토어**가 있어서, 그 옮기는 코드는 한 번도 실행되지 않는 상태입니다.

> ⚠️ 이건 **재직 중에 발견하거나 고친 게 아닙니다.** 말한다면 "다시 보니 이런 함정이 있더라"로만 말하세요.

### Q31. 그냥 스토어를 하나로 만들면 되지 않았나요?

**답변** `📁 내 경험`
> 하나로 모으면 **persist 저장 단위도 하나**가 됩니다.
> 타이머 상태 하나 바뀌어도 루틴 이력까지 통째로 디스크에 다시 씁니다. 루틴 이력은 오래 쓴 사용자일수록 큽니다.
> 그리고 버전도 하나라서, **어느 한 부분 구조만 바뀌어도 전체 migrate를 건드려야** 합니다.
>
> 그래서 **바뀌는 이유와 저장 주기가 다른 건 나눠두는 게 맞다**고 봤습니다.

**30초 버전** — "하나로 모으면 타이머 하나 바뀌어도 큰 루틴 이력까지 통째로 다시 쓰고, 버전도 하나라 작은 구조 변경에도 전체 migrate를 건드려야 합니다."

**꼬리 질문 대비**
- **"리렌더는 하나로 해도 selector로 막을 수 있잖아요?"** → 맞다고 인정하고(Q18), 문제는 리렌더가 아니라 **저장 단위와 버전 관리**라고 답합니다.

### Q32. 이 작업으로 사용자가 체감한 개선이 있었나요?

### Q33. 다시 고른다면 Zustand를 또 쓰시겠어요? Jotai처럼 파생 상태를 기본으로 지원하는 건요?
