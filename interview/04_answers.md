# 답변 가이드 — 자주 나오는 질문 30선

> **주의**: 아래는 *답변의 뼈대*입니다. 그대로 외우면 티가 납니다.
> `[ ]` 부분은 본인만 아는 사실이니 직접 채우세요.
> 코드에서 확인한 근거는 그대로 써도 됩니다.
>
> 답변은 두 종류로 나눴습니다.
> - **`📁 내 경험`** — 이력서·실제 프로젝트에서 꺼낸 답입니다. 이 답을 먼저 말하세요.
> - **`🌐 개념 정리`** — 특정 경험보다 일반적인 접근을 정리한 답입니다. 외우기보다 **이해해서 내 말로** 하세요.

## 답변의 기본 틀

경험 질문은 대부분 이 순서로 답하면 됩니다.

```
상황 (왜 문제였나)  →  판단 (무엇을 골랐나, 왜)  →  결과 (어떻게 됐나)  →  배운 점
```

40초~1분이 적당합니다. 길어지면 면접관이 끊습니다.
**결과에 숫자가 있으면 조건과 함께** 말하세요.

## Q1. AI 개발 하네스를 만들게 된 계기는?

**뼈대** `📁 내 경험`
> **→ 새 코드라도 막으려고, 편집한 파일 에러만 걸러서 막는 하네스를 만들었습니다.** 레거시 에러 때문에 전체 검증을 켤 수 없었기 때문입니다.
>
> **→ 레거시 타입 에러가 이미 수백 개(367개)였습니다.** 전체 검증을 켜면 매번 수백 개가 쏟아져서 아무도 안 봅니다.
>
> **→ 문제는 새로 짜는 코드까지 같이 방치된다는 것이었습니다.**
>
> **→ 검사는 전체로, 막는 건 이번에 편집한 파일 에러만입니다.** 전체를 다 고치는 건 현실적으로 어려우니, **최소한 새 코드는 막아두자**는 판단이었습니다.

**30초 버전** — "레거시 타입 에러가 367개라 전체 검증을 켤 수 없었습니다. 그래서 새 코드라도 막으려고, 이번에 편집한 파일 에러만 걸러서 막는 하네스를 만들었습니다."

**꼬리 질문 대비**

**→ "전체를 고칠 생각은 안 했나요?"** 견적을 내봤는데 [ ]였고, 그 사이 **새 에러가 계속 쌓이는 게 더 문제**라고 봤습니다. 이건 에러를 줄이는 게 아니라 **더 늘지 않게 하는 장치**라, 파일을 건드릴 때 같이 고치면 점점 줄어든다고 답합니다.

**→ "파일 하나만 타입 검사가 되나요?"** 안 됩니다. 파일끼리 서로 참조해서요. **검사는 전체, 거르는 건 결과**라고 정확히 말합니다. (→ 17번 참고)

**포인트** — "AI를 써보고 싶어서"가 아니라 **구체적 문제에서 출발**했다는 걸 보여주세요.
367개라는 숫자를 기억하고 있으면 신뢰도가 올라갑니다.

## Q5. 한 번에 다 만들지 않고 단계적으로 도입한 이유는?

**뼈대** `📁 내 경험`
> **→ 거부감이 생기면 아무도 안 쓰는 도구라, 방해가 적은 것부터 넣었습니다.** 개발 흐름에 끼어드는 도구이기 때문입니다.
>
> **→ 처음엔 저장할 때 자동 포맷만 넣었습니다.** 이건 불편이 없으니까요.
>
> **→ 그다음 작업을 끝낼 때 타입 검증으로 막는 것을 넣었습니다.**
>
> **→ 리뷰·빌드 진단처럼 판단이 필요한 건 마지막에 붙였습니다.**

**30초 버전** — "거부감이 생기면 안 쓰는 도구라, 불편 없는 자동 포맷부터 넣고, 타입 검증 차단, 마지막에 리뷰·빌드 진단 순서로 붙였습니다."

**꼬리 질문 대비**

**→ "처음부터 차단을 걸었으면 더 빨랐지 않나요?"** 빠를 순 있어도, 처음부터 막히면 "왜 내 작업을 막냐"로 끝나서 **꺼버리게 된다**고 봤습니다. **익숙해진 다음에 막는 게** 오래 간다고 답합니다.

**포인트** — 기술 순서가 아니라 **사람이 받아들이는 순서**로 설계했다는 점.

## Q6~7. 팀 배포의 어려움 / 팀원 반응은?

**뼈대** `📁 내 경험`
> **→ 차단을 본인이 건드린 파일로만 한정해서, 남의 에러로 막히지 않게 했습니다.** 가장 걱정한 건 **"왜 내 작업을 막느냐"는** 반응이었습니다.
>
> **→ 남이 만든 에러로 내가 막히면 바로 신뢰를 잃습니다.** 그래서 차단은 **본인이 이번에 건드린 파일**로만 걸었습니다.
>
> **→ 온보딩 문서를 쓰고 PR로 리뷰를 받은 다음 도입했습니다.** [ 실제 반응 — 우려 / 무관심 / 호응 ]
>
> **→ 다른 분들이 직접 규칙을 추가하기 시작했을 때 자리 잡았다고 느꼈습니다.**

**30초 버전** — "남의 에러로 막히지 않게 본인이 건드린 파일만 막았고, 문서와 PR 리뷰를 거쳐 도입했습니다. 다른 분들이 직접 규칙을 추가하기 시작한 게 자리 잡은 신호였습니다."

**꼬리 질문 대비**

**→ "반대하는 사람은 어떻게 설득했나요?"** [ 실제 사례 ]. 없었다면 지어내지 말고, 처음부터 **반대할 이유(남의 에러로 막힘)를 설계에서 없앴다**는 쪽으로 답합니다.

**포인트** — "공동 운영"이 하네스의 **성공 지표**였다는 프레이밍.

## Q10. 효과를 숫자로 확인한 게 있나요?

**정직하게 가세요.** `📁 내 경험`
> **→ 숫자로는 재지 못했습니다.** 리뷰 시간이나 버그 수를 따로 측정하진 못했습니다.
>
> **→ 체감한 변화는 있었습니다.** [ 체감한 변화 — 예: 리뷰에서 스타일 지적이 줄고 설계 얘기가 늘었다 ]
>
> **→ 다시 한다면 도입 전에 기준값을 먼저 재두겠습니다.**

**30초 버전** — "숫자로 재진 못했습니다. 체감 변화는 [ ]였고, 다시 하면 도입 전에 기준값부터 재두겠습니다."

**꼬리 질문 대비**

**→ "그럼 뭘 재면 됐을까요?"** [ 본인 생각 ]. 예를 들면 리뷰에서 타입·스타일 지적이 몇 건 나오는지처럼 **도입 전후를 같은 기준으로 셀 수 있는 것**을 고르겠다고 답합니다.

**포인트** — 없는 숫자를 만들지 마세요. **"측정 안 했다 + 다음엔 이렇게"** 가 정답입니다.

## Q17. 자동 수정을 허용하지 않고 진단만 하게 한 이유는?

**뼈대** `📁 내 경험`
> **→ 진단까지만 AI에게 받고, 적용은 사람이 판단하게 했습니다.** AI가 빌드 로그를 보고 원인을 짚는 건 잘합니다.
>
> **→ 고치는 것까지 맡기면 검증 안 된 변경이 조용히 들어옵니다.**
>
> **→ 빌드 설정·네이티브 쪽은 특히 위험합니다.** 잘못 건드리면 **원인 찾기가 더 어려워집니다.**
>
> **→ "원인은 이거고, 이렇게 고치면 된다"까지만 받습니다.** **적용은 사람이 판단**합니다.

**30초 버전** — "원인 찾기는 AI가 잘하지만 고치기까지 맡기면 검증 안 된 변경이 들어와서, 진단까지만 받고 적용은 사람이 하게 했습니다."

**꼬리 질문 대비**

**→ "그럼 속도가 느려지지 않나요?"** 적용 한 번을 사람이 하는 비용보다, 빌드 설정이 잘못 바뀌었을 때 **그걸 찾는 비용이 훨씬 크다**는 쪽으로 답합니다. 체감한 시간 차이가 있으면 [ ]로 덧붙입니다.

**포인트** — AI를 무비판적으로 신뢰하지 않는다는 신호. 면접관이 좋아합니다.

## Q26~28. 메모리 문제를 어떻게 처음 알게 됐나요?

**뼈대** `📁 내 경험`
> **→ [ 크래시 리포트 / QA 제보 / 직접 발견 ]로 알게 됐습니다.**
>
> **→ 특정 화면을 오래 쓰면 메모리가 계속 오르는 패턴이었습니다.**
>
> **→ 결국 안드로이드 OutOfMemory(메모리 부족) 크래시로 이어졌습니다.**
>
> **→ 원인을 좁히는 데 [ 기간 ] 걸렸습니다.**

**30초 버전** — "[ 계기 ]로 알게 됐고, 화면을 오래 쓰면 메모리가 계속 올라 안드로이드에서 메모리 부족 크래시까지 이어지는 패턴이었습니다."

**꼬리 질문 대비**

**→ "처음 세운 가설이 틀린 적 있나요?"** (거의 항상 나옵니다) 처음엔 **이미지 캐시를 의심**했는데 아니었습니다. 화면을 오갈 때마다 늘어나는 걸 보고 **화면이 사라질 때 정리가 안 되는 쪽**으로 방향을 틀었고, 애니메이션 값(Reanimated SharedValue)이 **화면이 없어진 뒤에도 남아 있는 걸** 찾았습니다.

**포인트** — 틀린 가설을 말하는 게 **감점이 아니라 가점**입니다. 디버깅 과정을 보여주세요.

## Q31~34. 어떻게 측정했고, 69%는 예상한 수준이었나요?

**⚠️ 숫자 기준** — 면접에서는 **PDF 기준**(실사용자 지표)으로 먼저 말하세요. md 이력서의 Debug 빌드 숫자를 섞으면 앞뒤가 안 맞습니다. (→ 17번 상단 표)

**뼈대** `📁 내 경험`
> **→ 실사용자 Peak Memory(P95)가 958.5MB에서 297.4MB로 69% 줄었습니다.** 제출한 이력서 기준이고, P95는 **상위 5% 나쁜 구간의 최고 메모리**입니다.
>
> **→ 고치는 동안은 안드로이드 네이티브 힙을 직접 쟀습니다.** 같은 조작을 반복하는 시나리오를 정해두고 **수정 전후를 같은 조건**에서 비교했습니다.
>
> **→ 누적 할당량 기준 101.9MB → 31.2MB였습니다.** 회수되지 않고 남는 양은 **31.2MB → 11MB**였습니다.
>
> **→ 솔직히 이 정도까지 나올 줄은 몰랐습니다.** **정리되지 않던 값이 24개**라 누적 효과가 컸습니다.

**30초 버전** — "실사용자 P95 피크 메모리가 958.5MB에서 297.4MB로 69% 줄었습니다. 고치는 동안엔 같은 시나리오로 안드로이드 네이티브 힙을 재서 전후를 비교했고, 정리 안 되던 값이 24개라 효과가 컸습니다."

**꼬리 질문 대비**

**→ "69%면 너무 많이 줄어든 것 아닌가요?"** 정리 안 되던 값이 **24개**였고 화면을 오갈수록 쌓이는 구조였다고 답합니다. 그리고 **P95라 원래 가장 나쁜 구간**이었다는 점을 덧붙입니다.

**→ "메모리 69%면 상주 메모리가 그만큼 준 건가요?"** 아닙니다. 안드로이드 쪽 숫자는 **누적 할당량 기준**이라고 바로 구분합니다.

**⚠️ 중요** — "메모리 69% 감소"라고만 하면 *상주 메모리*로 오해받습니다.
**"누적 할당량 기준"**(md 숫자) 또는 **"Peak Memory P95"**(PDF 숫자)를 반드시 붙이세요. 되물었을 때 못 답하면 신뢰를 잃습니다.

## Q39. 지연 로딩하면 처음 들어갈 때 느려질 텐데, 확인했나요?

**⚠️ 사실관계 — lazy 로딩은 구현했다가 최종적으로 제거했습니다.** 현재 코드는 전부 정적 import입니다.

**뼈대 (결말까지 말하는 게 핵심)** `📁 내 경험`
> **→ 정확히 그 트레이드오프 때문에 결국 되돌렸습니다.**
>
> **→ 처음엔 화면 62개를 lazy(필요할 때 불러오기)로 바꿨습니다.** 시작 시간이 줄어드는 건 확인했습니다.
>
> **→ 그런데 화면 전환할 때 한 번 깜빡이는 느낌이 생겼습니다.** lazy 경계마다 Suspense와 스켈레톤이 붙었기 때문입니다.
>
> **→ 시작은 한 번이고 화면 전환은 매번입니다.** 그쪽 비용이 더 크다고 판단했습니다.
>
> **→ 판단 근거는 프로덕션 베이스라인으로 만들었습니다.** **lazy를 잠깐 걷어내서 재보고**, 다시 복구했다가 최종적으로 제거했습니다.

**30초 버전** — "화면 62개를 lazy로 바꿔 시작은 빨라졌지만 화면 전환마다 깜빡임이 생겼습니다. 시작은 한 번, 전환은 매번이라 프로덕션 기준값을 재본 뒤 제 작업을 되돌렸습니다."

**꼬리 질문 대비**

**→ "그럼 그 작업은 헛수고였나요?"** 아닙니다. lazy는 걷었지만 **측정 체계와 telemetry(계측 데이터 수집)는 남겼고**, 그 덕에 다음 판단도 숫자로 할 수 있게 됐다고 답합니다.

**포인트** — 이건 **약점이 아니라 강점으로 말할 수 있는 항목**입니다.
"성능 개선했습니다"가 아니라 **"측정해보고 제 작업을 되돌렸습니다"** 이기 때문입니다.
자기 코드에 애착 없이 데이터로 판단했다는 신호이고, **커밋 히스토리에 그 과정이 남아 있어 증명도 됩니다.**

**⚠️ 이력서 표현 주의** — "약 50개 화면을 제외했다"는 **현재 코드와 다릅니다.**
질문받기 전에 먼저 "그건 되돌렸습니다"를 꺼내세요.

## Q45~50. 상태 관리를 손본 계기와 위험 관리

**뼈대** `📁 내 경험`
> **→ 파생 데이터는 저장하지 않고 계산하게 바꾸고, 기존 데이터는 마이그레이션으로 옮겼습니다.**
>
> **→ 계기는 한쪽만 바뀌는 버그였습니다.** 같은 데이터가 여러 스토어에 흩어져 있어서 반복됐습니다.
>
> **→ 핵심은 파생 데이터를 계산해서 쓰는 구조입니다.** 파생 데이터는 **다른 값에서 계산되는 값**입니다.
>
> **→ 제일 걱정은 기존 사용자 데이터였습니다.** 이미 서비스 중이라 저장된 값을 새 구조로 옮기는 **마이그레이션을 따로** 만들었습니다.
>

**포인트** — 무조건 "의존성이 적어서 좋다"가 아니라 **트레이드오프를 인지**했다는 게 중요합니다.

## Q168~169. 원인 모를 버그 / 재현 안 되는 버그

**뼈대** `🌐 개념 정리`
> **→ 재현 조건부터 좁히고, 가설은 한 번에 하나씩만 바꿔서 확인합니다.**
>
> **→ 재현이 되면 절반은 끝난 겁니다.** 그래서 **재현 조건을 좁히는 데** 먼저 시간을 씁니다.
>
> **→ 재현이 안 되면 로그와 리포트에서 공통점을 찾습니다.** 기기, OS 버전, 특정 화면 순서 같은 것들요.
>
> **→ 가설은 하나씩 배제하고, 한 번에 하나만 바꿉니다.** 여러 개를 동시에 바꾸면 **뭐가 효과였는지 모르게** 됩니다.

**▶ 내 경험**
> **→ 메모리 누수(→ Q26~28)가 좋은 예입니다.** **이미지 캐시 가설을 버리고**, 화면을 오갈 때마다 늘어나는 패턴으로 **"화면 정리" 쪽으로 좁혔습니다.**

**30초 버전** — "재현 조건부터 좁히고, 안 되면 로그에서 기기·OS·화면 순서의 공통점을 찾습니다. 가설은 한 번에 하나씩만 바꿔서 확인합니다."

**꼬리 질문 대비**

**→ "끝내 재현이 안 되면요?"** 원인을 못 찾아도 **로그를 더 심어서 다음에 잡히게** 하고, 그 사이 **사용자 피해를 줄이는 방어 코드**를 넣는다고 답합니다.

## Q178. 테스트가 많지 않은 환경에서 안정성을 어떻게 지켰나요?

>
> **→ 대신 [ 크래시 모니터링 / 단계적 배포 / 실기기 확인 ]으로 보완했습니다.**

**꼬리 질문 대비**

**→ "왜 그때 테스트를 안 붙였나요?"** [ 실제 사정 ]. 핑계보다 **우선순위를 어떻게 정할지**(데이터가 깨지는 곳 먼저)로 답을 마무리합니다.
