## 2. 성능 · 측정

### Q2. 이력서 첫 줄의 성능 개선 — 어떻게 측정하고 개선했나요? (20:06)

**실제 답변** — "매달 마지막 주에 Xcode Organizer로 메모리를 확인. 입사 두 달 후 978인가, 958까지 튄 걸 발견. 버전별로 나뉘어 있어서 전후에 뭘 했는지 확인 → 애니메이션에서 리턴(정리)을 안 해주고 있었음 → 정리하는 훅을 만들어 24곳에 적용 → Performance Monitor와 Instruments로 개선 확인 후 배포."

**문제점**
- **흐름은 좋았습니다.** 측정 주기 → 발견 → 버전별 비교 → 원인 → 공용 훅 → 재측정 → 배포. 이 순서를 유지하세요.
- **숫자가 또 흔들렸습니다.** "978인가? 958" — 큐피스트 때와 같은 실수입니다.
- **결과 숫자(297MB)를 말하지 않았습니다.**
- "리턴을 안 해준다"는 **useEffect 정리(cleanup) 함수**를 말한 것입니다. 용어로 말하세요.

**다시 쓴 답변** `📁 내 경험`

**→ Organizer로 실사용자 Peak Memory P95를 보고, 958.5MB에서 297.4MB로 줄였습니다.**

```
Organizer(버전별)에서 튄 릴리스 확인 → 그 버전에서 바뀐 코드로 좁힘
  → Instruments로 같은 화면 반복 진입 → 메모리가 계단처럼 오르고 안 내려옴

### Q14. 체크리스트 위젯의 Shared Storage는 직접 구현했나요? 데이터 흐름을 그려 주세요 (36:27)

**실제 답변** — 여러 번 막힌 끝에 "Zustand 업데이트 → Shared 업데이트 → Firestore. 위젯에서 바뀌면 반대로 Shared → Zustand → Firestore."

**문제점** — 내용은 맞았는데 **2분 넘게 걸렸습니다.** 이력서에 있는 네 단계를 그대로 외워 두면 한 번에 그립니다.

**다시 쓴 답변** `📁 내 경험`

**→ 앱에서 바꾸든 위젯에서 바꾸든 기기 저장소를 거치고, 서버(Firestore) 반영은 앱이 맡습니다.**

```

위젯에서 변경: 위젯 체크 → Shared Storage 기록(항목별 수정 시각) → 앱 진입 시 Zustand와 병합 → Firestore 반영
```

**→ 충돌은 항목 단위 수정 시각으로 풀었습니다.** 앱과 위젯이 같은 항목을 동시에 고치면 더 늦게 고친 쪽을 살립니다.

**→ "위젯이 Firestore에 직접 쓰지 않은 이유는요?"** 위젯은 실행 시간이 짧고 네트워크가 보장되지 않습니다. 그래서 위젯은 기기 저장소에만 쓰고, 서버 반영은 앱이 맡게 나눴습니다.

### Q15. 멀티 디바이스(같은 계정의 여러 기기)도 지원했나요? iOS·Android에서 무엇이 필요하죠? (39:31) ❌

**실제 답변** — "시계(Wear OS)도 업데이트됐다." → "같은 계정으로 묶인 기기요" → "기억이 안 난다."

**문제점** — **답이 이력서에 있었습니다.** Shared Storage는 **한 기기 안**의 공유이고, **기기 사이**는 Firestore가 맡습니다. 이걸 나눠 말하면 됩니다.

**다시 쓴 답변** `📁 내 경험`

**→ 한 기기 안은 공유 저장소, 기기 사이는 Firestore로 맞췄습니다.**

```
A 기기 앱에서 체크 → Firestore에 저장 (위젯에서 체크했다면 A 앱을 열 때 저장)
  → B 기기 앱이 실시간 리스너(onSnapshot)로 받음
  → B 기기 공유 저장소에 기록 → B 위젯 갱신
```

**→ 충돌은 체크리스트 묶음 단위로, 수정 시각이 더 늦은 쪽이 이깁니다.** 그래서 두 기기에서 같은 묶음의 다른 항목을 거의 동시에 체크하면 **한쪽이 덮일 수 있습니다.** 막으려면 항목 단위로 저장해야 합니다. 삭제는 `deleted: true` 표시로 남겨 다른 기기에도 전했습니다.

**→ 멀티 디바이스에 필요한 것:** 같은 계정의 데이터를 모으는 **서버 동기화**(루티너리는 Firestore)와, 앱이 꺼진 기기를 깨우는 **푸시**입니다. iOS는 **조용한 푸시**(알림 없이 앱을 깨우는 푸시), Android는 **FCM data 메시지**를 씁니다. 서버가 없다면 iOS는 **iCloud(CloudKit)** 로 같은 Apple ID 기기끼리 맞출 수 있지만, Android에는 같은 역할의 실시간 기능이 없습니다.

**→ 한계:** 루티너리는 푸시로 깨우는 부분을 만들지 않아서, 앱이 꺼진 기기의 위젯은 **앱을 열 때** 바뀝니다. 푸시도 OS가 횟수를 제한해서 **보장은 안 됩니다.**

### Q19. Old Architecture와 New Architecture의 특징·장단점, JSI란? (48:04) ❌

**실제 답변** — "New Arch는 JSI(JavaScript Interface)를 쓴다. Old Arch는 타입 안정성이 떨어지고, New Arch는 Codegen으로 타입 안정성이 좋다. Old Arch는 네이티브 모듈… 타입 터보 모듈을 사용하는 걸로…"

**문제점**
- **TurboModule은 New Architecture 것입니다.** Old Arch에 붙였습니다.
- 면접관이 **"Old Arch부터 설명하면 자연스럽다"**, **"JSI가 나온 이유"** 로 두 번 힌트를 줬습니다. **Bridge의 문제**에서 시작하면 됐습니다.
- **루티너리를 New Arch로 올린 경험**이 있다고 해놓고, 그 경험을 못 꺼냈습니다.

**다시 쓴 답변** `🌐 개념 정리` + `📁 내 경험` — **Bridge의 문제 → 해결 순서로 외우세요.**

**→ Old Arch는 JS와 네이티브가 Bridge로 메시지를 주고받았고, New Arch는 JSI로 JS가 네이티브를 직접 부릅니다.**

```
Old: JS ─(JSON으로 바꿔 큐에 넣음, 비동기)→ Bridge → 네이티브
New: JS ─(JSI: C++ 객체를 직접 호출, 동기 가능)→ 네이티브
```

**→ Bridge의 문제 셋을 New Arch가 하나씩 풉니다.** 직렬화 비용 → JSI, 앱 시작 때 모듈 전부 초기화 → TurboModule(처음 쓸 때 로드), 비동기 레이아웃 → Fabric(동기 측정). Codegen은 TS 타입으로 연결 코드를 만들어 타입 불일치를 막습니다. `🌐 개념 정리`

**→ 실제로 겪은 것:** Release에서 ProGuard가 JNI·TurboModule 클래스를 지워 시작 4초 뒤 SIGABRT가 났고, keep 규칙으로 고쳤습니다([26번 Q6](./26_wrtn_interview.md)). **TurboModule을 처음부터 만든 적은 없습니다.** 한계: 동기 호출을 남용하면 JS 스레드를 막아서, 가능하면 비동기를 씁니다.

  → 고치고 같은 방법으로 재측정 → 그래도 안 되면 FlashList
```

**→ 고치는 순서:** 안정된 `keyExtractor` → 항목은 `React.memo`, `renderItem`은 고정된 함수로(인라인 금지) → 높이가 고정이면 `getItemLayout` → 항목 안 이미지는 표시 크기로. 측정 없이 `useMemo`부터 붙이지 않습니다. `🌐 개념 정리`

**→ 루티너리에서 FlashList로 바꾼 이유:** **[ 실제 화면과 증상 — 확인 필요 ]** 기억나지 않으면 "확인이 필요하다"고 말하고 위 순서로 답합니다.

### Q24. FlashList v1과 v2의 차이는? (59:10) ❌

**실제 답변** — "거기까지는 알아보지 못했다."

**다시 쓴 답변** `🌐 개념 정리`

**→ v1은 셀 재사용을 위해 크기 예측값이 필요했고, v2는 New Architecture의 동기 측정을 써서 그 값이 필요 없어졌습니다.**

```
v1: estimatedItemSize 필요 (틀리면 빈칸·점프), Old·New 둘 다 지원
v2: 그리기 전에 동기로 측정, JS로 다시 작성, New Architecture 전용
```

**→ 공통점은 "셀 재사용"입니다.** 나간 셀을 버리지 않고 새 데이터로 다시 씁니다. 그래서 셀 안 `useState` 값이 다른 항목에 남을 수 있어, 데이터가 바뀌면 초기화해야 합니다. `🌐 개념 정리`

**→ 채팅 앱과 연결:** v2는 과거 메시지를 위로 불러와도 보던 위치가 유지됩니다. 크랙 같은 대화 화면에 바로 쓰입니다.

### Q25. Reanimated 4의 CSS 애니메이션과 worklet으로 만든 애니메이션의 차이는? (59:24) —

**실제 답변** — 질문만 받고 시간이 끝났습니다. **2차에서 다시 나올 가능성이 큽니다.**

**다시 쓴 답변** `🌐 개념 정리` + `📁 내 경험`

**→ CSS 방식은 "상태가 바뀌면 이렇게 움직여라"를 선언하는 것이고, worklet 방식은 매 프레임 값을 UI 스레드에서 직접 계산하는 것입니다.**

```
CSS      : 펼침·색 변화·로딩 점처럼 정해진 움직임 (짧고 선언적)
worklet  : 드래그·스와이프처럼 손가락을 따라가는 움직임 (SharedValue + useAnimatedStyle)
```

**→ Reanimated 4에서 바뀐 것:** CSS 애니메이션·전환 문법이 들어왔고, New Architecture 전용이며, worklet 엔진이 `react-native-worklets`로 분리됐습니다. 움직임은 `transform`과 `opacity`만 바꾸는 게 가장 쌉니다. `🌐 개념 정리`

**→ 제가 겪은 주의점:** 화면이 사라져도 SharedValue 애니메이션이 계속 돌 수 있어 `cancelAnimation`으로 정리해야 합니다(Q2). **[ 루티너리가 Reanimated 3인지 4인지 확인 ]**

**→ ② "비개발 인원도 개발에 참여한다고 하셨는데, 그 코드는 어떤 검증을 거쳐 들어가나요?"** 하네스 경험과 바로 이어집니다.
