## 1. 소개 · 지원 동기

### Q1. 간단하게 자기소개 부탁드립니다 (18:59)

**실제 답변** — "4년 차 프론트엔드·RN 개발자. 첫 회사는 Electron·RN·React, 두 번째 메이크델타는 RN·React, 세 번째 루티너리는 RN과 Claude Code로 개발."

**문제점**
- **회사와 기술 이름만** 있고 **한 일과 숫자**가 없습니다.
- "Claude Code로 개발했다"는 도구를 썼다는 말일 뿐입니다. **하네스를 만들어 팀에 깔았다**는 게 강점입니다.
- 이 팀은 **성능**을 본다고 했는데, 첫 문장에 성능이 없습니다.

**다시 쓴 답변** `📁 내 경험`

**→ 실사용자 지표로 성능 문제를 찾아 고치는 4년 차 RN 개발자 이원교입니다.**

**→ 직전 루티너리(500만 사용자 습관 앱)에서 Peak Memory P95를 958MB에서 297MB로 줄였습니다.** 화면이 사라져도 정리 안 되던 애니메이션 값이 원인이었습니다.

**→ 플랫폼 경계도 직접 맡았습니다.** 홈 위젯, Wear OS, 앱이 꺼진 상태의 위치 알림을 Swift·Kotlin으로 만들었습니다.

**→ AI 에이전트가 안전하게 일하는 환경을 팀에 깔았습니다.** 편집한 파일만 자동 검사하고, 타입 에러가 있으면 작업이 안 끝나게 막는 하네스입니다.

**→ 회사 순서는 페이히어(POS) → 메이크델타(트레이딩) → 루티너리입니다.** 순서를 틀리면 이력서와 다르게 들립니다.

### Q5. 이직하려는 이유와 왜 뤼튼인지 (23:41)

**실제 답변** — "경영 악화로 퇴사. 뤼튼은 재밌는 회사 같다. 잼으로 영상 AI, 뤼튼으로 채팅 앱, 크랙으로 게임 AI 룰… 종합 엔터테인먼트 회사 같다."

**문제점**
- 퇴사 이유는 짧고 좋았습니다. **그대로 유지**하세요.
- **잼은 운영하지 않는 서비스**입니다(위험 발언 2번). 크랙도 "게임 AI"가 아니라 **AI 캐릭터 채팅**입니다.
- "재밌는 회사 같다"는 **내가 왜 맞는 사람인지**가 빠졌습니다.

**다시 쓴 답변** `📁 내 경험`

**→ 퇴사는 회사 사정이 어려워져서였습니다.** 한 문장으로 끝냅니다. ([23번](./23_ykplan_review.md) ②와 같은 문장)

**→ 뤼튼에 지원한 이유는, 제가 해온 일이 이 팀에서 가장 크게 쓰이기 때문입니다.** 크랙·캬라푸·OOC는 **사용자가 오래 켜 두고 대화하는 앱**입니다.

**→ 오래 켜 두는 앱에서 제일 먼저 무너지는 게 메모리와 렌더링입니다.** 저는 루티너리에서 **실사용자 지표로 메모리 문제를 찾아 고친 경험**이 있습니다.

**→ AI를 전 과정에 쓰는 팀이라는 점도 컸습니다.** 저는 에이전트를 쓰는 데서 그치지 않고 **팀이 같이 쓰는 규칙과 검증 장치를 만든** 경험이 있습니다.

**→ "우리 서비스 중 써 본 건 있나요?"** **[ 크랙을 실제로 써 봤는지 · 느낀 점 하나 ]** 써 보지 않았다면 2차 전에 **반드시 크랙을 30분 이상 써 보고**, 긴 대화에서 느려지는지 같은 **성능 관점 관찰 하나**를 준비하세요.

## 2. 성능 · 측정

### Q2. 이력서 첫 줄의 성능 개선 — 어떻게 측정하고 개선했나요? (20:06)

### Q11. OTA는 무엇을 썼고, 어떻게 구성했나요? (32:49~35:03)

**실제 답변** — "App Center가 없어진 뒤 오픈소스를 사용. S3와 CloudFront로, 서버가 없어서… 리와인드(롤백)까지." → "사용자가 S3에 직접 접근하나?" → 답이 흐려짐 → "스탠드얼론 서버 맞나요?" → "네. 루티너리는 백엔드가 없었다."

**문제점**
- **앱이 번들을 어떻게 찾아 받는지**를 설명하지 못해서 면접관이 세 번 되물었습니다.
- "서버 없음"과 "스탠드얼론 서버 맞음"이 **서로 부딪힙니다.**
- "백엔드가 없었다"는 사실이 아닙니다(Firebase + API 서버).

**다시 쓴 답변** `📁 내 경험`

**→ 오픈소스 CodePush 클라이언트는 그대로 두고, 업데이트 정보와 번들을 S3에 올려 CloudFront로 내려주는 방식이었습니다. 돌아가는 CodePush 서버는 없습니다.**

**→ 앱이 업데이트를 찾는 흐름은 이렇습니다.**

```
앱 시작
  → CloudFront의 "최신 배포 정보" 파일을 읽음 (S3가 원본)
  → 내 네이티브 버전에 맞는 새 번들이 있으면
  → CloudFront에서 번들 zip을 내려받음
  → 다음 실행 때 새 번들로 교체
```

**→ "사용자가 S3에 직접 접근하나요?"** 아닙니다. **S3는 원본 저장소이고, 사용자는 CloudFront(CDN)에서만** 받습니다. 받는 파일은 공개해도 되는 JS 번들입니다.

**→ 배포와 롤백은 GitHub Actions 버튼 하나로 했습니다.** 배포는 번들과 배포 정보를 S3에 올리는 것, 롤백은 **문제 번들을 비활성화**하는 것입니다.

**→ 만들다가 막은 구멍이 있습니다.** 배포 정보를 **CloudFront 캐시에서 읽으면** 오래된 캐시 때문에 기록이 비어 보일 수 있습니다. 그래서 **쓸 때는 항상 S3 원본에서 읽고, 기존 기록이 빠지면 쓰지 않게** 했습니다.

**→ "스탠드얼론 서버인가요?"** **아닙니다.** "서버 프로세스 없이 **정적 파일만으로** 동작하게 만든 구조"라고 정확히 말합니다.

**→ 루티너리 백엔드는?** 없던 게 아니라 **Firebase가 대부분, 꼭 필요한 기능만 별도 API 서버**였습니다([25번 Q2](./25_qpist_review.md)).

| **네이티브 코드** (라이브러리 · 권한 · 네이티브 모듈) | **Fastlane** → 앱 스토어 바이너리 | **개발자 맥에서 실행** (`yarn ios:archive:prd` 등 → `bundle exec fastlane <lane>`) |
| **JS만** | **CodePush** → S3 + CloudFront | **GitHub Actions** (`workflow_dispatch` — 버튼으로 실행) |

**⚠️ 네이티브 빌드는 GitHub Actions에서 돌지 않습니다.** 워크플로는 CodePush 배포·롤백 3개뿐입니다. "CI에서 빌드한다"고 말하면 틀립니다.

```
[iOS — Fastlane, 맥에서 실행]
lane 3개: firebase_stg (DEV) · firebase_prd (PROD) · archive_prd (스토어)

  ① 비밀값 로드: env/.env.secrets (dotenv)
  ② sync_version
      → 버전 이름: package.json의 version
      → 빌드 번호: git 커밋 수 + 1
      → 둘 다 ios/Config.xcconfig 에 기록 (VERSION · BUILD_NUMBER)
  ③ gym으로 .ipa 빌드
      → firebase_stg / firebase_prd: DEV·PROD scheme, development 내보내기, 자동 서명
      → archive_prd: PROD scheme, app-store 내보내기, 수동 서명
        (프로비저닝 프로파일 5개: 앱 · 위젯 · 워치 · 인텐트 · 알림 확장)
  ④ 업로드
      → firebase_stg / firebase_prd: Firebase App Distribution (testers 그룹)
      → archive_prd: App Store Connect API 키로 TestFlight 업로드
        (skip_submission — 심사 제출 안 함)
  ⑤ Slack 알림: 테스트 빌드는 QA 채널, TestFlight는 릴리스 채널

[Android — Fastlane, 맥에서 실행]
lane 3개: firebase_stg (dev 플레이버) · firebase_prd (prod 플레이버) · archive_prd (스토어)

  ① yarn android:clean 후 실행, 비밀값 로드
  ② ENVFILE로 환경 선택: env/.env.dev / env/.env.prod
  ③ gradle 빌드
      → firebase_stg / firebase_prd: assemble → APK
      → archive_prd: bundle → AAB
  ④ 버전
      → versionName: build.gradle이 package.json에서 읽음
      → versionCode: git 커밋 수 + 1062000 (archive_prd는 +1 해서 overrideVersionCode로 넘김)
  ⑤ 업로드
      → firebase_*: Firebase App Distribution
      → archive_prd: Google Play 내부 테스트 트랙, draft 상태
  ⑥ Slack 알림

[CodePush — GitHub Actions, 버튼으로 실행]
codepush-dev-deploy (staging) · codepush-prod-deploy (production) · codepush-rollback

  ① 입력: 플랫폼 · 바이너리 버전 · 강제 업데이트 여부 · 롤아웃 % · 제외할 에셋
  ② 의존성 설치 (Node 22 · yarn 캐시)
  ③ 새 번들 버전 계산: S3 원본의 배포 기록 JSON을 읽어 patch +1
  ④ npx code-push release → 번들과 배포 기록을 S3에 올림, CloudFront로 배포
  ⑤ 같은 번들로 소스맵 생성 → Sentry에 업로드
     (release 이름에 바이너리 버전 + CodePush 번들 버전을 같이 넣음)
  ⑥ Slack 알림 (성공·실패 모두 — if: always())

  롤백: 배포 기록에서 문제 버전을 enabled: false로 → 그 아래 활성 버전으로 돌아감
        (활성 버전이 없으면 스토어 바이너리 원래 번들로 돌아감)
```

**→ 핵심은 "테스트 트랙까지 자동, 출시는 사람"입니다.** TestFlight는 **심사 제출 없이**, Play는 **draft**로만 올립니다. 출시는 기획·QA 확인과 타이밍(이벤트, 주말)이 걸린 판단이라 남겼습니다.

**→ 버전은 원본이 하나입니다.** iOS와 Android가 **`package.json` 하나**를 읽고, 빌드 번호는 **git 커밋 수**에서 만들어서 사람이 올리다 겹치는 일이 없습니다. Android versionCode에는 커밋 수에 **1062000**을 더합니다. **[ 더한 이유 — 기존 스토어 versionCode보다 크게 맞추려던 값인지 확인 ]**

**→ JS만 바뀌면 스토어를 안 거칩니다.** CodePush 배포는 **바이너리 버전에 묶여서** 나갑니다. 네이티브가 다른 옛 앱에는 새 JS가 가지 않습니다.

**→ "왜 네이티브 빌드는 CI에 안 올렸나요?"** **[ 실제 이유 — 예: iOS 빌드에 macOS 러너 비용, 서명 인증서를 CI에 두는 부담, 배포 빈도가 낮아 로컬로 충분 ]**. 지금이라면 **macOS 러너 + 인증서 관리(match 등)** 로 옮기겠다고 답합니다.

**→ "Fastlane 내부는요?"** lane은 **작업 순서를 묶은 함수**입니다. 루티너리 lane은 `gym`(iOS 빌드) · `gradle`(Android 빌드) · `upload_to_testflight` · `upload_to_play_store` · `firebase_app_distribution` · `slack` **action**을 차례로 부릅니다. 버전 동기화는 `sync_version`이라는 **직접 만든 lane**입니다.

### Q13. CI/CD 인프라 구축의 성과 지표가 있나요? (36:01) ❌

**실제 답변** — "거기까지는 생각을 못 했다."

**다시 쓴 답변** `📁 내 경험`

**→ 빌드 시간을 줄인 게 아니라, 사람이 하던 배포 단계를 없앤 게 성과입니다.**

**→ 사람이 하던 일:** **[ 이전 배포 방식 — 예: 로컬에서 Xcode Archive → 수동 업로드, 빌드 번호 수동 수정 ]**

**→ 자동화 뒤:** 버튼 하나로 **iOS·Android 두 플랫폼 · DEV/PROD**가 나갑니다. 빌드 번호 충돌과 **버전 불일치가 없어졌습니다.**

**→ 숫자가 있다면:** 배포 한 번에 들던 시간 **[ 예: 1시간 → 버튼 1번 + 대기 n분 ]**, 배포 빈도 **[ 주 n회 ]**. **모르면 지어내지 말고** "시간을 잰 적은 없지만 수동 단계가 n개에서 0개가 됐다"고 말합니다.

**→ 부족했던 점도 말합니다.** **Fastlane lane은 성공 알림만 있고 실패 알림이 없었습니다**(CodePush 워크플로는 실패도 알림). 지금이라면 실패 알림과 **빌드 캐시**(CocoaPods·Gradle)부터 넣겠습니다.

## 6. 위젯 · 멀티 디바이스

### Q14. 체크리스트 위젯의 Shared Storage는 직접 구현했나요? 데이터 흐름을 그려 주세요 (36:27)

**실제 답변** — 여러 번 막힌 끝에 "Zustand 업데이트 → Shared 업데이트 → Firestore. 위젯에서 바뀌면 반대로 Shared → Zustand → Firestore."

**문제점** — 내용은 맞았는데 **2분 넘게 걸렸습니다.** 이력서에 있는 네 단계를 그대로 외워 두면 한 번에 그립니다.

**다시 쓴 답변** `📁 내 경험`

```
[앱에서 바꿀 때]
Zustand 스토어 변경
  → Shared Storage에 기록 (iOS App Group / Android DataStore)
  → 위젯 다시 그리기 요청 (iOS WidgetCenter / Android Glance update)
  → Firestore에 순서대로 반영

[위젯에서 바꿀 때]  (iOS AppIntents · Android Glance 액션)
위젯에서 체크
  → Shared Storage에 기록 (항목마다 수정 시각 포함)
  → 앱을 열 때 Shared Storage와 Zustand를 병합
  → Firestore에 순서대로 반영
```

**→ 충돌은 항목 단위 수정 시각으로 풀었습니다.** 앱과 위젯이 같은 항목을 동시에 고치면 **더 늦게 고친 쪽**을 살립니다.

**→ "위젯이 Firestore에 직접 쓰지 않은 이유는요?"** 위젯은 **실행 시간이 짧고 네트워크가 보장되지 않습니다.** 그래서 위젯은 기기 저장소에만 쓰고, 서버 반영은 **앱이 맡게** 나눴습니다.

### Q15. 멀티 디바이스(같은 계정의 여러 기기)도 지원했나요? iOS·Android에서 무엇이 필요하죠? (39:31) ❌

**실제 답변** — "시계(Wear OS)도 업데이트됐다." → "같은 계정으로 묶인 기기요" → "기억이 안 난다."

**문제점** — **답이 이력서에 있었습니다.** Shared Storage는 **한 기기 안**의 공유이고, **기기 사이**는 Firestore가 맡습니다. 이걸 나눠 말하면 됩니다.

**다시 쓴 답변** `📁 내 경험` + `🌐 개념 정리`

**→ 한 기기 안은 Shared Storage, 기기 사이는 Firestore가 원본이었습니다.**

**→ 같은 계정의 다른 기기는 Firestore를 통해 맞춰집니다.** 각 기기는 앱을 열 때 Firestore와 병합하고, **항목마다 수정 시각**으로 충돌을 풉니다. 이 규칙이 앱-위젯 충돌 해결과 **같은 로직**입니다.

**→ 워치는 별도 경로였습니다.** Wear OS는 **Wearable Data Layer(DataClient)** 로 폰 앱 데이터가 바뀌면 워치 UI가 갱신되게 했습니다.

**→ 남는 문제는 "앱을 안 연 기기의 위젯"입니다.** 위젯은 혼자 서버를 구독할 수 없어서, B 기기에서 체크해도 **A 기기 위젯은 A에서 앱을 열 때까지** 옛 값입니다. **[ 루티너리에서 이걸 어떻게 받아들였는지 ]**

**→ 이걸 풀려면 서버가 기기를 깨워야 합니다.** `🌐 개념 정리`
- **iOS** — 데이터가 바뀌면 **조용한 푸시(content-available)** 로 앱을 백그라운드에서 깨우고 → App Group 갱신 → `WidgetCenter.reloadTimelines`. 단, **시스템이 깨우는 횟수를 제한**해서 보장은 안 됩니다.
- **Android** — **FCM data 메시지** → WorkManager로 데이터 받기 → DataStore 갱신 → Glance `update()`.
- 둘 다 안 되면 위젯의 **정해진 갱신 주기**(iOS 타임라인 · Android updatePeriod)에 기댑니다.

### Q16. 메이크델타 인앱 구독 3단계 요금제 — 어떤 문제가 생기고, 어떻게 해결했나요? 라이브러리는? (41:21) ❌

**실제 답변** — 라이브러리 이름부터 막혀 "죄송합니다… 거기까지 제가…"로 넘어감.

**문제점** — 이력서 문장인데 **한 마디도 못 했습니다.** 결제는 이 회사에서도 **크랙 재화 결제**로 바로 이어지는 주제라 2차에서 다시 나올 가능성이 큽니다.

**다시 쓴 답변** `📁 내 경험` + `🌐 개념 정리`

**→ 라이브러리는 [ 메이크델타에서 쓴 것 — react-native-iap / RevenueCat 중 확인 ] 였고, 가장 어려운 건 "결제가 앱 밖에서 끝난다"는 점이었습니다.**

**→ 자주 생기는 문제 다섯 가지와 대응입니다.**

| 문제 | 왜 생기나 | 대응 |
|---|---|---|
| **결제는 됐는데 앱이 결과를 못 받음** | 결제창에서 앱을 끄거나 네트워크가 끊김 | 앱 시작 때 **끝나지 않은 거래를 다시 받아서** 처리 (`getAvailablePurchases` / 거래 리스너) |
| **처리를 안 끝낸 거래** | 지급 전에 앱이 죽음 | 서버 지급이 끝난 **뒤에만** `finishTransaction`. Android는 **3일 안에 확인(acknowledge)** 안 하면 **자동 환불** |
| **영수증 조작** | 앱이 "샀다"고 하는 걸 믿음 | 영수증 검증은 **서버**에서 |
| **기기 변경·재설치** | 앱은 이미 산 걸 모름 | **구매 복원** 버튼 |
| **등급 변경(3단계)** | 올릴 땐 즉시, 내릴 땐 다음 갱신일부터 적용 | 등급을 **같은 구독 그룹**에 넣고 스토어 규칙을 따름. 앱은 **서버가 알려준 현재 등급**만 믿음 |

**→ 환불·갱신은 앱이 모르는 사이에 일어납니다.** 그래서 **App Store Server Notifications / Google RTDN**으로 서버가 직접 받아야 합니다. `🌐 개념 정리`

**→ 루티너리에서 한 일도 붙입니다.** Adapty로 구독을 관리했고, **구매 직후 미리 유료 기능을 켜던 걸 빼서** 서버 동기화 결과로만 바뀌게 했습니다([26번 Q9](./26_wrtn_interview.md)).

**→ "재화(코인) 결제라면요?"** 구독과 달리 **같은 구매가 두 번 지급되면 안 됩니다.** 서버가 **거래 ID로 한 번만** 지급하고, 앱은 지급 확인 뒤에 finish합니다.

### Q17. Skia 차트와 차트 웹뷰가 이력서에 둘 다 있는데, 교체한 건가요, 공존한 건가요? (42:55~46:42) ❌

**먼저 할 일 — 실제 사실을 하나로 정하세요.** 아래 빈칸을 채우면 답이 정해집니다.

| 확인할 것 | 내 답 |
|---|---|
| 시간 순서 — Skia 주식 앱과 코인 차트 웹뷰 중 **무엇이 먼저**였나 | **[ ]** |

| 주식 앱이 나중에 그 웹뷰 차트로 **바꿨나** | **[ ]** |

**다시 쓴 답변 예시** `📁 내 경험` — 면접에서 말한 순서(Skia 먼저 → 웹뷰 나중)가 사실일 때

**→ 정리하면:** **한 앱 안에서 가장 부드러워야 하면 Skia, 여러 곳에서 같이 써야 하면 웹뷰.** 선택 기준을 이렇게 한 문장으로 말하세요.

**⚠️ 이력서 문장 점검** — 실제 사실이 "Skia가 느려서 웹뷰로 갔다"라면 이력서의 **"네이티브 렌더링 성능 확보를 위해"** 는 고쳐야 합니다. 다른 회사에 내기 전에 [20번](./20_resume_fix.md)처럼 수정 문구를 정하세요.

### Q18. Skia 성능이 왜 안 좋았을까요? 지금 경험으로 분석해 보면? (46:53) ❌

**실제 답변** — "당시엔 DOM(useRef)을 쓰는 방법을 도전해 보지 않았다. 그걸 했다면 더 좋았을 것."

**문제점** — Skia는 DOM이 아닙니다. **웹뷰 차트의 해법(useRef + Canvas)을 Skia 문제에 붙였습니다.**

**다시 쓴 답변** `🌐 개념 정리` + `📁 내 경험`

**→ Skia 자체가 느린 게 아니라, 새 값이 올 때마다 React 렌더를 거쳐 그림을 처음부터 다시 만든 게 원인이었을 가능성이 큽니다.**

**→ ① React 렌더를 거친 다시 그리기.** 시세가 올 때마다 **state → 컴포넌트 다시 렌더 → Skia 경로(Path) 재계산**이 JS 스레드에서 돌면, JS가 바쁠 때 프레임이 밀립니다. **[ 당시 코드가 state로 그렸는지 확인 ]**

**→ ② 그릴 필요 없는 것까지 다시 그림.** 캔들 수백 개 중 **바뀌는 건 마지막 하나**인데 전체 경로를 다시 만들었을 수 있습니다.

**→ 지금이라면 이렇게 고칩니다.**
- 값은 **Reanimated SharedValue**에 넣고, 경로 계산은 `useDerivedValue`로 **UI 스레드**에서 합니다. React 렌더를 안 거칩니다.
- **지난 캔들은 한 번 그려서 고정**(Picture로 기록)하고, **마지막 캔들만** 다시 그립니다.
- 줌·패닝은 **Gesture Handler → SharedValue** 로 바로 이어서 JS를 안 거치게 합니다.

**→ 원칙은 웹뷰 차트와 같습니다.** **자주 바뀌는 값을 React state에 넣지 않는다.** 이 문장으로 Q8·Q17·Q18을 하나로 묶으세요.

### Q19. Old Architecture와 New Architecture의 특징·장단점, JSI란? (48:04) ❌

**실제 답변** — "New Arch는 JSI(JavaScript Interface)를 쓴다. Old Arch는 타입 안정성이 떨어지고, New Arch는 Codegen으로 타입 안정성이 좋다. Old Arch는 네이티브 모듈… 타입 터보 모듈을 사용하는 걸로…"

**문제점**
- **TurboModule은 New Architecture 것입니다.** Old Arch에 붙였습니다.
- 면접관이 **"Old Arch부터 설명하면 자연스럽다"**, **"JSI가 나온 이유"** 로 두 번 힌트를 줬습니다. **Bridge의 문제**에서 시작하면 됐습니다.
- **루티너리를 New Arch로 올린 경험**이 있다고 해놓고, 그 경험을 못 꺼냈습니다.

**다시 쓴 답변** `🌐 개념 정리` + `📁 내 경험` — **Bridge의 문제 → 해결 순서로 외우세요.**

**→ Old Arch는 JS와 네이티브가 Bridge로 메시지를 주고받았고, New Arch는 JSI로 JS가 네이티브를 직접 부릅니다.**

**→ Old Arch(Bridge)의 문제 세 가지.**
1. **직렬화 비용** — 모든 호출을 **JSON으로 바꿔서** 큐에 넣고, 반대편에서 다시 풀었습니다.
2. **비동기만 가능** — 레이아웃 크기를 **바로 재서 쓰는** 일이 안 됐습니다. 화면이 한 프레임 늦게 맞춰집니다.
3. **시작 비용** — 네이티브 모듈을 **앱 시작 때 전부** 초기화했습니다.

**→ New Arch는 이걸 하나씩 풉니다.**

| 구성 | 하는 일 | 푸는 문제 |
|---|---|---|
| **JSI** | JS가 C++ 객체를 **직접 들고 호출**. JSON 변환 없음, **동기 호출 가능** | 직렬화 · 비동기 |
| **TurboModule** | 네이티브 모듈을 **처음 쓸 때 로드**(지연 로딩) | 시작 비용 |
| **Codegen** | TS 타입 정의로 JS-네이티브 연결 코드를 **생성** | 타입 불일치 |
| **Fabric** | C++ 렌더러. **동기 레이아웃 측정**, React 18 **동시성 기능** 지원 | 비동기 레이아웃 |
| **Bridgeless** | Bridge 자체를 없앰 (RN 0.74부터 기본) | — |

**→ 단점도 말합니다.** 라이브러리가 New Arch를 지원해야 하고, 동기 호출을 **남용하면 JS 스레드를 막습니다.**

**→ 실제로 겪은 차이 두 가지.** `📁 내 경험`
- Release에서 ProGuard가 **JNI·TurboModule·Fabric 클래스를 지워** 앱 시작 4초 후 SIGABRT — keep 규칙으로 해결 ([26번 Q6](./26_wrtn_interview.md))
- 알림 `id`에 `undefined`를 넘기면 **JSI 호출이 멈춤** — 타입 검사가 느슨하던 Bridge 때는 안 보이던 문제 ([26번 Q12](./26_wrtn_interview.md))

**→ "TurboModule을 직접 만들어 봤나요?"** **Codegen 스펙부터 직접 만든 적은 없습니다.** New Arch 앱의 빌드·크래시 문제를 고친 경험이라고 정확히 말합니다.

### Q21. 외부 URL의 아주 큰 이미지(웹툰처럼 긴 이미지)를 Android에서 OOM 없이 그리려면? (51:40) △

**실제 답변** — "이미지를 잘라서 렌더링하는 방법, 큰 데이터를 쪼개서 렌더링하는 방법."

**문제점** — **방향은 맞습니다.** 다만 **왜 OOM이 나는지**와 **어디서 자르는지**가 없었습니다. 면접관은 정답보다 **접근 순서**를 보고 싶다고 했습니다.

**다시 쓴 답변** `🌐 개념 정리`

**→ 원본을 통째로 메모리에 올리지 않는 게 핵심입니다. 크기를 먼저 읽고, 화면 크기만큼만, 보이는 부분만 디코딩합니다.**

**→ 왜 터지나.** 비트맵 메모리는 **가로 × 세로 × 4바이트**입니다. 1,080 × 30,000 웹툰 한 장이면 **약 130MB**입니다. 게다가 GPU가 한 번에 그릴 수 있는 텍스처 크기에 **상한**(기기마다 보통 4,096~16,384px)이 있어서 너무 길면 안 그려지기도 합니다.

**→ ① 크기만 먼저 읽습니다.** `BitmapFactory.Options.inJustDecodeBounds = true`로 **픽셀은 안 읽고** 가로·세로만 압니다.

**→ ② 화면 크기에 맞춰 줄여서 디코딩합니다.** 화면 폭이 1,080px이면 그보다 큰 원본은 `inSampleSize`로 **2배, 4배 줄여서** 읽습니다. Glide·Fresco·Coil 같은 라이브러리가 이걸 자동으로 합니다.

**→ ③ 긴 이미지는 세로로 잘라 보이는 조각만 디코딩합니다.** `BitmapRegionDecoder`로 **필요한 영역만** 읽고, 조각들을 **가상화 리스트**(FlashList)에 넣어서 **화면 밖 조각은 메모리에서 내립니다.**

**→ ④ 서버를 거칠 수 있다면 가장 쉽습니다.** 이미지 프록시·CDN에서 **리사이즈·분할**해서 내려줍니다. 이번 조건은 "외부 URL을 바로 쓴다"라서 앱에서 해야 합니다.

**→ RN에서는** `expo-image`나 `react-native-fast-image`가 디코딩 크기를 **표시 크기에 맞춰** 줄여 줍니다. 그래도 아주 긴 이미지는 ③처럼 **조각 단위 네이티브 처리**가 필요합니다. **[ 실제로 써 본 이미지 라이브러리 ]**

**→ 마지막에 측정으로 닫습니다.** 고치기 전후 **Memory Profiler의 Native Heap**을 비교합니다 — Q4와 같은 방법입니다.

### Q22. JSC 대신 Hermes를 기본 엔진으로 만든 이유와, 그 대가는? (54:32) ❌

**실제 답변** — 질문을 다시 듣고 "빌드하는 데 시간이 걸린다… TurboModule과 연관… 헷갈린다."

**다시 쓴 답변** `🌐 개념 정리`

**→ 모바일 앱의 시작 속도와 메모리를 위해, 빌드할 때 미리 바이트코드로 바꿔 두는 엔진을 만든 겁니다.**

**→ 장점 세 가지.**
1. **시작이 빠릅니다.** JSC는 앱을 켤 때 JS **소스를 읽고 파싱**합니다. Hermes는 **빌드 때 바이트코드로 미리 컴파일**(AOT)해서 앱 시작 때 그 과정이 없습니다. **TTI(첫 화면에서 조작 가능까지 시간)** 가 줄어듭니다.
2. **메모리가 적습니다.** 바이트코드를 **필요한 부분만 메모리에 올리고**(mmap), 모바일에 맞춘 **GC(Hades)** 가 멈춤 시간을 짧게 합니다.
3. **앱 크기·일관성.** iOS·Android가 **같은 엔진**을 씁니다. JSC는 Android에서 앱에 엔진을 **따로 넣어야** 했습니다.

**→ 포기한 것.**
- **JIT가 없습니다.** 오래 도는 **계산 위주 코드의 최고 속도**는 JIT가 있는 엔진보다 느릴 수 있습니다. 다만 iOS는 앱 안에서 JSC도 JIT를 못 써서 **차이가 크지 않습니다.**
- 초기에는 **Proxy · Intl 같은 기능 지원이 늦었습니다**(지금은 대부분 지원).
- 빌드에 **컴파일 단계가 하나 더** 생깁니다.

**→ 정리 문장:** **"모바일은 최고 속도보다 시작 속도와 메모리가 중요해서, 실행 때 할 일을 빌드 때로 옮긴 엔진이 Hermes입니다."**

**→ "TurboModule과 관계는요?"** **엔진과 아키텍처는 별개입니다.** JSI는 엔진 위에 놓인 인터페이스라 **JSC 위에서도 동작**합니다. 면접에서 둘을 섞으면 안 됩니다.

### Q23. FlatList의 특징과 성능 이슈가 생기는 이유, 찾는 방법, 최적화 (56:57) ❌

**실제 답변** — "가상화 모델이라 100개 중 10개만 렌더링" → (성능 이슈 원인 없음) → "FlashList로 바꿨다. 무슨 문제였는지는 기억이 안 난다" → "useMemo… 여러 방법을 썼는데 기억이 안 난다."

**문제점** — 면접관이 **"명칭이 기억 안 나도 이런 기능이라고 말해 달라"** 고까지 했습니다. [08번 Q6](./08_tech_react_native.md)에 답이 있습니다.

**다시 쓴 답변** `🌐 개념 정리` + `📁 내 경험`

**→ FlatList는 보이는 영역 근처만 그리는 가상화 리스트인데, 그 계산과 렌더가 JS 스레드에서 돌아서 JS가 바쁘면 빈 화면이 보입니다.**

**→ 성능 이슈가 생기는 이유.**
1. **JS 스레드 의존** — 스크롤은 UI 스레드에서 도는데 **새 항목을 그리는 건 JS**라, 빠르게 넘기면 **빈칸(blank)** 이 보입니다.
2. **항목 다시 렌더** — 부모가 바뀌면 **보이는 항목이 전부** 다시 그려집니다. `renderItem`을 인라인 함수로 넘기면 더 심합니다.
3. **높이 측정** — 높이를 모르면 **그려 보고 재야** 합니다.
4. **화면 밖 항목은 지우고 새로 만듦** — 재사용하지 않아서 생성 비용과 메모리가 듭니다.

**→ 찾는 방법.** **Perf Monitor**로 JS FPS와 UI FPS를 따로 보고(JS만 떨어지면 렌더 문제), **React DevTools Profiler**로 어떤 항목이 왜 다시 그려지는지 봅니다. Release 빌드에서 **Flashlight**로 점수를 재기도 합니다.

**→ 최적화 순서.**
1. `keyExtractor`로 **안정된 key**
2. 항목 컴포넌트를 **`React.memo`**, `renderItem`은 **`useCallback`**
3. 높이가 고정이면 **`getItemLayout`** — 측정을 건너뜁니다
4. `initialNumToRender` · `maxToRenderPerBatch` · `windowSize` 조정 — **재보고** 바꿉니다
5. 항목 안 이미지는 **표시 크기로 줄여서**
6. 그래도 안 되면 **FlashList**

**→ 루티너리에서 FlashList로 바꾼 이유:** **[ 실제 화면과 증상 — 확인 필요 ]** 기억나지 않으면 "어떤 화면이었는지는 확인이 필요하다"고 말하고 위의 일반 순서로 답합니다.

### Q24. FlashList v1과 v2의 차이는? (59:10) ❌

**실제 답변** — "거기까지는 알아보지 못했다."

**다시 쓴 답변** `🌐 개념 정리`

**→ v1은 셀 재사용을 위해 크기 예측값이 필요했고, v2는 New Architecture의 동기 측정을 써서 그 예측값이 필요 없어졌습니다.**

| | v1 | v2 (2025) |
|---|---|---|
| 아키텍처 | Old·New 모두 | **New Architecture 전용** |
| 크기 예측 | **`estimatedItemSize` 필요** — 틀리면 빈칸·점프 | **필요 없음** — 그리기 전에 **동기로 측정** |
| 구현 | 네이티브 코드 일부 포함 | **JS만으로** 다시 작성 |
| 그리드·벽돌형 | 벽돌형은 별도 컴포넌트 | `masonry` 옵션으로 통합 |
| 채팅 같은 역방향 목록 | 위치 유지가 까다로움 | **위로 항목이 추가돼도 보던 위치 유지**(`maintainVisibleContentPosition`)가 기본 |

**→ 공통점은 "셀 재사용"입니다.** 화면 밖으로 나간 셀을 버리지 않고 **새 데이터로 다시 씁니다.** FlatList와 가장 큰 차이입니다.

**→ 재사용 때문에 조심할 점:** 셀 안에 `useState`로 들고 있던 값이 **다른 항목에 남을 수 있습니다.** 항목 데이터가 바뀌면 상태를 초기화해야 합니다.

**→ 채팅 앱과 연결:** 과거 메시지를 위로 불러올 때 **스크롤이 튀지 않는 것**이 v2의 이점입니다. 크랙 같은 대화 화면에 바로 쓰입니다.

### Q25. Reanimated 4의 CSS 애니메이션과 worklet으로 만든 애니메이션의 차이는? (59:24) —

**→ 언제 무엇을 쓰나.**

| | CSS 애니메이션·전환 | worklet (SharedValue · useAnimatedStyle) |
|---|---|---|
| 쓰는 곳 | 상태 변화에 따른 **정해진 움직임** — 펼침, 색 바뀜, 로딩 점 | **손가락을 따라가는** 움직임 — 드래그, 스와이프, 스크롤 연동 |
| 코드 | 짧고 선언적 | 길지만 **매 프레임 제어** 가능 |
| 실행 | 둘 다 UI 스레드 | 둘 다 UI 스레드 |

**→ 채팅 앱에 대입하면** 타이핑 중 점 세 개, 메시지 등장 효과는 **CSS**, 메시지 스와이프 답장·길게 눌러 메뉴는 **worklet + Gesture Handler**입니다.

**→ worklet 쪽 주의점은 제가 겪은 것입니다.** 화면이 사라져도 **SharedValue 애니메이션이 계속 돌 수** 있어서 언마운트 때 `cancelAnimation`으로 정리해야 합니다. 루티너리 메모리 누수 원인이 이것이었습니다(Q2). worklet 안에서 JS 함수를 부를 땐 `runOnJS`(4에서는 `scheduleOnRN`)로 넘깁니다. **[ 루티너리가 Reanimated 3인지 4인지 확인 ]**

## 9. 역질문 (1:00:13)

**실제 질문**
1. "AI를 어떻게 활용하시나요?" → **좋은 질문이었습니다.** 리뷰·기획·개발·QA 전반, 비개발 인원도 개발 참여라는 답을 들었습니다.
2. "모바일 개발자와 프론트엔드의 차이는?" → 질문 앞에 **페이히어 경험을 길게 설명**해서 질문이 흐려졌습니다.

**문제점**
- 두 번째 질문은 **한 문장**이면 충분했습니다.
- 면접관이 **"오래 켜도 발열·버벅임·메모리 누수가 없어야 한다"** 고 했는데, 그 말에 **꼬리 질문을 붙일 기회**를 놓쳤습니다.

**다시 쓴 역질문** — 오늘 들은 정보로 만드세요. **2개만** 고릅니다.

**→ ① "오래 켜 둘 때의 발열·메모리를 지금은 어떤 지표로 보고 계신가요?"** 면접관이 강조한 바로 그 부분이고, **측정을 중시하는 사람**이라는 걸 보여줍니다.

**→ ② "비개발 인원도 개발에 참여한다고 하셨는데, 그 코드는 어떤 검증을 거쳐 들어가나요?"** 하네스 경험과 바로 이어집니다.

**→ ③ "크랙·캬라푸·OOC는 코드베이스를 얼마나 공유하나요?"** 모노레포 경험이 없는 걸 **배우려는 질문**으로 바꿉니다.

**→ 연봉·복지는 이 자리에서 묻지 않습니다.**
