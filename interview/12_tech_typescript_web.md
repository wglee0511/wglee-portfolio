## TypeScript

### Q1. any와 unknown의 차이는?

**답변** `🌐 개념 정리`
> **→ `any`는 검사를 아예 끄는 것이고, `unknown`은 검사를 나중으로 미루는 것입니다.**
>
> **→ `any`부터는 타입이 있으나 마나입니다.** 그 값을 어떻게 쓰든 컴파일러가 아무 말도 안 해서 **거기서부터는 타입이 있으나 마나가 됩니다.**
>
> **→ `unknown`은 확인 전엔 아무것도 못 하게 막습니다.** **이게 뭔지 확인하기 전에는** 쓸 수 없습니다.
>
> **→ 그래서 외부 값은 `unknown`으로 받습니다.** **API 응답, JSON.parse 결과**는 `unknown`으로 받고, **확인해서 타입을 확정한 다음에** 쓰는 게 맞습니다.

**30초 버전** — "any는 검사를 끄고, unknown은 확인할 때까지 아무것도 못 하게 막습니다. 그래서 외부 값은 unknown으로 받고 좁힌 뒤에 씁니다."

**꼬리 질문 대비**

**→ "그럼 any는 언제 쓰나요?"** 마이그레이션 중간 단계처럼 **임시로 통과시켜야 할 때**만 쓰고, 대신 **주석이나 TODO**를 남깁니다. 영구적으로 남기면 그 지점이 나중에 **런타임 에러의 진원지**가 됩니다.

### Q2. 타입과 인터페이스는 어떻게 나눠 쓰나요?

**답변** `🌐 개념 정리`
> **→ 선언을 합치거나 확장할 땐 interface, 타입을 계산할 땐 type입니다.**
>
> **→ interface를 쓰는 경우입니다.** **같은 이름으로 여러 번 선언해서 합쳐야 하거나**, **라이브러리가 만든 타입에 뭘 덧붙일 때**입니다.
>
> **→ type을 쓰는 경우입니다.** **"A 아니면 B", "조건에 따라 다른 타입", "기존 타입을 틀 삼아 새로 만들기"** 같은 계산이 필요할 때입니다.
>
> **→ 실무에서는 팀 컨벤션이 더 중요합니다.** **둘 다 되는 경우가 대부분**이라서요.

**30초 버전** — "선언을 합치거나 라이브러리 타입을 확장할 땐 interface, 유니온·조건부·매핑처럼 타입을 계산할 땐 type입니다. 대부분은 둘 다 돼서 팀 컨벤션을 따릅니다."

**꼬리 질문 대비**

**→ "선언 합치기는 실제로 언제 쓰나요?"** 라이브러리의 전역 타입(예: `Window`나 모듈 타입)에 **우리 프로젝트용 필드를 덧붙일 때**입니다.

### Q3. 제네릭은 왜 필요한가요?

**답변** `🌐 개념 정리`
> **→ 넣은 것과 나온 것 사이의 관계를 남기기 위해서입니다.**
>
> **→ `any`는 그 관계를 끊습니다.** **뭘 넣었든 나올 때는 `any`가 됩니다.**
>
> **→ 제네릭은 그 연결을 타입으로 적습니다.** **"넣은 타입이 그대로 나온다"는 연결 자체**를 타입으로 적어둘 수 있습니다.
>
> **→ `extends`로 최소 조건을 겁니다.** "적어도 이런 건 갖고 있어야 한다"고 걸면, **안에서 그 속성을 마음 놓고** 쓸 수 있습니다.

**30초 버전** — "입력과 출력의 관계를 타입으로 남기려고 씁니다. any는 그 연결이 끊기고, extends로 최소 조건을 걸면 안에서 속성도 안전하게 씁니다."

**꼬리 질문 대비**

**→ "제네릭을 과하게 쓰면요?"** 타입 인자가 **한 번만 쓰이면** 관계를 표현하는 게 없으니 **그냥 구체 타입**이 낫습니다. 읽기만 어려워집니다.

### Q4. 타입 좁히기(narrowing)는 어떻게 하나요?

**답변** `🌐 개념 정리`
> **→ "이 값이 여러 타입 중 어느 쪽인지" 확정해가는 것입니다.**
>
> **→ 기본 도구는 네 가지입니다.** **`typeof` · `in` · `instanceof` · 값 자체를 비교**하는 것입니다.
>
> **→ 직접 만든 검사는 타입 가드 함수로 만듭니다.** **`x is T`** — 이 검사를 통과하면 이 타입이라고 알려주는 함수 — 입니다.
>
> **→ 유니온에는 표시용 속성(discriminant)이 가장 안전합니다.** `{ status: 'success', data } | { status: 'error', message }` 처럼요.
>
> **→ 그러면 자동으로 좁혀지고 빠진 케이스도 잡힙니다.** `status`만 확인해도 나머지가 좁혀지고, **케이스를 빠뜨리면 컴파일 에러가 납니다.**

**30초 버전** — "typeof·in·instanceof·값 비교가 기본이고, 직접 만든 검사는 `x is T` 타입 가드로 씁니다. 유니온은 status 같은 표시용 속성을 두면 자동으로 좁혀지고 빠진 케이스도 잡힙니다."

**꼬리 질문 대비**

**→ "케이스를 빠뜨리면 어떻게 컴파일 에러가 나나요?"** switch 끝의 default에서 값을 **`never` 타입 변수에 넣으면**, 처리 안 한 케이스가 있을 때 **그 할당이 에러**가 납니다.

### Q5. 레거시 코드베이스에 타입 검증을 어떻게 도입하나요?

**▶ 내 경험 (이 질문은 하네스 이야기로 답하세요 — 가장 강한 카드입니다)** `📁 내 경험`
> **→ "이번에 고친 파일만" 검사하는 방식으로 도입했습니다.** 루티너리에 들어갔을 때 **타입 에러가 이미 수백 개 쌓여 있어서 전체 검증을 켤 수 없는 상태**였습니다.
>
> **→ 전체 수정은 불가능하고, 두면 새 코드까지 방치됩니다.** 그대로 두면 **새로 짜는 코드까지 같이 방치**됩니다.
>
> **→ 구조는 편집 때 정리, 끝날 때 차단입니다.** 파일을 고치면 **ESLint가 알아서 정리**하고, 작업을 끝낼 때 **타입 검사를 통과 못 하면 거기서 막습니다.**
>
> **→ 예전 에러는 두고 새 코드에만 조건을 겁니다.** **예전 에러는 그대로 두되, 새로 쓰는 코드에만 통과 조건을 거는 것**이죠.
>
> **→ 핵심은 막는 범위를 본인이 건드린 파일로만 한정한 것입니다.** **남이 만든 에러로 내가 막히면 바로 신뢰를 잃고 아무도 안 쓰게 됩니다.**

**30초 버전** — "레거시 타입 에러가 쌓여 전체 검증을 못 켜는 상태라, 이번에 고친 파일에만 품질 게이트를 걸었습니다. 편집 때 ESLint 자동 수정, 작업 끝날 때 타입 검사로 막되, 남이 만든 에러로는 안 막히게 범위를 한정한 게 핵심입니다."

**꼬리 질문 대비**

**→ "팀에서 실제로 썼나요?"** 온보딩 문서를 쓰고 **PR 리뷰를 거쳐 도입**했고, 이후 **다른 팀원들이 규칙을 추가하며 같이 운영**했다고 답합니다.

**→ "그럼 예전 에러는 영영 안 고치나요?"** 파일을 건드리는 순간 그 파일이 검사 대상이 되니, **고치는 김에 조금씩 줄어드는 구조**라고 설명합니다.

**포인트** — 기술이 아니라 **"조직에서 굴러가게 만드는 설계"** 를 보여주는 답변입니다.

### Q6. 타입이 있는데도 런타임 에러가 나는 경우는?

**답변** `🌐 개념 정리`
> **→ 밖에서 들어오는 값을 안 확인했을 때입니다.**
>
> **→ TypeScript는 실행할 때 사라집니다.** 빌드할 때만 있어서, API 응답에 `User` 타입을 붙여놔도 **실제로 그렇게 생겼는지는 아무도 확인해주지 않습니다.** 그냥 그럴 거라고 적어둔 것뿐입니다.
>
> **→ 그래서 타입 검사는 통과하는데 앱은 터집니다.** **서버가 필드 이름을 바꾸면** 실행 중에 터집니다.
>
> **→ 외부 값은 실행 중에도 확인합니다.** **zod 같은 걸로 실제 모양이 맞는지 확인**하고, **그 결과에서 타입을 뽑는 게** 안전합니다.

**30초 버전** — "타입은 실행 때 사라지니까, API 응답처럼 외부에서 온 값을 확인 안 하면 터집니다. 그래서 zod 같은 걸로 실행 중에 모양을 검사하고 거기서 타입을 뽑습니다."

**꼬리 질문 대비**

**→ "`as`로 단언하는 건요?"** `as`는 **"내가 맞다고 보증한다"는 선언일 뿐 검사가 아닙니다.** 외부 값에 쓰면 **같은 문제가 그대로** 남습니다.

### Q7. 이벤트 루프를 설명해 주세요.

**답변** `🌐 개념 정리`
> **→ JS는 한 번에 한 가지 일만 해서, 지금 하던 게 끝나야 다음 일을 잡습니다.**
>
> **→ 끝난 비동기 콜백은 대기줄에서 꺼내 실행합니다.** 콜백이 대기줄에 서고, 이벤트 루프가 **할 일이 없어진 순간** 그걸 꺼냅니다.
>
> **→ 중요한 건 대기줄이 두 개라는 점입니다.** **Promise 같은 마이크로태스크가 setTimeout 같은 매크로태스크보다 먼저** 처리됩니다.
>
> **→ 번갈아가지 않습니다.** **마이크로태스크 줄이 완전히 빌 때까지 전부** 처리하고 나서 다음 매크로태스크로 갑니다.

**30초 버전** — "JS는 하나씩 처리하고, 끝난 비동기 콜백은 대기줄에서 꺼내 실행합니다. Promise 같은 마이크로태스크 줄이 완전히 빈 다음에야 setTimeout 같은 매크로태스크로 넘어갑니다."

**꼬리 질문 대비**

**→ "그게 실무에서 왜 중요한가요?"** 마이크로태스크 안에서 Promise를 계속 만들면 그 줄이 안 비어서 **화면 그릴 차례가 아예 안 옵니다.** RN에서는 여기에 **JS가 막히면 화면 그리는 쪽은 멀쩡해도 새 내용이 안 올라온다**는 게 겹칩니다. 그래서 **무거운 계산은 조각으로 쪼개거나**, **네이티브나 워크렛** — 화면 그리는 쪽에서 도는 코드 — 으로 내립니다.

### Q8. 클로저란 무엇이고, 왜 문제가 되나요?

**답변** `🌐 개념 정리`
> **→ 함수가 만들어질 때 주변에 있던 변수들을 계속 붙들고 다니는 것입니다.**
>
> **→ 함수가 살아 있으면 변수도 안 지워집니다.** 유용하지만, **그 함수가 어딘가에 살아 있으면 붙들고 있는 변수도 같이 남습니다.**
>
> **→ 그래서 정리 안 한 콜백은 누수가 됩니다.** 이벤트 리스너나 타이머 콜백을 정리 안 하면, **그 콜백이 잡고 있던 큰 객체까지 통째로** 메모리에 남습니다.
>
> **→ React의 stale closure는 반대 방향 문제입니다.** **옛날 값을 계속 붙들고 있어서** 이펙트 안에서는 첫 렌더 때의 값만 보입니다.

**▶ 내 경험** — 클린업 누락으로 인한 실제 누수 사례(Reanimated SharedValue)로 연결하세요. (→ 07번 Q5)

**30초 버전** — "함수가 만들어질 때 주변 변수를 붙들고 다니는 겁니다. 함수가 살아 있으면 그 변수도 안 지워져서 누수가 되고, React에선 옛날 값을 붙드는 stale closure로 나타납니다."

**꼬리 질문 대비**

**→ "실제로 겪은 누수가 있나요?"** 루티너리에서 **SharedValue 정리 누락으로 네이티브 메모리가 쌓이던 문제**를 cleanup 훅으로 잡아, **Native Heap Total Allocations를 101.9MB → 31.2MB**로 줄였다고 답합니다.

### Q9. HTTP 캐시는 어떻게 동작하나요?

**답변** `🌐 개념 정리`
> **→ `Cache-Control`이 기본입니다.** **`max-age`로 서버에 다시 안 물어보고 그냥 써도 되는 시간**을 정합니다.
>
> **→ 시간이 지나면 최신인지만 물어봅니다.** **`ETag`나 `Last-Modified`** 를 같이 보내서 **"내가 가진 게 아직 최신인가"만** 확인합니다.
>
> **→ 안 바뀌었으면 304입니다.** 서버가 **304만 돌려주고 내용은 안 보내니까** 그대로 쓰면 됩니다.
>
> **→ 정적 파일은 길게, HTML은 짧게 둡니다.** 이미지나 JS 파일처럼 안 바뀌는 건 **파일명에 해시를 붙이고 캐시를 길게**, HTML은 **짧게 두고 매번 확인**하는 조합이 일반적입니다.

**30초 버전** — "max-age 동안은 묻지 않고 쓰고, 지나면 ETag로 최신인지만 물어서 안 바뀌었으면 304를 받습니다. 정적 파일은 해시 파일명에 긴 캐시, HTML은 짧게 둡니다."

**꼬리 질문 대비**

**→ "`no-cache`와 `no-store`의 차이는?"** `no-cache`는 **저장은 하되 쓸 때마다 서버에 확인**, `no-store`는 **아예 저장하지 않는 것**입니다.

**포인트** — React Query의 staleTime 설명과 **구조가 같다**고 연결하면 이해도가 드러납니다.

### Q10. CORS는 왜 있고, 어떻게 푸나요?

**답변** `🌐 개념 정리`
> **→ 브라우저가 다른 주소에서 온 응답을 스크립트한테 안 넘겨주는 것이 기본 정책입니다.** 아무 사이트나 남의 서버 데이터를 내 페이지에서 읽어가면 안 되니까요.
>
> **→ 서버가 허용해야 넘겨줍니다.** **`Access-Control-Allow-Origin`** 같은 걸로 **"이 주소는 읽어도 된다"고 밝혀야** 합니다.
>
> **→ 요청이 안 나간 게 아니라 응답을 못 읽는 것입니다.** **서버까지는 갔을 수 있습니다.**
>
> **→ 그래서 서버 설정 문제입니다.** **클라이언트에서 푸는 문제가 아닙니다.**
>
> **→ RN에는 CORS가 적용되지 않습니다.** 브라우저가 아니라서요. 이것 때문에 **웹에서만 막히는 상황**이 자주 생깁니다.

**30초 버전** — "브라우저가 다른 출처의 응답을 스크립트에 안 넘겨주는 정책이고, 서버가 허용 헤더로 밝혀야 풀립니다. 요청은 갔는데 응답을 못 읽는 거라 서버 설정 문제이고, RN에는 적용되지 않습니다."

**꼬리 질문 대비**

**→ "preflight는 뭔가요?"** 커스텀 헤더나 PUT·DELETE 같은 요청 전에 브라우저가 **OPTIONS로 "이 요청 보내도 되냐"를 먼저 묻는 것**입니다. **서버가 이걸 허용해야** 본 요청이 나갑니다.

> **→ 진짜 효과는 실제 사용자 쪽에서 보입니다.** **여러 기기와 네트워크가 섞인** 환경에서 봐야 알 수 있어서요.

**30초 버전** — "LCP·INP·CLS를 보는데, 로컬 측정만으론 부족하다고 봅니다. 루티너리에서도 로컬 n=10 중앙값으로 확인한 뒤, 실제 사용자의 시작 단계별 시간을 Amplitude로 보내는 telemetry를 따로 만들었습니다."

### Q13. Canvas로 직접 렌더링한 이유는?

**▶ 내 경험 (차별화되는 항목입니다)** `📁 내 경험`
> **→ 시세마다 다시 그려야 하는 차트라 DOM 대신 Canvas에 직접 그렸습니다.** 메이크델타의 트레이딩 차트가 **시세가 들어올 때마다 계속 다시 그려야 하는 화면**이었습니다.
>
> **→ DOM으로는 감당이 안 됐습니다.** 캔들과 지표 선을 DOM 요소로 그리면 **값이 하나 들어올 때마다 브라우저가 전체 배치를 다시 계산**합니다.
>
> **→ Canvas는 배치 계산 없이 그림만 다시 그립니다.**
>
> **→ 축·확대축소·이동·십자선은 D3로 처리했습니다.** **D3의 scaleTime · scaleLinear · zoom · drag** 를 썼습니다.
>
> **→ D3는 그리기가 아니라 계산에만 썼습니다.** **"이 값이 화면 어느 위치인지" 계산하고 마우스 동작을 해석하는 데만** 쓴 셈입니다.

**30초 버전** — "시세마다 다시 그려야 하는 차트라 DOM으로는 배치 재계산을 감당 못 해서 Canvas에 직접 그렸습니다. D3는 그리기가 아니라 좌표 계산과 줌·드래그 해석에만 썼습니다."

**꼬리 질문 대비**

**→ "주식 앱에서는 왜 다르게 했나요?"** 주식 앱은 웹뷰가 아니라 앱 안에서 직접 그려야 할 만큼 성능이 필요해서 **React Native Skia로 캔들 차트를 구현**했습니다. 같은 차트라도 **어디서 도느냐에 따라 그리는 방법을 다르게 골랐습니다.**

**→ "Canvas의 단점은요?"** 요소가 DOM에 없어서 **클릭한 위치가 어느 캔들인지 직접 계산**해야 하고, **접근성도 따로** 챙겨야 합니다. 그래서 **위치 계산을 D3 scale에 맡겼다**고 잇습니다.
