## 2. 스트리밍 채팅 UI · 성능

### Q3. AI 응답이 스트리밍으로 올 때 채팅 UI를 어떻게 만들겠습니까?

**답변** `🌐 개념 정리` + `📁 내 경험`

**→ 토큰마다 화면을 다시 그리지 않게 모아서 반영하고, 지금 받는 메시지 하나만 다시 그립니다.** 채팅 UI를 직접 만든 적은 없지만, 자주 바뀌는 값 때문에 화면이 밀리는 문제는 겪어봤습니다.

**→ ① 토큰은 ref에 모으고, 화면 주기(약 16ms)마다 한 번만 state에 반영합니다.** 토큰이 1초에 수십 개 와도 렌더는 프레임당 한 번입니다.

**→ ② 끝난 메시지는 `memo`로 고정합니다.** 받는 중인 메시지를 목록에서 떼어 **그 하나만** 다시 그립니다.

**→ ③ 마크다운 변환처럼 무거운 일은 `useDeferredValue`로 미룹니다.** 스크롤과 입력이 먼저 돌게 합니다.

**→ 비슷한 문제를 메이크델타 차트에서 풀었습니다.** 시세가 계속 들어와서 React가 매번 다시 그리면 버벅였고, **React는 틀만 그리고 그림은 Canvas에 직접** 그렸습니다.

**→ "자동 배칭이 있는데 왜 직접 모으나요?"** 자동 배칭은 **같은 순간의** setState를 묶습니다. 토큰은 **네트워크 이벤트마다 따로** 와서 묶이지 않습니다.

**→ "코드로 설명해 보세요."** [25번 Q20](./25_qpist_review.md)의 **ref 버퍼 + `requestAnimationFrame`** 코드를 그대로 씁니다.

### Q4. 대화가 길어질수록 채팅 화면이 느려지고 메모리가 늘어납니다. 어떻게 보겠습니까?

**답변** `🌐 개념 정리` + `📁 내 경험`

**→ 먼저 계단식으로 오르는지 보고, 보이는 메시지만 그리게 한 뒤, 화면을 떠날 때 정리되는지 확인합니다.**

**→ ① 측정부터 합니다.** 같은 동작을 반복하면서 메모리가 **계단처럼 오르는지** 봅니다. 오르기만 하고 안 내려오면 **정리가 안 되는 것**입니다.

**→ ② 목록은 가상화합니다.** `FlatList`(또는 FlashList)로 **화면에 보이는 메시지만** 그립니다. 채팅은 아래부터 쌓이니 `inverted` 목록을 씁니다.

**→ ③ 이미지·애니메이션 정리를 봅니다.** 캐릭터 이미지 캐시, 타이핑 애니메이션 같은 것이 **화면을 떠나도 남는지** 확인합니다.

**→ 루티너리에서 실제로 이 순서로 잡았습니다.** 처음엔 이미지 캐시를 의심했는데 아니었고, **특정 화면을 반복 진입할 때만 계단식으로 오르는** 패턴을 보고 애니메이션 값 정리 누락을 찾았습니다(Q5).

**→ "FlashList와 FlatList 차이는요?"** FlashList는 **화면 밖으로 나간 셀을 버리지 않고 재사용**해서 빈 화면이 덜 보입니다. 대신 셀 높이를 잘 예측해야 합니다. **[ 실제로 써봤는지 ]**

### Q5. 성능 문제나 치명적 오류를 해결한 경험을 하나 말해 주세요. 무엇으로 측정했고 원인이 뭐였나요?

**답변** `📁 내 경험` — **공고가 직접 요구한 항목입니다. 문장 그대로 외우세요.**

**→ Xcode Organizer 실사용자 P95로 재보니, 화면이 사라져도 정리 안 되던 애니메이션 값이 원인이었고, 정리해서 Peak Memory를 958.5MB에서 297.4MB로 줄였습니다.**

**→ 측정 도구는 Xcode Organizer입니다.** 실제 사용자 기기에서 모인 숫자라서 골랐습니다. **P95가 메모리 부족으로 앱이 죽는 구간**이라 P50과 같이 봤습니다.

**→ 원인을 좁힐 때는 Instruments를 썼습니다.** 특정 화면을 **반복 진입할 때만 계단식으로 오르는** 패턴을 봤습니다.

**→ 처음엔 이미지 캐시를 의심했는데 아니었습니다.** 캐시를 줄여도 그래프가 그대로였습니다.

**→ 원인은 Reanimated SharedValue 정리 누락이었습니다.** 타이머·온보딩·진행 비교 화면의 애니메이션 값이 **화면이 사라져도 취소되지 않고** 쌓였습니다.

**→ 공용 훅 하나로 묶어 고쳤습니다.** 언마운트할 때 한꺼번에 취소하고, 사라진 뒤에는 콜백이 안 돌게 막았습니다. **값 24개**(온보딩 14 · 타이머 6 · 비교 4)에 적용했습니다.

**→ "Organizer는 화면 단위로 안 나오는데 어떻게 화면을 찾았나요?"** Organizer로 **문제가 있다는 것과 크기**를 보고, 원인 화면은 **Instruments로 화면을 반복 진입하며** 찾았다고 답합니다.

**→ "Android는요?"** Android Native Heap도 Debug 빌드에서 재서 **101.9MB → 31.2MB**를 확인했습니다. **면접에서는 PDF 숫자(P95)로 통일**하고, 이건 되물으면만 말합니다.

### Q6. Sentry로 크래시를 재현하고 고친 경험이 있나요?

**답변** `📁 내 경험`

**→ 릴리스 빌드에서만 앱 시작 4초 후 죽던 SIGABRT 크래시를, Sentry 스택에서 JNI 호출을 보고 ProGuard 규칙을 추가해 고쳤습니다.** (`336dd4564`, Sentry 이슈 `7046127658`)

**→ Sentry에서 본 건 `facebook::jni::isObjectRefType` 호출 중 SIGABRT였습니다.** Debug에선 안 나고 **Release에서만** 났습니다.

**→ 그래서 코드보다 빌드 차이를 의심했습니다.** Release에서만 도는 건 **ProGuard(코드 축소 도구)** 입니다. ProGuard가 **Facebook JNI 클래스를 안 쓰는 걸로 보고 지워버린** 것이었습니다.

**→ keep 규칙을 추가했습니다.** React Native JNI, TurboModule, Fabric, Hermes 관련 클래스를 지우지 않게 했습니다. **New Architecture를 켠 앱에서는 꼭 필요한 규칙**입니다.

**→ "재현은 어떻게 했나요?"** **Release 빌드를 기기에 직접 깔아서** 같은 시점에 죽는지 확인했습니다. Debug로는 절대 재현이 안 되는 종류였습니다.

**→ "Sentry와 Crashlytics를 같이 쓰나요?"** 루티너리는 둘 다 있었고, 저는 **catch 블록의 에러를 Sentry `captureException`으로 모으는 정리**를 했습니다(`#832`). Sentry 초기화 위치를 앞당기고 **CodePush 번들 버전을 같이 기록**해서, **어느 OTA 번들에서 난 에러인지** 구분되게 했습니다(`8fc859c67`).

### Q7. 원인을 알 수 없는 앱 시작 크래시는 어떻게 추적했나요?

**답변** `📁 내 경험`

**→ 콜드 스타트에서만 나던 크래시를, SDK 초기화 순서가 꼬인 레이스로 보고 초기화를 앞으로 옮겨 고쳤습니다.** (`f3a1cea1f`, Airbridge)

**→ 어트리뷰션 SDK인 Airbridge가 원인이었습니다.** Airbridge는 첫 화면(Activity)이 만들어질 때 자기 초기화가 끝나 있다고 가정합니다.

**→ 그런데 앱 시작을 빠르게 하려고 SDK 초기화를 500ms 미뤄 둔 상태였습니다.** 콜드 스타트에서 **첫 화면이 초기화보다 먼저 뜨면** `IllegalStateException`으로 죽었습니다.

**→ Airbridge만 `Application.onCreate()`에서 바로 초기화하게 바꿨습니다.** 첫 화면보다 **항상 먼저** 끝나게 보장했습니다. 나머지 무거운 SDK는 그대로 뒤로 미뤘습니다.

**→ 배운 점은 "다 미루면 안 된다"입니다.** 시작 속도 때문에 미루더라도, **다른 코드가 먼저 끝나 있다고 믿는 SDK는 예외**로 둬야 합니다.

**→ "그 크래시는 어떻게 찾았나요?"** **[ Crashlytics/Sentry에서 본 스택과 몰린 조건 — 콜드 스타트·특정 OS 등 ]** 스택에 SDK의 Lifecycle 코드가 보였다는 흐름으로 말합니다.

### Q8. 화면이 버벅이는데 JS가 아니라 네이티브 쪽이 원인이었던 경험이 있나요?

**답변** `📁 내 경험`

**→ iOS 알림 예약이 메인 스레드에서 동기로 돌아 UI를 붙잡고 있어서, 네이티브 메서드를 비동기 API로 다시 구현했습니다.** (`633449e1f`)

**→ 원인은 `PushNotificationIOS` 라이브러리였습니다.** 알림 예약·취소를 **옛 API(`UILocalNotification`)로 메인 스레드에서 동기 실행**했습니다.

**→ 상태가 바뀔 때마다 알림을 몰아서 다시 예약하는 구조라, 그때마다 화면이 멈췄습니다.**

**→ 라이브러리를 patch해서 네이티브 메서드 본문을 `UNUserNotificationCenter`로 바꿨습니다.** 스레드 안전한 비동기 API입니다. **JS 쪽 호출 방식은 그대로**라 앱 코드는 안 바꿨습니다.

**→ 원인을 좁히려고 진단용 토글도 넣었습니다.** 임시로 다른 알림 경로(notifee)로 바꿔서 **버벅임이 사라지는지** 먼저 확인했습니다.

**→ Android ANR도 비슷했습니다.** 이벤트 로깅 하나가 **분석 SDK 6개와 저장소 작업 2개를 한꺼번에** 돌려 메인 스레드를 **0.5~2초** 붙잡았고, `InteractionManager`로 화면을 다 그린 뒤로 미뤘습니다.

**→ "라이브러리를 patch하면 업데이트 때 위험하지 않나요?"** 맞습니다. 그래서 **JS 시그니처는 그대로 두고 네이티브 본문만** 바꿨고, patch 파일로 남겨 **버전을 올릴 때 다시 확인할 대상**이 보이게 했습니다.

## 3. 인앱결제 · 광고 · 어트리뷰션

### Q9. 인앱결제를 연동해 봤나요? 구매 검증은 어떻게 설계하나요?

**답변** `📁 내 경험`

**→ 루티너리는 Adapty로 구독을 관리했고, 저는 구매 직후 상태를 "낙관적으로 켜지 않고" 서버 동기화 결과를 기다리게 바꿨습니다.** (`43f978195`)

**→ 영수증 검증은 클라이언트가 아니라 서버에서 해야 합니다.** 앱이 "샀다"고 말하는 걸 믿으면 **조작된 요청으로 유료 기능이 열립니다.** 루티너리는 Adapty 서버가 스토어 영수증을 검증했습니다.

**→ 구매 완료 직후 미리 켜던 걸 뺐습니다.** 미리 켜면 **검증이 실패해도 유료 화면이 잠깐 열립니다.** 실제 동기화 결과로만 구독 상태를 바꾸게 했습니다.

**→ 앱으로 돌아올 때 다시 확인합니다.** 포그라운드로 올 때 구독 상태를 재검증하되, **1시간 쿨다운**을 둬서 불필요한 호출을 막았습니다.

**→ 이벤트 리스너 레이스도 고쳤습니다.** 비동기로 리스너를 붙이는 사이에 화면이 사라지면 **언마운트 뒤에 리스너가 붙어 남는** 문제였습니다. 취소 플래그로 막았습니다(`c24e7e03d`).

**→ "재화(코인)를 지급하는 구조라면요?"** 구독과 달리 **같은 구매가 두 번 지급되면 안 됩니다.** 서버가 **거래 ID로 한 번만 지급**하고(멱등), 앱은 지급 완료를 확인한 뒤에야 스토어에 **구매 완료(finish)** 를 알립니다. 순서가 바뀌면 **돈은 나갔는데 재화가 없는** 상황이 생깁니다. `🌐 개념 정리`

**→ "구매 복원은요?"** 기기를 바꾸거나 재설치하면 **스토어에 남은 구매 기록으로 권한을 다시 찾는** 기능입니다. 루티너리는 `adapty.restorePurchases()`로 처리했습니다. **[ 복원 버튼 흐름을 직접 만졌는지 ]**

### Q10. 광고 SDK를 붙이면서 겪은 문제가 있나요?

**답변** `📁 내 경험`

**→ Android에서 보상형 광고가 무한 로딩되어 사용자가 기능을 못 쓰던 문제를 고쳤습니다.** (`6a62cb252`)

**→ 루티너리는 구독 대신 광고를 보고 기능을 쓰게 하는 구조였습니다.** 그런데 광고가 안 뜨면 **팝업이 계속 돌기만 하고** 루틴을 끌 수가 없었습니다.

**→ 원인은 실패를 받는 쪽이 없었던 것입니다.** 광고 로딩 **에러 이벤트 처리기가 없어서**, 실패해도 앱은 계속 기다렸습니다.

**→ 네 가지를 넣었습니다.** 에러 처리기, **타임아웃 5초 → 15초**(Android 네트워크 고려), 로딩 중 **취소 버튼**, 실패·타임아웃 시 팝업 자동 닫기입니다.

**→ 실패 유형별로 로그를 남겼습니다.** 로딩 실패, 타임아웃, 예외를 나눠 기록해서 **어느 쪽이 많은지** 볼 수 있게 했습니다.

**→ "광고가 실패하면 사용자에게 보상을 줘야 하나요?"** 기획과 정할 문제지만, **사용자가 막히지 않는 것**이 먼저라고 답합니다. 루티너리는 실패하면 팝업을 닫고 원래 화면으로 돌려보냈습니다.

### Q11. 어트리뷰션 SDK나 딥링크를 다뤄 봤나요?

**답변** `📁 내 경험`

**→ 루티너리는 Airbridge를 썼고, 저는 초기화 순서 크래시를 고쳤고 딥링크 라우팅도 직접 다뤘습니다.**

**→ 어트리뷰션 SDK는 "이 설치가 어느 광고에서 왔나"를 알려주는 도구입니다.** 그래서 **앱 시작 가장 앞에서** 초기화돼야 하고, 늦추면 Q7처럼 크래시가 나거나 설치 기록이 빠집니다.

**→ 딥링크는 `src/navigations/linking.ts`에서 React Navigation `linking` 설정으로 처리했습니다.** 예를 들어 **타이머가 도는 중에 다른 루틴 시작 딥링크를 누르면** 그 루틴이 시작되도록 고쳤습니다(`b94d876ba`).

**→ "디퍼드 딥링크는요?"** 앱이 **설치 안 된 상태에서** 링크를 누르면, 설치 후 첫 실행 때 **원래 가려던 화면으로** 보내주는 기능입니다. 어트리뷰션 SDK가 이 정보를 넘겨줍니다. **[ 루티너리에서 디퍼드 딥링크를 직접 다뤘는지 ]** `🌐 개념 정리`

### Q12. 푸시 알림을 눌렀을 때 특정 화면으로 가게 하는 흐름은 어떻게 만들었나요?

**답변** `📁 내 경험`

**→ Android에서 포그라운드 알림이 안 뜨고 탭해도 이동이 안 되던 걸, 인앱 배너 + 딥링크 이동으로 다시 만들었습니다.** (`f84355076`)

**→ 원인이 세 가지였습니다.**
- Android 12부터 `PendingIntent`에 **FLAG_IMMUTABLE**이 필요한데, 알림 라이브러리의 탭 동작이 이 조건에 걸렸습니다.
- 알림 `id`가 비어 있을 때 그대로 넘기면 **New Architecture에서 JSI 호출이 멈추는** 문제가 있었습니다.
- Android 13부터 필요한 **POST_NOTIFICATIONS 권한**이 빠져 있었습니다.

**→ 포그라운드에선 시스템 알림 대신 인앱 배너를 띄우고, 탭하면 딥링크로 이동하게 했습니다.**

**→ "앱이 꺼진 상태(콜드 스타트)에서 알림을 누르면요?"** 네비게이션이 **준비되기 전에** 이동을 시도하면 무시됩니다. 그래서 **처음 열린 알림을 받아 두었다가, 네비게이션 준비가 끝난 뒤 이동**합니다. React Navigation의 `linking.getInitialURL`이 이 자리입니다.

## 4. 네이티브 · New Architecture

### Q13. Swift나 Kotlin으로 네이티브 모듈을 만들어 봤나요?

**답변** `📁 내 경험`

**→ 네, JS가 떠 있지 않은 곳에서 돌아야 하는 기능을 Swift·Kotlin으로 만들었습니다.** 홈 위젯, 위치 알림, Wear OS입니다.

**→ 홈 위젯은 Android 5종을 Jetpack Glance로 다시 만들고, iOS 체크리스트 위젯은 AppIntents로 위젯에서 바로 체크되게 했습니다.** 앱과 위젯은 **App Group / 공유 저장소**로 데이터를 주고받습니다.

**→ 위치 알림은 앱이 꺼져 있어도 돌아야 했습니다.** 네이티브 지오펜스가 이벤트를 받으면 **Headless JS**(화면 없이 JS를 잠깐 깨우는 방식)로 넘겼고, 제한 시간은 **5초**였습니다. 재부팅 후 다시 등록하는 리시버도 넣었습니다.

**→ 라이브러리 네이티브 코드를 직접 고친 적도 있습니다.** Q8의 iOS 알림 patch입니다.

**→ "Kotlin·Swift 숙련도는 어느 정도인가요?"** **RN에 필요한 네이티브 경계를 혼자 만들 수 있는 수준**이라고 선을 긋습니다. 네이티브 앱을 처음부터 짜는 수준이라고는 말하지 않습니다. ([10번](./10_tech_kotlin_android.md) · [11번](./11_tech_swift_ios.md) Q0)

### Q14. New Architecture(TurboModule · Fabric · JSI)를 설명해 주세요. 실제로 겪은 차이가 있나요?

**답변** `🌐 개념 정리` + `📁 내 경험`

**→ 예전 Bridge는 JS와 네이티브가 메시지를 직렬화해서 비동기로 주고받았고, New Architecture는 JSI로 JS가 네이티브 객체를 직접 부릅니다.**

**→ JSI**는 JS가 C++ 객체를 **직접 들고 호출하는 통로**입니다. JSON으로 바꿨다 푸는 과정이 없고, 동기 호출도 됩니다.

**→ TurboModule**은 그 위의 네이티브 모듈 방식입니다. **처음 쓸 때 불러오고(지연 로딩)**, 타입 정의(Codegen)로 JS와 네이티브의 약속을 맞춥니다.

**→ Fabric**은 새 화면 렌더러입니다. 화면 트리를 C++에서 관리해서 **동기 레이아웃 측정, React 18 동시성 기능**을 쓸 수 있습니다.

**→ 루티너리는 `newArchEnabled=true`인 RN 0.84 앱이었고, 실제로 차이를 두 번 겪었습니다.** ① Release에서 ProGuard가 **JNI·TurboModule·Fabric 클래스를 지워** SIGABRT(Q6). ② 알림 `id`에 `undefined`를 넘기면 **JSI 호출이 멈춤**(Q12).

**→ "TurboModule을 직접 만들어 봤나요?"** **직접 Codegen 스펙부터 만든 적은 없습니다.** New Arch 앱을 운영하면서 생긴 빌드·크래시 문제를 고친 경험이 있다고 정확히 말합니다.

### Q15. Nitro 모듈을 써 봤나요?

**답변** `📁 내 경험`

**→ 사진 꾸미기 기능에서 Nitro 기반인 `react-native-vision-camera` 5와 `react-native-nitro-image`를 도입했습니다.** (`2e8fdb87b`, `#1344`) 직접 Nitro 모듈을 만든 적은 없습니다.

**→ Nitro는 JSI 위에서 타입 정의 하나로 Swift·Kotlin·C++ 코드를 생성해 주는 모듈 시스템입니다.** TurboModule보다 **호출 비용이 적고 타입이 엄격**한 게 장점입니다. `🌐 개념 정리`

**→ 도입하면서 네이티브 빌드 충돌을 하나 풀었습니다.** Q17입니다.

**→ "직접 만든다면 어디에 쓰겠어요?"** 공고에 있는 것처럼 **스트리밍 텍스트 처리나 이미지 디코딩**처럼 JS 스레드에서 무거운 일입니다. 다만 **먼저 JS 쪽 렌더 배칭으로 충분한지 측정**하고, 부족할 때 내립니다.

### Q16. C++ 경험이 있나요?

**답변** `📁 내 경험`

**→ C++로 모듈을 짠 경험은 없습니다.** 대신 C++ 층에서 나는 크래시를 읽고 고친 경험은 있습니다.

**→ Q6의 SIGABRT가 C++(JNI) 층 크래시였습니다.** 스택 트레이스에서 `facebook::jni`를 보고, 코드가 아니라 **빌드에서 클래스가 지워졌다**는 걸 찾았습니다.

**→ 필요하면 Nitro부터 시작하겠습니다.** Nitro는 타입 정의 하나로 C++ 뼈대를 만들어 줘서, **C++ 코드를 처음부터 다 쓰지 않고도** 성능이 필요한 부분만 채울 수 있습니다.

**→ AI 에이전트를 쓰는 방식도 같습니다.** 낯선 Kotlin·Swift도 **코드 분석 → 계획 → 구현 → 검증** 순서로 혼자 만들었습니다. C++도 같은 순서로 하되, **제가 설명 못 하는 코드는 넣지 않습니다.**

**→ "그럼 C++이 필요한 일이 오면요?"** **팀에 C++을 아는 분이 있으면 리뷰를 받고**, 메모리 해제·스레드 같은 위험한 부분은 **테스트를 먼저** 깔겠다고 답합니다.

### Q17. 네이티브 빌드 문제를 해결한 경험이 있나요?

**답변** `📁 내 경험`

**→ 라이브러리 두 개가 같은 Android 의존성을 서로 다른 버전으로 끌어와 런타임에 죽던 걸, Gradle에서 버전을 고정해 고쳤습니다.** (`2e8fdb87b`)

**→ `react-native-vision-camera`가 `androidx.media3`를 1.9.0으로 올렸습니다.** 그런데 `react-native-video`는 **1.8.0 기준으로 컴파일**돼 있었습니다.

**→ 그래서 빌드는 되는데 실행하면 죽었습니다.** 1.8.0에 있던 생성자가 1.9.0에서 사라져 **`NoSuchMethodError`** 가 났습니다.

**→ media3 그룹 전체를 1.8.0으로 고정했습니다.** vision-camera는 **사진 촬영만 쓰고 media3는 안 쓴다**는 걸 확인하고 고정해도 안전하다고 판단했습니다. 이유를 `build.gradle` 주석으로 남겼습니다.

**→ iOS 쪽은 Podfile에서 카메라·사진 권한 모듈을 켰습니다.** 권한 모듈이 빠지면 **빌드는 되는데 권한 요청에서 막힙니다.**

**→ "이런 충돌은 어떻게 찾나요?"** `./gradlew app:dependencies`로 **누가 어떤 버전을 끌어오는지** 트리를 봅니다. `NoSuchMethodError`는 거의 항상 **컴파일 때와 실행 때 버전이 다르다**는 신호입니다.

## 5. 상태 · 애니메이션

### Q18. 서버 상태와 클라이언트 상태를 어떻게 나눠 설계했나요?

**답변** `📁 내 경험`

**→ 서버에서 오는 데이터는 TanStack Query가, 앱 안에서만 쓰는 상태는 Zustand가 맡게 나눴습니다.**

**→ 서버 데이터는 원본이 서버에 있습니다.** 캐시, 다시 불러오기, 실패 재시도를 **TanStack Query에 맡기면** 직접 동기화 코드를 안 짜도 됩니다.

**→ 클라이언트 상태는 앱이 원본입니다.** 타이머 진행, 화면 설정 같은 건 **Zustand + MMKV**로 기기에 저장했습니다. 스토어는 21개였습니다.

**→ 둘을 섞으면 같은 데이터가 두 곳에 생깁니다.** 서버 데이터를 Zustand에 복사해 두면 **어느 쪽이 최신인지** 맞추는 코드가 따로 필요해집니다.

**→ 채팅에 적용하면** 대화 기록·캐릭터 정보는 **TanStack Query**, 입력창 초안·스트리밍 중인 텍스트는 **클라이언트 상태**입니다.

**→ "스트리밍 메시지를 Query 캐시에 넣나요?"** 받는 중에는 **로컬 상태로 그리고**, 끝나면 `setQueryData`로 **완성된 메시지만 캐시에 넣습니다.** 토큰마다 캐시를 바꾸면 구독하는 화면이 전부 다시 그려집니다. `🌐 개념 정리`

### Q19. Reanimated와 Gesture Handler를 쓰면서 주의한 점은요?

**답변** `📁 내 경험`

**→ 애니메이션 값이 화면 수명과 따로 놀기 때문에, 화면이 사라질 때 반드시 정리하는 것을 원칙으로 했습니다.**

**→ Reanimated는 UI 스레드에서 따로 돕니다.** 그래서 JS 쪽 화면이 사라져도 **애니메이션이 계속 돌고 값이 남을 수** 있습니다. Q5의 누수가 이것이었습니다.

**→ 정리 코드를 공용 훅으로 묶었습니다.** 화면마다 각자 정리하게 두면 **누군가 빠뜨립니다.**

**→ worklet 안에서 JS 함수를 바로 부르지 않습니다.** UI 스레드에서 도는 코드라, JS 쪽 함수를 부를 때는 `runOnJS`로 넘깁니다.

**→ "Gesture Handler는 왜 쓰나요?"** RN 기본 터치는 **JS 스레드를 거쳐서**, JS가 바쁘면 제스처가 밀립니다. Gesture Handler는 **네이티브에서 제스처를 처리**해서 스와이프·드래그가 부드럽습니다. 채팅에서는 **메시지 스와이프 답장, 길게 눌러 메뉴** 같은 곳입니다.

## 6. 배포 · 운영

### Q20. OTA 배포와 롤백은 어떻게 했나요?

**답변** `📁 내 경험`

**→ App Center 종료 후 오픈소스 CodePush 클라이언트에 S3·CloudFront를 붙여 서버 없이 직접 구축했고, 배포·롤백은 GitHub Actions 버튼 하나로 돌렸습니다.**

**→ 번들과 배포 기록은 S3에 두고 CloudFront로 내려줍니다.** 따로 돌아가는 서버가 없습니다.

**→ 만들다가 배포 기록이 통째로 날아갈 수 있는 구멍을 막았습니다.** 기록을 **CloudFront 캐시에서 읽으면** 오래된 캐시 때문에 비어 보일 수 있습니다. 그래서 **항상 S3 원본에서 읽고, 기존 기록이 빠지면 쓰지 않게** 했습니다.

**→ 롤백은 문제 번들을 비활성화하는 방식입니다.** 배포 워크플로에는 **롤아웃 비율**과 **강제 업데이트** 옵션이 있습니다.

**→ "롤백하면 바로 사라지나요?"** 아닙니다. 앱이 **다음에 업데이트를 확인할 때까지** 잘못된 번들이 남습니다. 한동안 두 버전이 섞이니 **서버가 둘 다 받을 수 있어야** 합니다.

**→ "OTA로 못 고치는 건요?"** **네이티브 코드 변경**입니다. 라이브러리를 올리거나 권한을 바꾸면 스토어 배포가 필요합니다. 그래서 **OTA 번들이 어느 네이티브 버전과 맞는지** 꼭 묶어서 배포합니다. 자세한 건 [25번 Q16](./25_qpist_review.md).

### Q21. 스토어 릴리스와 CI/CD는 어떻게 운영했나요?

**답변** `📁 내 경험`

**→ Fastlane으로 빌드부터 스토어 업로드까지 자동화하고, 출시 버튼만 사람이 누르게 나눴습니다.**

**→ 빌드 번호는 커밋 수에서 만듭니다.** 사람이 번호를 올리다 **겹치거나 빠뜨리는** 일이 없습니다.

**→ 버전 이름은 `package.json` 하나가 원본입니다.** iOS와 Android가 같은 값을 읽습니다.

**→ 자동은 테스트 트랙까지입니다.** iOS는 TestFlight에 올리고 **심사 제출은 안 합니다**(`skip_submission: true`). Android는 내부 트랙에 **draft**로 올립니다. **출시 판단은 사람이** 합니다.

**→ 결과는 Slack 웹훅으로 알립니다.**

**→ "왜 출시까지 자동화 안 했나요?"** 출시는 **기획·QA 확인과 타이밍(이벤트, 주말)** 이 걸린 판단이라 사람 몫으로 남겼습니다.

**→ "CI 실패 알림은요?"** 솔직히 **성공 알림만 있고 실패 알림 블록은 없었습니다.** 지금 보면 넣어야 할 부분이라고 답합니다.

### Q22. 작은 크래시인데 기획에서는 새 기능이 급하다고 합니다. 어떻게 하나요?

**답변** `📁 내 경험`

**→ 영향받는 사용자 수와 결제·데이터 유실 여부로 숫자를 만들어서, 그 숫자로 같이 정합니다.**

**→ 먼저 규모입니다.** 영향받은 사용자가 **몇 명, 전체의 몇 %** 인지, 크래시 없이 쓴 사용자 비율이 얼마나 떨어졌는지 봅니다.

**→ 다음은 어디서 나는지입니다.** **결제 화면이나 데이터 저장 중**이면 작아도 먼저 고칩니다. 돈이나 기록이 걸린 건 되돌릴 수 없어서입니다.

**→ 아니면 일정에 넣고 막아 둡니다.** 원격 설정(Remote Config)으로 **문제 기능만 끄고** 새 기능을 먼저 할 수도 있습니다.

**→ "숫자가 애매하면요?"** **이번 스프린트에 고칠 비용(시간)** 과 **안 고쳤을 때 늘어날 위험**을 나란히 보여주고, 결정은 같이 합니다. **[ 루티너리에서 실제로 이렇게 조율한 사례 ]**

### Q23. 여러 앱이 공통 패키지를 쓰는 모노레포를 다뤄 봤나요?

**답변** `📁 내 경험`

**→ 모노레포를 운영한 적은 없습니다. 대신 메이크델타에서 디자인 시스템을 앱과 분리된 패키지(`MakedeltaMobileUI`)로 만들었습니다.** **[ 이 패키지를 쓰던 앱이 몇 개였는지 ]**

**→ 공통 패키지에서 가장 조심한 건 의존성 중복입니다.** React·RN 같은 건 `peerDependencies`로 빼서 **앱이 가진 버전을 쓰게** 했습니다. 패키지가 따로 들고 있으면 **같은 라이브러리가 두 벌** 들어가서 오류가 납니다.

**→ 모노레포로 가면 좋아지는 점도 압니다.** 공통 코드를 고치면 **세 앱에서 바로 같이 검증**할 수 있고, 버전 맞추는 일이 줄어듭니다.

**→ 대신 한 번의 변경이 세 앱을 다 깨뜨릴 수 있습니다.** 그래서 **바뀐 패키지에 걸린 앱만 골라 빌드·테스트**하는 CI가 핵심이라고 봅니다. `🌐 개념 정리`

**→ "Turborepo · Nx 써봤나요?"** **안 써봤습니다.** 들어가서 팀 구성을 먼저 읽겠다고 답합니다.

## 7. AI 코딩 에이전트

### Q24. AI 코딩 에이전트를 팀에서 어떻게 쓰게 만들었나요? 규칙은 어떻게 개선했나요?

**답변** `📁 내 경험`

**→ 사람이 확인하던 걸 기계가 강제하게 만든 하네스를 팀에 깔았습니다.** 훅 2개, 규칙 문서 8개, 리뷰·진단 에이전트, 차단 명령 9개입니다.

**→ 훅은 "반드시 지켜야 하는 것"입니다.** 파일을 고치면 **ESLint가 자동으로** 돌고, 작업을 끝낼 때 **타입 검사를 통과 못 하면 작업이 안 끝납니다.**

**→ 기존 타입 에러가 367개라, 전체 검사 결과에서 편집한 파일 에러만 걸러 막았습니다.** 새 코드는 깨끗하게 유지하고, 옛 에러는 그 파일을 건드릴 때 같이 고쳤습니다.

**→ 규칙 문서는 "가능하면 지키는 것"입니다.** 에이전트가 읽고 따르지만 **보장은 안 됩니다.** 그래서 꼭 지켜야 하는 건 규칙이 아니라 훅으로 옮겼습니다.

**→ 실제 크래시가 생기면 리뷰 항목이 됩니다.** 우리 앱에서 났던 크래시 패턴을 **리뷰 에이전트 검사 항목**으로 넣었습니다.

**→ "규칙이 늘면 컨텍스트가 낭비되지 않나요?"** 그래서 한 문서에 몰지 않고 **8개로 나눴습니다.** 다만 **적용 범위를 좁게 잡은 건 컴포넌트 규칙 하나**였고, 나머지는 거의 늘 같이 읽힌다는 한계도 정직하게 말합니다.

**→ "git push를 못 하게 막았나요?"** 막은 건 **force push, `rm -rf`, `reset --hard`** 같은 되돌릴 수 없는 명령 9개입니다. **일반 `git push`는 막지 않았습니다.**

### Q25. AI가 만든 코드를 어떻게 검증하나요? 틀린 걸 잡은 사례가 있나요?

**답변** `📁 내 경험`

**→ 기계가 검사할 수 있는 건 기계에게 맡기고, 제가 보는 건 "설명할 수 있나"와 "실제 기기에서 맞나"입니다.**

**→ 타입·린트는 훅이 막습니다.** 그래서 제가 리뷰할 때는 **동작과 경계 조건**에 집중합니다.

**→ 리뷰 에이전트에는 고치는 도구를 주지 않았습니다.** 진단·리뷰 에이전트의 도구는 **Read·Grep·Glob·Bash뿐**이고 Edit·Write가 없습니다. **보고만 하고, 고칠지는 사람이** 정합니다.

**→ 제가 설명 못 하는 코드는 넣지 않습니다.** 순서가 **코드 분석 → 계획 → 구현 → 검증**이라, 계획에서 이해가 안 되면 다음으로 안 넘어갑니다.

**→ 원인 진단은 실제 기기에서 확인합니다.** Q8에서 iOS 버벅임을 고칠 때도 바로 고치지 않고, **다른 알림 경로로 바꿔 증상이 사라지는지 먼저** 확인했습니다.

**→ "AI가 틀린 걸 잡은 사례는요?"** **[ 실제 사례 하나 ]** — 생각이 안 나면 [22번 Q4](./22_ykplan_interview.md)의 사례를 씁니다.

**→ "AI가 짠 코드의 책임은 누구에게 있나요?"** **커밋한 사람**입니다. 그래서 설명 못 하는 코드는 안 넣는다는 원칙을 둔다고 답합니다.

## 8. 협업 · 마무리

### Q26. 기획·디자인·백엔드와 같은 스쿼드에서 일할 때 어떻게 소통하나요?

**답변** `📁 내 경험`

**→ 플랫폼 제약은 기획 단계에서 먼저 말하고, 대안을 같이 들고 갑니다.**

**→ 예를 들어 iOS 위젯은 앱이 원하는 순간에 바로 바뀌지 않습니다.** 다시 그려달라고 **요청은 할 수 있지만 시점은 시스템이 정합니다.** 이걸 기획 초기에 말하고 **"눌러서 바로 반영되는 방식"** 으로 대안을 냈습니다.

**→ 백엔드와는 실패했을 때를 먼저 맞춥니다.** 결제·동기화처럼 **중간에 끊겼을 때 누가 다시 시도하나**를 정해 두면 장애 대응이 빨라집니다.

**→ PR은 작게 나눕니다.** 결제처럼 위험한 코드는 **따로 표시해서 리뷰를 모았습니다.**

**→ "디자인과 의견이 다르면요?"** 성능이나 플랫폼 규칙 때문에 안 되면 **안 되는 이유와 비슷한 효과를 내는 대안**을 같이 보여줍니다. 취향 문제면 디자인 결정을 따릅니다.
