# 기술 면접 — React

> 프론트엔드 기술 면접에서 자주 나오는 React 질문과 답변입니다.
> **답변 뒤의 `▶ 내 경험`은 이력서와 연결하는 문장**입니다. 이게 있어야 암기가 아니라 경험으로 들립니다.

>
> 답변은 두 종류로 나눴습니다.
> - **`📁 내 경험`** — 이력서·실제 프로젝트에서 꺼낸 답입니다. 이 답을 먼저 말하세요.
> - **`🌐 개념 정리`** — 일반 개념 설명입니다. 외우기보다 **이해해서 내 말로** 하세요.

## 렌더링과 재조정

### Q1. React의 렌더링은 언제 일어나나요?

**답변** `🌐 개념 정리`
> **→ 세 가지입니다.** **상태가 바뀔 때**, **부모가 리렌더될 때**, **컨텍스트 값이 바뀔 때**입니다.
>
> **→ "props가 바뀌어야 리렌더된다"는 오해입니다.** **부모가 리렌더되면 자식은 props가 그대로여도 같이 리렌더됩니다.**
>
> **→ 리렌더가 곧 DOM 조작은 아닙니다.** 렌더는 **"새 엘리먼트 트리를 만드는 것"** 입니다.
>
> **→ 화면에는 바뀐 부분만 반영됩니다.** **재조정** — 이전 트리와 새 트리를 비교해서 바뀐 부분만 찾는 과정 — 을 거칩니다.

**30초 버전** — "상태 변경, 부모 리렌더, 컨텍스트 변경 세 가지입니다. props가 그대로여도 부모가 다시 그려지면 자식도 다시 그려지고, 실제 DOM에는 재조정을 거쳐 바뀐 부분만 반영됩니다."

**꼬리 질문 대비**

**→ "그럼 리렌더가 많은 게 왜 문제인가요?"** 화면이 그대로여도 **렌더 함수 안의 계산과 자식들을 훑는 비용은 똑같이 듭니다.** 리스트가 크거나 렌더 중 무거운 계산이 있으면 그게 바로 **화면 끊김**으로 나타납니다.

### Q2. key는 왜 필요하고, index를 쓰면 왜 안 되나요?

**답변** `🌐 개념 정리`
> **→ key는 "이게 아까 그 항목이 맞나"를 알려주는 이름표입니다.** **재조정** — 이전 화면과 새 화면을 비교하는 과정 — 에서 씁니다.
>
> **→ key가 없으면 순서로만 비교합니다.** 중간에 항목이 하나 끼면 **그 뒤가 전부 다른 것으로 취급**됩니다.
>
> **→ index를 key로 쓰면 상태가 엉뚱한 항목에 붙습니다.** 정렬하거나 넣고 지울 때 **같은 번호에 다른 데이터가 들어가기** 때문입니다.
>
> **→ 대표적인 버그가 있습니다.** 리스트 중간을 지웠는데 **입력창 값이 다른 행으로 옮겨가는** 경우입니다.

**언제 index를 써도 되나** — 순서가 절대 안 바뀌고, 추가·삭제가 없고, 항목에 상태가 없을 때만입니다.

**30초 버전** — "key는 재조정 때 '아까 그 항목'을 알아보는 이름표입니다. index를 쓰면 순서가 바뀔 때 같은 번호에 다른 데이터가 들어가서 상태가 엉뚱한 행에 붙습니다."

**꼬리 질문 대비**

**→ "key로 `Math.random()`을 쓰면요?"** 렌더마다 key가 바뀌니 **매번 전부 새 항목으로 보고 지웠다 다시 만듭니다.** 상태도 날아가고 성능도 나빠집니다. **데이터의 고유 id**를 씁니다.

### Q3. Virtual DOM이 실제 DOM보다 빠른가요?

**답변 (함정 질문입니다)** `🌐 개념 정리`
> **→ 아닙니다.** **손으로 최소한의 DOM만 건드리면 그게 제일 빠릅니다.**
>
> **→ Virtual DOM은 화면 구조의 JS 객체 사본입니다.** 화면 구조를 자바스크립트 객체로 한 벌 들고 있는 겁니다.
>
> **→ 목적은 속도가 아닙니다.** **"어떻게 바꿀지가 아니라 어떤 모습이어야 하는지만 써도 성능이 안 무너지게 하는 것"** 입니다.
>
> **→ 전체 재계산 비용을 diff로 줄여주는 장치입니다.** 상태에 따라 화면을 통째로 다시 그리듯 짜는 대가인 전체 재계산을, **diff** — 이전 것과 새것을 비교해 달라진 데만 추리는 작업 — 로 감당할 만큼 줄여줍니다.

**30초 버전** — "아닙니다. 직접 최소한만 건드리는 게 제일 빠르고, Virtual DOM은 '모습만 선언해도 성능이 무너지지 않게' 해주는 장치입니다. 비교 비용을 내고 개발 편의를 얻는 거래입니다."

**꼬리 질문 대비**

**→ "그럼 Virtual DOM을 안 쓰는 프레임워크는요?"** Svelte·Solid처럼 **컴파일 단계에서 바뀔 곳을 미리 알아내 직접 DOM을 고치는 방식**도 있습니다. **비교 비용을 아예 없애는 쪽**을 택한 거라고 설명합니다.

**포인트** — "빠르다"고 답하면 바로 반박당합니다. **얻는 것과 내주는 것을 같이 말하는 게 정답**입니다.

## Hooks

### Q4. useMemo / useCallback은 언제 쓰나요? 다 붙이면 안 되나요?

**답변** `🌐 개념 정리`
> **→ 세 경우에만 씁니다.** ① **계산 자체가 무거울 때**, ② 그 값이 **다른 memo 컴포넌트의 props**로 갈 때, ③ **다른 훅의 의존성 배열**에 들어갈 때입니다.
>
> **→ 메모이제이션도 공짜가 아닙니다.** 메모이제이션 — 계산 결과를 기억해뒀다 재활용하는 것 — 은 **의존성 배열을 매번 비교**해야 하고, 이전 값을 들고 있을 **메모리**도 듭니다.
>
> **→ 더 큰 문제는 옛날 값이 조용히 남는 것입니다.** **의존성 배열이 틀리면** 옛날 값이 남고, **버그 찾기가 훨씬 어려워집니다.**

**30초 버전** — "계산이 무겁거나, memo 컴포넌트에 props로 가거나, 다른 훅 의존성에 들어갈 때만 씁니다. 메모이제이션도 비교 비용과 메모리가 들고, 의존성을 틀리면 옛날 값이 조용히 남습니다."

**꼬리 질문 대비**

**→ "React Compiler가 나오면 필요 없어지나요?"** **자동 메모이제이션이 대부분을 대신해주는 방향**인 건 맞습니다. 다만 **컴파일러가 안전하다고 판단할 수 있게 규칙을 지켜 짜는 건 여전히 사람 몫**이라고 봅니다.

### Q5. useEffect의 클린업은 왜 필요한가요?

**답변** `🌐 개념 정리`
> **→ 이펙트가 외부에 남긴 것을 되돌리기 위해서입니다.** **구독, 타이머, 이벤트 리스너, 진행 중인 요청** 같은 것들입니다.
>
> **→ 클린업이 없으면 콜백이 살아 남습니다.** 화면이 사라진 뒤에도 콜백이 살아 있고, **그 콜백이 붙든 값까지 안 지워집니다.**
>
> **→ 결과는 두 가지 버그입니다.** **메모리 누수**와 **"이미 사라진 화면이 상태를 갱신하는" 버그**입니다.
>
> **→ 의존성이 바뀔 때도 클린업이 먼저 돕니다.** 그래서 **이전 구독이 새 구독과 겹치지 않습니다.**

**▶ 내 경험** `📁 내 경험`
> **→ 루티너리에서 클린업 누락으로 쌓이던 네이티브 메모리를 69% 줄였습니다.** 원인은 **Reanimated의 SharedValue** — 애니메이션이 쓰는 값 — **정리가 빠져서 네이티브 쪽 메모리가 계속 쌓이는 문제**였습니다.
>
> **→ 애니메이션 cleanup 훅을 다시 설계했습니다.** **`cancelAnimation`으로 이전 애니메이션을 확실히 끄고**, **`isMounted` 체크**로 화면이 사라진 뒤에는 worklet — 화면 그리는 쪽에서 도는 애니메이션 코드 — 이 실행되지 않게 막았습니다.
>
> **→ 직접 재서 확인했습니다.** 정리 훅에 등록한 **SharedValue 24개**에 적용했고, **Android Native Heap**으로 재보니 **Total Allocations가 101.9MB → 31.2MB, 69% 줄었습니다.**
>
> **→ 배운 점입니다.** **"클린업은 JS 메모리만의 문제가 아니라 네이티브 자원 문제이기도 하다"** 는 것입니다.

**30초 버전** — "이펙트가 밖에 남긴 구독·타이머·리스너를 되돌리려고 씁니다. 루티너리에서 SharedValue 정리 누락으로 네이티브 메모리가 쌓이던 걸 공용 cleanup 훅으로 잡아서, Native Heap Total Allocations를 101.9MB에서 31.2MB로 69% 줄였습니다."

**꼬리 질문 대비**

**→ "JS 쪽 GC가 있는데 왜 네이티브 메모리가 남나요?"** 애니메이션 값과 worklet은 **네이티브(UI 스레드) 쪽 자원**이라, **JS 참조만 끊는다고 바로 정리되지 않았습니다.** 그래서 `cancelAnimation`으로 **명시적으로 끄는 게** 필요했습니다.

**→ "어떻게 측정했나요?"** Android Native Heap 계측으로 **개선 전후를 같은 조건에서 직접** 쟀다고 답합니다. **Remaining Size도 31.2MB → 11.0MB**로 줄었습니다.

### Q6. useEffect 의존성 배열을 비우면 어떻게 되나요?

**답변** `🌐 개념 정리`
> **→ 처음 한 번만 실행되고, 안에서 잡은 값이 굳습니다.** 화면이 처음 뜰 때 한 번 돌고, **그 안의 값은 첫 렌더 시점 그대로**입니다.
>
> **→ 이걸 stale closure라고 합니다.** 말 그대로 **옛날 값을 계속 붙들고 있는 상태**입니다. 나중에 상태가 바뀌어도 이펙트 안에서는 처음 값만 보입니다.
>
> **→ 최신 값이 필요하면 두 가지 방법이 있습니다.** **함수형 업데이트(`setState(prev => ...)`)** 를 쓰거나, **ref에 최신 값을 담아 참조**합니다.

**30초 버전** — "처음 한 번만 실행되고, 안에서 잡은 값이 첫 렌더 값으로 굳는 stale closure가 생깁니다. 최신 값이 필요하면 함수형 업데이트나 ref를 씁니다."

**꼬리 질문 대비**

**→ "그냥 의존성에 다 넣으면 되지 않나요?"** **넣는 게 원칙입니다.** 다만 값이 바뀔 때마다 이펙트가 다시 돌아서 **구독을 끊었다 다시 맺는 비용**이 생깁니다. **그게 부담일 때만** ref로 최신 값을 읽습니다.

### Q7. useState와 useReducer는 어떻게 나눠 쓰나요?

**답변** `🌐 개념 정리`
> **→ 상태끼리 서로를 참조해야 하면 useReducer입니다.** 예를 들어 "로딩 중이면 제출 불가, 에러가 있으면 로딩 해제" 같은 규칙이 여러 개 얽히는 경우입니다.
>
> **→ useState 여러 개로는 규칙이 흩어집니다.** 그 규칙이 **컴포넌트 곳곳에 흩어집니다.**
>
> **→ reducer로 모으면 전환 규칙이 문서처럼 남습니다.** **"어떤 상태에서 어떤 상태로 갈 수 있는지"가 한 곳에** 남습니다.
>
> **→ 독립적인 값 두세 개면 useState입니다.** 그쪽이 **더 읽기 쉽습니다.**

**30초 버전** — "상태끼리 규칙으로 얽혀 있으면 useReducer로 전환 규칙을 한 곳에 모으고, 독립적인 값 몇 개면 useState가 더 읽기 쉽습니다."

**꼬리 질문 대비**

**→ "reducer의 장점이 또 있나요?"** reducer는 **순수 함수라 화면 없이 단독으로 테스트**하기 쉽습니다. **상태 전환이 복잡할수록** 이 장점이 커집니다.

### Q8. 커스텀 훅은 어떤 기준으로 분리하나요?

**답변** `🌐 개념 정리`
> **→ "같이 바뀌는 것끼리" 묶습니다.** **재사용은 결과지 목적이 아니라고** 봅니다.
>
> **→ 한 번만 쓰여도 뽑을 가치가 있습니다.** 컴포넌트에서 **성격이 다른 일을 떼어낼 수 있으면** 훅으로 뽑습니다.
>
> **→ 두 곳에서 쓴다는 이유만으로 묶으면 오히려 나빠집니다.** 한쪽 요구사항이 달라질 때 훅 안에 **"이 경우엔 이렇게" 하는 조건이 계속 늘어납니다.**

**30초 버전** — "재사용이 아니라 '같이 바뀌는 것끼리' 묶는 게 기준입니다. 두 곳에서 쓴다는 이유만으로 묶으면 조건 분기가 늘어서 오히려 나빠집니다."

**꼬리 질문 대비**

**→ "직접 만든 훅 예시가 있나요?"** 루티너리의 **애니메이션 cleanup 훅**을 듭니다. **화면마다 따로 정리하던 걸 훅 하나로 통일**한 경우라, "같이 바뀌는 정리 로직을 모은 것"의 예로 맞습니다(→ Q5).

## 상태 설계

### Q9. 상태를 어디에 둘지 어떻게 정하나요?

**답변** `🌐 개념 정리`
> **→ 서버 상태, 전역 스토어, 로컬 세 단계로 나눕니다.**
>
> **→ ① 서버에서 온 것은 서버 상태입니다.** **React Query**처럼 받아온 데이터를 보관해주는 쪽에 맡깁니다. **전역 스토어에 복사하지 않습니다.**
>
> **→ ② 여러 화면이 공유하고, 화면을 벗어나도 살아야 하는 것은 전역 스토어입니다.**
>
> **→ ③ 나머지는 전부 로컬입니다.** 입력값, 열림/닫힘 같은 것들입니다.
>
> **→ 가장 흔한 실수는 ①을 ②에 복사하는 것입니다.** 그 순간 **같은 데이터가 두 곳에 생기고 둘을 계속 맞춰줘야 합니다.** **그게 대부분의 버그 원인**이 됩니다.

**▶ 내 경험** `📁 내 경험`
> **→ 루티너리에서 서버 데이터 복사를 걷어내고, 목록 갱신 때 저장을 3번에서 1번으로 줄였습니다.** 당시 **Zustand 스토어가 21개**까지 늘어난 상태였습니다.
>
> **→ 서버 데이터는 React Query 한 곳에만 둡니다.** 스토어로 복사하던 걸 걷어내서 **서버에서 온 건 React Query 한 곳만 들고 있게** 정리했습니다.
>
> **→ Zustand에서는 계산해서 쓸 수 있는 값을 저장하지 않게 바꿨습니다.** 루틴 목록이 원본 말고도 **정렬한 목록과 날짜별로 펼친 목록을 따로 저장**하고 있었습니다.
>
> **→ 그래서 목록 하나에 저장이 세 번 일어났습니다.** 그때마다 **화면이 다시 그려졌습니다.**
>
> **→ 원본만 두고 나머지는 계산으로 바꿨습니다.** **원본이 바뀔 때만 다시 계산**되게 해서 **저장을 한 번으로** 줄였습니다.

**⚠️ 표현 주의** — **"구독 범위를 좁혔다"고 말하지 마세요.**
코드를 보면 좁은 구독은 **원래 그 저장소의 기본 스타일**이었고, 본인이 옮긴 작업이 아닙니다.

**30초 버전** — "서버 데이터는 React Query, 여러 화면이 공유하는 건 전역 스토어, 나머지는 로컬입니다. 루티너리에서 스토어 21개 중 서버 데이터 복사를 걷어내고, 정렬·펼친 목록을 따로 저장하던 걸 계산으로 바꿔서 목록 갱신 때 저장을 3번에서 1번으로 줄였습니다."

**꼬리 질문 대비**

**→ "저장 구조를 바꾸면 기존 사용자 데이터는요?"** 스토어별로 **`version`과 `migrate`를 둬서** 저장 구조 변경에 대응했다고 답합니다.

**→ "구독 범위는 어떻게 관리했나요?"** 위 ⚠️처럼 좁은 구독은 **원래 있던 스타일**이라고 솔직히 말하고, 본인이 한 건 **서버 상태 분리와 파생 상태 제거**라고 선을 긋습니다.

### Q10. props drilling은 항상 나쁜가요?

**답변** `🌐 개념 정리`
> **→ 아닙니다. 2~3단계면 오히려 명시적이라 좋습니다.** **데이터 흐름이 코드에 그대로 보이니까요.**
>
> **→ 문제는 통과만 시킬 때입니다.** 중간 컴포넌트들이 **자기가 안 쓰는 props를 그냥 통과시키기만 할 때**입니다.
>
> **→ 그땐 Context나 컴포지션을 씁니다.** 컴포지션은 중간에서 넘기는 대신 **완성된 화면 조각을 children으로 끼워 넣는 방식**입니다.
>
> **→ 컴포지션을 먼저 봅니다.** **Context는 값이 하나 바뀌면 그걸 쓰는 컴포넌트가 전부 다시 그려지기 때문**입니다.

**30초 버전** — "2~3단계면 흐름이 보여서 오히려 좋습니다. 안 쓰는 props를 통과만 시킬 때 문제고, 그땐 Context보다 컴포지션을 먼저 봅니다. Context는 값이 바뀌면 쓰는 쪽이 전부 다시 그려지니까요."

**꼬리 질문 대비**

**→ "Context 리렌더는 어떻게 줄이나요?"** **자주 바뀌는 값과 잘 안 바뀌는 값을 Context로 나누거나**, **일부만 구독할 수 있는 상태 라이브러리(Zustand 등)** 로 옮깁니다.

## 성능

### Q11. 리스트 성능은 어떻게 개선하나요?

**답변** `🌐 개념 정리`
> **→ key, memo, 가상화, 데이터 구조 순서로 봅니다.**
>
> **→ ① 안정적인 key입니다.** **이게 없으면 나머지가 다 무의미합니다.**
>
> **→ ② 아이템에 memo를 걸고 props가 매번 새로 만들어지지 않게 합니다.** 콜백을 그 자리에서 만들어 넘기면 **매번 다른 값으로 보여서 memo가 소용없어집니다.**
>
> **→ ③ 가상화입니다.** 목록 전체가 아니라 **화면에 보이는 것만 그리는 방식**입니다. 웹은 virtual 계열, RN은 FlatList/FlashList입니다.
>
> **→ ④ 그래도 안 되면 데이터 구조를 봅니다.** **그릴 때마다 정렬·필터를 새로 돌리고 있는 경우**가 많습니다.

**30초 버전** — "안정적인 key, 아이템 memo와 props 안정화, 보이는 것만 그리는 가상화, 마지막으로 렌더마다 정렬·필터를 다시 돌리는지 데이터 구조를 봅니다."

**꼬리 질문 대비**

**→ "④를 실제로 해본 적 있나요?"** 루티너리에서 **정렬·펼친 목록을 따로 저장하던 걸 원본이 바뀔 때만 계산**하게 바꾼 경험으로 연결합니다(→ Q9).

### Q12. 코드 스플리팅은 어떻게 적용했나요?

**답변** `🌐 개념 정리`
> **→ 라우트 단위가 기본이고, 그다음이 무거운 라이브러리를 쓰는 지점입니다.**
>
> **→ 큰 의존성은 그 화면에 진입할 때 불러옵니다.** **차트나 에디터처럼 특정 화면에서만 필요한** 경우입니다.

**▶ 내 경험** `📁 내 경험`
> **→ 메이크델타에서는 번들을 43% 줄였고, 루티너리에서는 해봤다가 측정 끝에 되돌렸습니다.**
>
> **→ 메이크델타 트레이딩 차트 웹뷰입니다.** **Vite의 manualChunks로 대형 라이브러리를 개별 청크로 분리**하고 **React.lazy + Suspense로 지연 로딩**해서 **번들 크기를 43% 줄였습니다.**
>
> **→ 루티너리에서는 같은 발상을 앱에 적용했습니다.** **화면 62개를 앱 시작할 때 한꺼번에 불러오지 않도록** 바꿔봤습니다.
>
> **→ 측정 결과는 개선이었습니다.** 시작 단계마다 표시를 남기는 측정 스크립트로 **n=10 중앙값**을 비교했고, **Debug 빌드 기준** **Splash 초기화 24.4%, JS 총 로딩 21.8% 개선**됐습니다.
>
> **→ 그래도 나중에 되돌렸습니다.** 화면마다 로딩 처리가 붙으면서 **화면 전환할 때 한 번 깜빡이는 비용**이 시작 시간에서 얻는 것보다 크다고 봤습니다. **시작은 한 번이고 화면 전환은 매번**이니까요.
>
> **→ 측정 체계는 그대로 남겼습니다.**

**30초 버전** — "메이크델타에서는 manualChunks와 React.lazy로 번들을 43% 줄였습니다. 루티너리에서도 화면 62개를 지연 로딩해 Debug 기준 시작 시간이 개선됐지만, 화면 전환 깜빡임 비용이 더 커서 되돌리고 측정 체계만 남겼습니다."

**꼬리 질문 대비**

**→ "되돌릴 거면 왜 했나요?"** **측정해보기 전엔 몰랐던 비용**이었고, **프로덕션 지표를 보고 판단**했다고 답합니다. **"측정해보고 내 작업을 되돌렸다"** 가 핵심입니다.

**→ "Debug 빌드 수치를 믿을 수 있나요?"** 그래서 **프로덕션에서 시작 단계별 시간을 Amplitude로 보내는 telemetry**를 따로 만들었다고 잇습니다.

### Q13. 리렌더가 많은 걸 어떻게 찾나요?

**답변** `🌐 개념 정리`
> **→ 먼저 재현하고 측정합니다.** **눈으로 짐작하면 대부분 틀립니다.**
>
> **→ React DevTools Profiler로 봅니다.** **"왜 다시 그려졌는지" 기록을 켜고**, 화면이 갱신된 한 번 단위로 봅니다.
>
> **→ RN이면 네이티브 쪽 측정을 같이 봅니다.** **JS만 봐서는 원인이 안 보이는 경우**가 있어서요.

**30초 버전** — "짐작하지 않고 재현해서 Profiler로 '왜 다시 그려졌는지'를 봅니다. RN이면 네이티브 쪽 측정도 같이 봅니다."

**꼬리 질문 대비**

**→ "JS만 봐서 안 보였던 사례가 있나요?"** SharedValue 누수는 **JS가 아니라 Android Native Heap 계측으로** 확인했다고 연결합니다(→ Q5).

**포인트** — "추측 → 수정"이 아니라 **"측정 → 수정 → 재측정"** 순서로 말하면 신뢰도가 올라갑니다.

### Q14. 제어 컴포넌트와 비제어 컴포넌트의 차이는?

**답변** `🌐 개념 정리`
> **→ 값의 출처가 React 상태냐, DOM이냐의 차이입니다.**
>
> **→ 제어는 즉시 검증·형식 교정이 됩니다.** 대신 **한 글자 칠 때마다 다시 그려집니다.**
>
> **→ 비제어는 입력이 가볍습니다.** **필요할 때만 ref로 값을 꺼내 읽기** 때문입니다.
>
> **→ 입력칸이 많은 폼은 비제어 방식이 보통 유리합니다.** **비제어 방식 폼 라이브러리**를 씁니다.

**30초 버전** — "값을 React 상태가 들고 있으면 제어, DOM이 들고 있으면 비제어입니다. 제어는 즉시 검증이 되고, 비제어는 입력이 가벼워서 큰 폼에 유리합니다."

**꼬리 질문 대비**

**→ "비제어 방식 폼 라이브러리라면?"** React Hook Form처럼 **ref로 값을 모아서 입력마다 리렌더하지 않는** 방식을 예로 듭니다.

### Q15. Error Boundary는 무엇을 못 잡나요?

**답변** `🌐 개념 정리`
> **→ 이벤트 핸들러, 비동기 코드, SSR, 그리고 Error Boundary 자기 자신의 에러는 못 잡습니다.**
>
> **→ 잡는 건 렌더 중 에러뿐입니다.** **화면을 그리는 도중에 난 에러만** 잡습니다.
>
> **→ 그래서 실무에서는 따로 받습니다.** **비동기 에러는 데이터 가져오는 쪽에서**, **그물에 안 걸린 나머지는 Sentry 같은 에러 수집 도구에서** 받습니다.

**▶ 내 경험** — [ Sentry로 실제 잡았던 에러 한 건 ]

**30초 버전** — "렌더 중 에러만 잡고, 이벤트 핸들러·비동기·SSR·자기 자신의 에러는 못 잡습니다. 그래서 비동기는 데이터 계층에서, 나머지는 Sentry 같은 수집 도구로 받습니다."

**꼬리 질문 대비**

**→ "Error Boundary는 함수 컴포넌트로 만들 수 있나요?"** 아직 **클래스 컴포넌트의 `componentDidCatch`·`getDerivedStateFromError`가 필요**합니다. 보통 **react-error-boundary** 같은 라이브러리로 감쌉니다.

### Q16. Strict Mode에서 이펙트가 두 번 실행되는 이유는?

**답변** `🌐 개념 정리`
> **→ 개발 모드에서 클린업이 제대로 되어 있는지 강제로 검사하기 위해서입니다.**
>
> **→ 띄웠다 없앴다 다시 띄우는 걸 흉내냅니다.** 클린업이 없으면 **구독이 두 개 생기는 식으로 바로 드러납니다.**
>
> **→ 프로덕션에서는 한 번만 실행됩니다.**
>
> **→ 여기서 문제가 보이면 원래 있던 버그입니다.** **Strict Mode 탓이 아니라 원래 있던 버그가 드러난 것**입니다.

**30초 버전** — "개발 모드에서 마운트·언마운트·재마운트를 흉내내서 클린업 누락을 드러내려는 겁니다. 프로덕션은 한 번이고, 여기서 터지면 원래 있던 버그입니다."

**꼬리 질문 대비**

**→ "요청이 두 번 나가는 건 어떻게 하나요?"** Strict Mode를 끄는 게 아니라 **클린업에서 요청을 취소(AbortController)하거나 중복을 무시**하게 고칩니다.
