# 면접 질문 — AI 개발 하네스 (루티너리)

> 근거: `.claude/settings.json`, `.claude/scripts/*.sh`, `.claude/agents/*.md`, `.claude/rules/*.md`
> 이력서 항목: "AI 개발 하네스 구축 및 팀 배포"

---

## A. 검증 계층 설계 (Hooks)

1. `PostToolUse` 훅에서 ESLint를 돌리는데 `--fix`를 붙이고 `|| true`로 실패를 삼킵니다. 자동 수정이 코드 의미를 바꿔버리는 경우(예: 미사용 import 제거가 side-effect import였던 경우)는 어떻게 방어하나요?

2. `post-edit.sh`가 `exit 0`으로 항상 성공을 반환합니다. ESLint가 파싱조차 못 하는 깨진 코드를 저장했을 때 이 훅이 알려주지 못하는데, 의도한 설계인가요?

3. `Stop` 훅의 타임아웃이 120초입니다. `tsc --noEmit`이 이 프로젝트(1,746개 파일)에서 실제로 얼마나 걸리나요? 타임아웃을 넘기면 어떤 일이 벌어지나요?

4. 세션 마커를 `/tmp/claude-edited-${sid}.txt`에 append 합니다. 같은 세션에서 같은 파일을 20번 편집하면 20줄이 쌓이는데, `sort -u`로 중복을 제거하는 이유와 비용은?

5. 마커 파일이 `/tmp`에 있습니다. macOS 재부팅이나 `/tmp` 정리로 파일이 사라지면 Stop 훅이 조용히 `exit 0` 합니다. 이 실패 모드를 알고 있었나요? 어떻게 개선하겠습니까?

6. `stop-tsc.sh`가 편집 파일 전체가 아니라 `grep -F "${rel}("` 로 tsc 출력을 필터링합니다. 파일명이 다른 파일의 부분 문자열인 경우(`Button.tsx` vs `IconButton.tsx`) 오탐이 발생하지 않나요?

7. 위 grep은 `경로(` 패턴을 찾습니다. tsc가 상대경로가 아닌 절대경로로 출력하는 환경에서는 매칭이 실패할 텐데, 어떻게 보장했나요?

8. 신규 코드에만 게이트를 적용하려고 "이번 세션에서 편집한 파일"을 기준으로 삼았습니다. 왜 `git diff`가 아니라 세션 마커였나요? 두 방식의 트레이드오프는?

9. 이미 에러가 있던 파일을 수정하면, 내가 만들지 않은 기존 에러까지 차단 사유가 됩니다. 이 경우 개발자 경험이 어떻게 되나요?

10. baseline 에러가 367개라고 스크립트 주석에 적혀 있습니다. 이 숫자는 언제 측정한 것이고, 시간이 지나 늘어나면 어떻게 관리하나요?

11. 차단(`decision: "block"`) 시 에러 전문을 `reason`에 넣습니다. 에러가 100개면 컨텍스트를 크게 잡아먹는데, 상한을 두지 않은 이유는?

12. Stop 훅은 `tsc`를 **매번 전체** 실행합니다. incremental 빌드(`tsconfig.tsbuildinfo`)를 쓰지 않은 이유가 있나요?

13. 훅이 `jq`에 의존합니다. `jq`가 없는 팀원 환경에서는 어떻게 동작하나요? 설치 안내는 어디에 있나요?

14. ESLint 훅은 non-blocking, 타입 검증은 blocking으로 나눴습니다. 이 비대칭을 선택한 근거는?

15. `Write|Edit` matcher만 걸려 있습니다. `MultiEdit`나 다른 편집 경로로 만들어진 변경은 마커에 안 잡히지 않나요?

## B. 서브에이전트 설계

16. 세 에이전트(`rn-reviewer`, `ios-build-fixer`, `android-build-fixer`) 모두 `tools: Read, Grep, Glob, Bash`로 **Edit/Write를 제외**했습니다. Bash는 남겨뒀는데, Bash로 파일을 수정할 수 있다는 점은 어떻게 통제하나요?

17. "자동 수정 권한 제거, 진단·보고로 역할 한정"이 설계 원칙인데, 왜 자동 수정을 허용하지 않았나요? 실제로 문제가 됐던 사례가 있었나요?

18. 세 에이전트 모두 `model: sonnet`입니다. 더 큰 모델을 쓰지 않은 기준은? 비용과 정확도를 어떻게 저울질했나요?

19. `rn-reviewer`가 잡는 최우선 항목이 "Reanimated worklet의 colors Proxy 캡처"입니다. 이 크래시가 왜 앱 **전체** 테마를 undefined로 만드나요? 원인을 JS 엔진 수준에서 설명해 주세요.

20. 위 패턴에서 `colors.redcc`를 worklet 밖에서 미리 뽑으면 해결되는 이유는? Reanimated의 worklet 직렬화가 Proxy를 만나면 어떻게 되나요?

21. 이 규칙을 정규식/문자열 매칭으로 검출한다면 오탐이 많을 텐데(`colors`가 지역변수인 경우 등), 어떻게 정확도를 확보했나요?

22. `useDerivedValue`는 "worklet인 경우"만 검사하라고 되어 있습니다. worklet 여부를 정적으로 어떻게 판별하나요?

23. 빌드 진단 에이전트가 "빌드 재실행은 3분(Android)/5분(iOS) 이상 소요되므로 최대한 피하라"고 지시합니다. 그럼에도 재실행이 필요한 경우의 판단 기준은?

24. 긴 Gradle/Xcode 로그를 "격리된 컨텍스트에서 분석해 원인만 반환"하는 게 핵심 가치입니다. 서브에이전트를 안 쓰고 메인에서 처리하면 구체적으로 무엇이 나빠지나요?

25. 에이전트가 잘못된 진단을 내놨을 때, 메인 Claude가 그걸 그대로 믿고 엉뚱한 수정을 하는 위험은 어떻게 줄였나요?

26. `android-build-fixer`가 알려진 패턴(daemon 죽음, duplicate class, Kotlin 버전 매트릭스 등)을 하드코딩하고 있습니다. 새로운 유형의 에러는 어떻게 커버되나요? 규칙은 누가 추가하나요?

27. 세 에이전트의 `description`이 매우 깁니다. 이 필드가 실제로 에이전트 자동 선택에 어떻게 쓰이는지 이해하고 작성한 건가요?

28. 리뷰 에이전트가 "300줄 초과 컴포넌트"를 지적하는데, 실제 코드베이스에는 1,515줄짜리 `DeveloperScreen.tsx`가 있습니다. 이런 기존 위반은 어떻게 다뤘나요?

## C. 규칙(rules)과 팀 운영

29. `code-rules.md`에 "components.md의 Functions → Components 순서는 **사람 컨벤션일 뿐**, eslint는 알파벳순으로만 정렬한다"고 명시했습니다. 도구가 강제하지 못하는 규칙을 문서에 남긴 이유는?

30. 사람 컨벤션과 ESLint 자동 정렬이 충돌하면 어느 쪽이 이기나요? 팀원이 헷갈리지 않게 어떻게 했나요?

31. `no-restricted-imports`로 `../`를 금지하고 `~/` 별칭을 강제합니다. 같은 폴더 `./`만 허용한 근거는?

32. `.claude/rules/*.md`에 `paths:` frontmatter로 적용 범위를 지정했습니다. 이게 실제로 어떻게 동작하나요? 파일을 열 때 자동 로드되나요?

33. 규칙 파일이 8개입니다. 컨텍스트 예산을 얼마나 차지하고, 어떻게 관리했나요?

34. `code-review.md`가 P1~P5 태그를 GitHub 액션(Request changes / Comment / Approve)에 매핑합니다. `rn-reviewer`의 심각도가 이 태그로 매핑된다고 했는데, 자동 리뷰가 잘못 P1을 달면 어떻게 되나요?

35. `settings.json`의 `deny`에 `git push --force`, `git reset --hard`가 있습니다. 그런데 `git push --force-with-lease`는 막히지 않습니다. 의도한 건가요?

36. deny 목록에 `rm -rf /*` 같은 패턴이 있는데, `rm -rf ./src` 처럼 실제로 위험한 상대경로는 안 막힙니다. 이 방어의 실효성을 어떻게 평가하나요?

37. 브랜치 보호는 "GitHub branch protection으로 강제, Claude 설정 아님"이라고 명시했습니다. 왜 이 구분을 문서에 강조했나요?

38. 하네스를 **팀 전체에 배포**했다고 했습니다. 팀원이 이 훅들을 끄고 싶어하면 어떻게 하나요? opt-out 경로가 있나요?

39. "이후 다른 팀원들이 규칙을 추가하며 공동 운영"했다고 했습니다. 규칙 추가 시 리뷰 프로세스가 있었나요? 충돌하는 규칙이 들어온 적은?

40. 온보딩 문서를 작성하고 PR 리뷰를 거쳐 도입했다고 했는데, 도입 과정에서 나온 반대 의견이나 우려는 무엇이었나요?

41. 하네스 도입 전후로 실제 지표(리뷰 시간, 버그 수, PR 크기 등)가 개선됐나요? 측정했나요?

42. 하지 않았다면, 효과를 어떻게 확신했나요?

43. Linear·Figma MCP를 연동했습니다. MCP 서버 인증 토큰은 어떻게 관리했나요? `settings.local.json`과 `settings.json`을 어떻게 나눴나요?

44. Figma MCP로 "디자인 기반 구현 흐름"을 만들었다고 했는데, 실제로 디자인→코드 정확도는 어느 정도였나요? 사람이 손대야 하는 비율은?

45. 동일 하네스를 Codex 환경으로 포팅했다고 했습니다. Hooks·Subagents 개념이 다른 도구에서 1:1 대응되지 않을 텐데, 무엇을 포기했나요?

46. "특정 도구 종속성 제거"가 목적이었다면, 두 환경의 규칙이 갈라지는(drift) 문제는 어떻게 막았나요?

47. AI가 생성한 코드의 저작권·라이선스 이슈, 혹은 사내 코드가 외부로 나가는 문제에 대해 팀/회사 차원의 정책이 있었나요?

48. 하네스가 잘못된 코드를 통과시킨 사례가 있었나요? 그때 규칙을 어떻게 보강했나요?

49. 이 하네스를 지금 다시 만든다면 가장 크게 바꿀 부분은?

50. 하네스 자체의 테스트는 어떻게 했나요? 훅 스크립트가 깨졌는지 어떻게 감지하나요?
