### Q2. 백엔드가 없었다면 서버 쪽은 어떻게 했나요? (31:08)

**실제 답변** — "Firestore로 DB를 관리했고, 정합성 문제는 따로 폴더 관리를 했다. 데이터를 Async Storage에서 관리하고 업데이트할 때 확인하는 전략."

**문제점**
- **질문의 전제를 바로잡지 않았습니다.** 루티너리는 서버가 없던 게 아니라, **Firebase가 서버 대부분을 대신하고 꼭 필요한 기능만 별도 API 서버**를 쓰는 구조였습니다. 이 구조를 먼저 말해야 "서버 쪽은 어떻게"에 대한 답이 됩니다.
- **저장소 이름이 틀렸습니다.** 앱 로컬 저장소는 Async Storage가 아니라 **MMKV**입니다.
- "폴더 관리"는 무슨 뜻인지 전달이 안 됩니다. 실제로는 이력서에 있는 **위젯 동기화 설계**입니다.

**루티너리 서버 구성 — 코드 기준으로 다시 확인한 것**

| 영역 | 실제로 쓴 것 | 맡은 일 |
|---|---|---|
| 인증 | **Firebase Auth** (Google·Facebook 로그인) | 로그인·계정 |
| 메인 데이터 | **Firestore** — 루틴·기록·체크리스트·친구·챌린지 등 도메인별 서비스 파일 21개(`src/database/`) | 앱이 서버를 거치지 않고 DB에 바로 읽고 씀 |
| 별도 API 서버 | **REST API** — Axios 인스턴스를 용도별 5개로 분리 (메인 30초, 채팅·구독 10초 타임아웃) | 채팅·웹 구독·기프트 코드·푸시·위치처럼 **서버에서 처리해야 하는 기능만** |
| 결제 | **Adapty** + 스토어 결제 | 구독 상태 관리 |
| 운영 | **Remote Config**(기능 플래그) · Analytics · Crashlytics · Sentry | 배포 없이 기능 켜고 끄기, 장애 추적 |
| 앱 로컬 | **Zustand + MMKV** (persist) · iOS App Groups / Android 공유 저장소 | 오프라인에서도 바로 뜨는 화면, 위젯과 데이터 공유 |

**다시 쓴 답변** `📁 내 경험`
> 서버가 아예 없던 건 아니고, **서버 대부분을 Firebase가 대신하는 구조**였습니다.
> 로그인은 Firebase Auth, 루틴·기록 같은 핵심 데이터는 Firestore에 앱이 직접 읽고 썼습니다.
> 채팅·웹 구독·기프트 코드·푸시처럼 **서버에서 검증해야 하는 기능만 별도 API 서버**로 뺐고, 앱에서는 용도별로 API 클라이언트를 나눠 타임아웃을 따로 걸었습니다.
>
> 대신 앱이 할 일이 많았습니다. 루틴 앱은 오프라인에서도 바로 열려야 해서, **기기 저장소(MMKV)에 먼저 저장하고 Firestore로 올리는 로컬 우선 구조**였습니다.
> 서버에서 받는 데이터는 React Query가 맡고, 앱 안에서만 쓰는 상태는 Zustand가 맡도록 역할을 나눴습니다.
>
> 정합성이 제일 어려웠던 곳은 **위젯**입니다. 앱과 홈 화면 위젯이 같은 루틴을 동시에 고칠 수 있었거든요.
> 그래서 **항목마다 마지막으로 고친 시각을 같이 저장**하고, 둘이 부딪히면 더 늦게 고친 쪽을 살렸습니다.
> 흐름은 이렇습니다: 앱 스토어 변경 → 위젯과 같이 쓰는 저장소에 기록 → 앱을 열 때 합치기 → Firestore에 순서대로 반영.

**30초 버전** — "Firebase가 서버 대부분을 맡고, 채팅·결제·푸시처럼 서버 검증이 필요한 것만 별도 API 서버였습니다. 그래서 앱이 로컬에 먼저 저장하고 Firestore로 올리는 구조였고, 앱과 위젯이 동시에 고치는 충돌은 수정 시각으로 풀었습니다."

**꼬리 질문 대비**
- **"클라이언트가 DB에 직접 쓰면 보안은요?"** → 결제·기프트처럼 **클라이언트를 믿으면 안 되는 일은 API 서버로 보냈다**는 점을 먼저 말합니다. Firestore 쪽은 보안 규칙으로 로그인한 본인 문서만 접근하게 막는 게 원칙인데, 규칙 파일을 직접 고쳤는지는 기억나는 만큼만 말하세요.
- **"API 서버는 직접 만들었나요?"** → 서버 코드를 짠 건 아니라고 분명히 말하고, **앱 쪽 API 계층(인스턴스 분리·타임아웃·에러 처리)**과 Firestore 서비스 계층을 맡았다고 답합니다. 서버 경험은 Q3처럼 개인 프로젝트의 Supabase로 잇습니다.

> ① **도구 권한에서 막습니다.** 루티너리 하네스에서 `git push --force`, `git reset --hard` 같은 **되돌릴 수 없는 명령 9개를 차단 목록**에 넣었습니다.
> 빌드 진단 에이전트는 아예 **파일 수정 권한을 뺐습니다.** 원인만 보고하고, 고치는 판단은 사람이 합니다.
> ② **명령을 실행하기 직전에 검사합니다.** 훅으로 실행할 명령 문자열을 보고 push가 들어 있으면 거절합니다.
> ③ 말씀하신 것처럼 별칭이나 스크립트로 **우회할 수 있으니, 결국 push할 능력 자체를 없앱니다.**
> 에이전트가 도는 환경에는 **원격 저장소에 쓸 수 있는 인증 키를 넣지 않습니다.** 명령을 아무리 바꿔도 권한이 없으면 실패합니다.
> ④ 마지막으로 **서버 쪽에서** 브랜치 보호를 걸어 사람 승인 없이는 main에 못 들어가게 합니다.
>
> 원칙은 **"에이전트가 스스로 바꿀 수 없는 층에서 막는다"** 입니다.

**왜 겹겹이 막나** `🌐` — 쉬운 비유

| 층 | 비유 | 뚫리는 경우 |
|---|---|---|
| 규칙 문서 ("push 하지 마") | 문에 붙인 "출입 금지" 종이 | AI가 잊거나 무시하면 끝 |
| 명령 차단 목록 · 훅 | 문 앞 경비원이 이름 확인 | `git` 대신 스크립트 파일로 실행하면 이름이 달라 통과 |
| 인증 키 제거 | **열쇠 자체를 안 줌** | 어떤 방법으로도 못 열음 |
| 서버 브랜치 보호 | 금고 안쪽 잠금 | 사람 승인 없으면 불가 |

## 3. LLM의 원리

### Q14. 입력 텍스트가 토큰이 되고, 모델을 거쳐 출력 토큰으로 나오는 사이에 무슨 일이? 토큰은 문자열과 뭐가 다른가요? (52:43 · 53:44) ❌

**실제 답변** — "LangChain으로 설명하는 게 맞나 싶은데" → "왜 토큰이라고 부를까요?" → **"그 부분은 모르겠습니다."**

**평가** — 면접관이 "관심 가져 보면 재밌다"로 넘겼습니다. AI 챗 앱 포지션에서 **기본기로 보는 질문**입니다.
LangChain은 LLM을 **바깥에서 감싸서 쓰는 도구**라 이 질문과는 층이 다릅니다.

**개념 정리** `🌐` — 쉬운 말로

**① 토큰이란** — 모델이 읽는 **글자 조각**입니다.
컴퓨터는 글자를 그대로 이해하지 못하니 문장을 조각으로 자르고, 조각마다 **번호**를 붙입니다.
조각은 글자 하나일 수도, 단어 하나일 수도, 단어의 일부일 수도 있습니다.

```
"안녕하세요 반갑습니다"
 → ["안녕", "하세요", " 반", "갑", "습니다"]   ← 조각으로 자르기 (토큰화)
 → [15921, 8820, 1033, 4471, 2210]             ← 번호로 바꾸기
```

**왜 문자열이 아니라 토큰인가**
- 글자 하나씩이면 너무 길어지고, 단어 단위면 처음 보는 단어를 못 다룹니다. **그 중간**이 토큰입니다.
- 모델이 한 번에 볼 수 있는 길이(**컨텍스트 창**)와 **요금**이 전부 토큰 수로 계산됩니다.
- 한국어는 영어보다 같은 뜻에 토큰이 더 많이 드는 편입니다. 그래서 **같은 대화도 비용이 더 나올 수 있습니다.**

**② 모델 안에서 일어나는 일**

```
입력 토큰 번호들
  → 각 번호를 "의미를 담은 숫자 묶음"으로 바꿈 (임베딩)
  → 여러 층을 거치며 "어떤 토큰이 어떤 토큰과 관련 있는지" 계산 (어텐션)
  → 다음에 올 토큰 후보마다 확률을 냄  예: "반"이 40%, "좋"이 25% …
  → 그중 하나를 고름 (temperature가 높을수록 덜 뻔한 걸 고름)
  → 고른 토큰을 입력 끝에 붙이고 → 처음부터 다시 → 끝 토큰이 나올 때까지 반복
  → 나온 번호들을 다시 글자로 바꿈
```

**핵심은 한 줄입니다 — "LLM은 다음 토큰 하나를 맞히는 일을 계속 반복한다."**
그래서 답이 **한 번에 오지 않고 한 조각씩** 옵니다. 이게 Q20 스트리밍의 이유입니다.

**이렇게 답하세요**
> 토큰은 모델이 읽는 글자 조각이고, 조각마다 번호가 붙습니다. 모델은 숫자만 다루니까요.
> 모델은 입력 토큰들을 보고 **다음에 올 토큰의 확률**을 계산해서 하나를 고르고, 그걸 입력에 붙여 다시 계산하는 걸 반복합니다.
> 그래서 응답이 조각조각 오고, 컨텍스트 길이와 비용도 토큰 수로 정해집니다.
> 앱 입장에서는 **한 조각씩 오는 응답을 어떻게 끊김 없이 그리느냐**가 과제가 됩니다.

### Q24. 어느 날 모든 에이전트가 스트리밍 리렌더 처리를 이상하게 짜기 시작했다. 알고 보니 모델 버전이 바뀌었다. 원인은? LLM은 왜 그렇게 많은 질문에 답할 수 있나? (1:12:45 · 1:14:29)

**실제 답변** — "React 19 기준인데 14처럼 낮은 버전을 참고하게 만들었다면 그렇게 되지 않을까." / "많은 질문을 통해 터득하고 하나씩 처리하면서 나아질 것."

**평가** — 첫 답은 **방향이 맞았습니다.** 두 번째 답이 막연했습니다.

**개념 정리** `🌐`
> LLM은 **학습한 글에서 본 패턴**으로 답합니다. 코드를 "이해"한다기보다, 수많은 코드에서 **다음에 올 법한 코드를 예측**하는 겁니다.
> 그래서 **어떤 데이터로 학습했느냐**에 따라 습관이 달라집니다.
> 모델 버전이 바뀌면 학습 데이터와 가중치가 바뀌니, 예전 버전 React 방식처럼 **새 렌더링 최적화를 모르는 코드**를 더 자주 낼 수 있습니다.
>
> 답할 수 있는 이유는 두 단계입니다.
> ① 엄청난 양의 글을 읽으며 **다음 토큰 맞히기**를 연습합니다. 이 과정에서 문법·지식·코드 패턴이 숫자로 들어갑니다.
> ② 그다음 **사람이 좋은 답을 고르는 방식으로 추가 학습**해서, 질문에 도움 되는 답을 하도록 다듬습니다.

**이렇게 답하세요** — 경험과 연결해서 대비책까지 말하세요. `📁`
> 모델은 학습한 코드의 패턴으로 답하니, 버전이 바뀌면 습관도 바뀝니다.
> 그래서 저는 **모델이 아니라 검사로 품질을 지킵니다.**
> 루티너리에서 실제로 났던 크래시 패턴을 리뷰 에이전트 검사 항목으로 넣은 것도, **어떤 모델이 짜든 같은 기준으로 걸러지게** 하려는 것이었습니다.
> 스트리밍이라면 "토큰 100개를 받는 동안 메시지 목록이 몇 번 그려지는지"를 세는 테스트를 두면, 모델이 바뀌어도 바로 잡힙니다.
> 그리고 운영에서는 **모델 버전을 고정**해두고, 바꿀 때는 이런 검사를 통과한 뒤에 바꿉니다.

### Q16. OTA(CodePush) 운영 — 급히 되돌린 경험, 잘못된 번들이 나갔을 때, 되돌려도 바로 적용이 안 된다면, CodePush 자체가 고장 난다면 (55:42 ~ 1:00:30) ❌

- CodePush는 → "App Center 끝나면서 없어졌고… 누가 만든 게 있어서 그걸로. 서버로 띄우지는 않았다"
- 급히 되돌린 경험 → "입사 초기, 10년 차 분 실수로 스테이징과 프로덕션 구분이 안 돼서 스테이징이 배포됐다"
- 잘못된 번들이 나가면 → "CodePush를 지울 수 있다. 버전 1이면 버전 2를 배포하고, 2 이상이면 지워서 돌린다"
- 바로 적용이 안 되는데? CodePush가 고장 나면? → **"설계할 때 고려했어야 했는데, 많이 배워간다."**

**문제점**
- **이력서에 "자체 CodePush 배포 인프라"** 가 있는데 "서버 안 띄웠다, 남이 만든 것"으로 들렸습니다. → 위험 발언 2번
- 스테이징 사고는 면접관이 "그럼 프로덕션엔 영향 없었던 거죠?"로 **반대로 이해**했습니다. 무엇이 어디로 나갔는지 한 문장으로 말하세요.
- 마지막 두 질문이 **운영 담당자를 뽑는 이 포지션의 핵심**입니다.

**① 내가 만든 배포 구조** `📁 내 경험`
> App Center가 종료돼서, 앱 쪽은 오픈소스 CodePush 클라이언트를 그대로 쓰고
> **번들 파일과 배포 기록은 S3에 두고 CloudFront로 내려주는** 구조를 만들었습니다. 따로 돌아가는 서버는 없습니다.
>
> 만들다가 위험한 걸 하나 찾았습니다. 배포 기록을 **CloudFront 캐시에서 읽으면**, 캐시가 오래됐을 때 기록이 **비어 있는 걸로 읽힙니다.**
> 그 상태로 새 배포를 쓰면 **이전 배포 기록이 통째로 날아갑니다.**
> 그래서 읽을 때는 **항상 S3 원본**에서 읽고, 쓰기 전에 **기존 기록이 전부 들어 있는지 확인해서 하나라도 빠지면 쓰지 않게** 막았습니다.

**② 급히 되돌린 경험** — `[ ]`를 실제 사실로 채우세요.
> 입사 초기에 **스테이징용 번들이 실사용자에게 나간** 적이 있습니다. 스테이징과 프로덕션 배포 설정이 나뉘어 있지 않았던 게 원인이었습니다.
> **[ 어떻게 되돌렸는지 / 영향 범위 ]**
> 이후 **배포 대상을 환경별로 분리**했습니다. **[ 실제로 바꾼 것 ]**

**③ 되돌리기로 했는데 바로 적용되지 않는다** `🌐 개념 정리`

CodePush는 **앱이 서버에 "새 거 있어요?" 하고 물어볼 때만** 바뀝니다. 보통 앱을 켜거나 다시 열 때 묻습니다.

```
롤백 버튼을 누름
  → 앱을 다시 연 사람부터 하나씩 이전 번들을 받음
  → 이미 잘못된 번들을 받은 사람은 "다음에 물어볼 때까지" 그대로
  → 앱을 안 여는 사람은 계속 잘못된 번들
```

그래서 예상할 수 있는 상황은:
- **한동안 두 버전이 섞여 있습니다.** 크래시 리포트도 섞여서 들어옵니다.
- 서버로 가는 요청 모양이 바뀐 번들이었다면, **서버는 옛 모양과 새 모양을 둘 다 받아야** 합니다.
- **완전히 사라지기까지 며칠**이 걸릴 수 있습니다.

**④ 잘못된 번들 때문에 CodePush 자체가 고장 난다면** `🌐 개념 정리`

가장 무서운 경우입니다. **"업데이트를 받아오는 코드"도 번들 안에 있기 때문**입니다.

| 상황 | 결과 |
|---|---|
| 새 번들이 **켜자마자 죽음** | CodePush는 앱이 "정상으로 켜졌다"(`notifyAppReady`)는 신호를 보내기 전에 죽으면 **다음 실행 때 자동으로 이전 번들로 돌아갑니다** |
| 켜지긴 했는데 **업데이트 확인 코드가 망가짐** | 새 번들을 다시는 못 받습니다. **스토어에 새 버전을 올리는 것만** 답입니다 |
| 정상 신호를 보낸 **뒤에** 죽음 | 자동 롤백이 안 됩니다. 잘못된 번들에 갇힙니다 |

**막는 방법**
- **업데이트 확인 코드를 앱 시작 가장 앞, 가장 단순하게** 둡니다. 다른 기능이 망가져도 이건 돌아가게요.
- "정상으로 켜졌다" 신호는 **핵심 화면이 실제로 뜬 다음에** 보냅니다. 그래야 자동 롤백이 넓게 작동합니다.
- **일부 사용자에게만 먼저** 내보냅니다(단계적 배포). 크래시가 늘면 멈춥니다.
- 네이티브 코드가 바뀐 배포는 **대상 앱 버전을 지정**해서 맞지 않는 앱에는 안 가게 합니다.
- 최악을 대비해 **스토어 긴급 배포 경로**(빌드 자동화)를 항상 살려둡니다. → 루티너리 Fastlane 자동화가 바로 이 역할입니다.

**이렇게 답하세요**
> 되돌려도 **앱이 다음에 업데이트를 확인할 때까지는** 잘못된 번들이 남습니다. 한동안 두 버전이 섞이니 서버도 둘 다 받을 수 있어야 합니다.
> CodePush 자체가 망가지면 OTA로는 못 고치고 **스토어 배포만 남습니다.** 그래서 미리 세 가지를 해둡니다.
> 업데이트 확인 코드는 앱 시작 맨 앞에 단순하게 두고, "정상 실행" 신호는 핵심 화면이 뜬 뒤에 보내서 자동 롤백이 걸리게 하고,

**평가** — Pusher에서 **"끊김"을 가장 큰 문제로 짚은 것은 정확합니다.** 해결책을 말하지 못한 게 아쉽습니다.

**개념 정리** `🌐` — 서버가 앱에 데이터를 보내는 방법들

| 방식 | 쉬운 비유 | 방향 | 쓰는 곳 |
|---|---|---|---|
| **폴링** | 1초마다 "온 거 있어요?" 하고 물어봄 | 앱 → 서버 반복 | 간단한 상태 확인 |
| **SSE** (Server-Sent Events) | 전화를 걸어두고 **상대만 계속 말함** | 서버 → 앱 한쪽 | **ChatGPT·Claude의 답변 스트리밍** |
| **WebSocket** | 전화를 걸어두고 **둘 다 말함** | 양쪽 | 채팅, 게임, Pusher |
| **웹훅** | 일이 생기면 **서버가 다른 서버에** 문자를 보냄 | 서버 → 서버 | 결제 완료 알림, Slack 알림 |

**SSE를 왜 AI 챗에서 많이 쓰나**
- LLM 답은 **서버가 일방적으로 조각조각** 보내기만 하면 됩니다. 양쪽 대화(WebSocket)까지 필요 없습니다.
- 일반 HTTP 위에서 돌아서 **설정이 단순**합니다.
- 브라우저는 끊기면 **알아서 다시 연결**하고, 마지막으로 받은 번호(`Last-Event-ID`)를 알려줘서 이어 받을 수 있습니다.
- 대신 React Native에는 기본 기능이 없어서 **라이브러리나 fetch 스트림으로** 받습니다.

**웹훅** `📁 내 경험`
> 루티너리에서 빌드가 끝나면 **Slack 웹훅으로 배포 상태를 자동 알림**하게 연결했습니다.
> 웹훅은 이렇게 "일이 끝났을 때 상대 서버에 알려주는" 방식이라, 결제 완료 같은 이벤트 처리에도 씁니다.

**Pusher 끊김 — 이렇게 답하세요** `📁 경험` + `🌐 개념`
> 페이히어에서 매장 앱과 고객 앱 사이 결제 이벤트를 Pusher로 주고받았습니다.
> 제일 걱정한 게 **끊김**이었습니다. 다시 연결하는 건 Pusher가 알아서 하지만, **끊겨 있는 동안 온 메시지는 다시 오지 않습니다.**
>
> 당시 완전히 해결하진 못했고, 지금 다시 한다면 이렇게 하겠습니다.
> ① 연결 상태 변화를 받아서, **다시 연결되면 서버에서 최신 상태를 한 번 받아옵니다.** 놓친 걸 메시지로 기다리지 않고 상태로 다시 맞춥니다.
> ② 메시지마다 **고유 번호**를 붙여서 같은 걸 두 번 받아도 한 번만 처리합니다.
> ③ 결제처럼 중요한 건 실시간 메시지만 믿지 않고 **서버 결과를 최종 기준**으로 둡니다.

**포인트** — "해결하지 못했다"로 끝내지 말고 **"지금이라면 이렇게"** 를 붙이세요. 이 세 가지는 AI 챗 스트리밍이 끊겼을 때도 똑같이 씁니다.

## 6. 스트리밍 응답과 React 렌더링 — AI 챗 앱의 핵심

### Q20. 응답이 스트리밍으로 오는데 앱이 갑자기 너무 느려진다. 무엇을 의심하나요? 한 글자씩 오면 React에서는 무슨 일이? (1:06:39 · 1:07:50)

**실제 답변** — "동작 반복을 하고 있는지, 진짜 기다리는지, LLM이 순차적으로 주는 것" → "한 글자씩 렌더링할 것 같다" → 줄이는 방법은 **"명칭이 기억이 안 난다… 죄송합니다."**

**평가** — "한 글자마다 다시 그린다"까지는 맞았습니다. **줄이는 방법**이 이 포지션에서 가장 중요한 답이었습니다.

**무슨 일이 일어나나** `🌐 개념 정리`

```
토큰 하나 도착 → setState → 화면 전체 다시 그리기
                    ↑ 1초에 30~50번
```

하나씩 보면 문제가 안 되는데, 겹치면 무거워집니다.

- **메시지 목록 전체**가 매번 다시 그려집니다. 새 메시지 하나만 바뀌었는데도요.
- 답변을 **마크다운으로 바꾸는 작업**이 토큰마다 처음부터 다시 돕니다. 답이 길수록 점점 느려집니다.
- **자동 스크롤**이 토큰마다 화면 크기를 다시 계산합니다.
- React Native라면 JS 스레드가 이걸로 꽉 차서 **터치·스크롤까지 밀립니다.**

**해결 방법** `🌐 개념 정리`

| 방법 | 쉬운 설명 |
|---|---|
| **모아서 그리기** | 토큰을 `useRef`에 쌓아두고, **화면 주기(약 16ms)마다 한 번** 또는 50ms마다 한 번만 state에 반영 |
| **지난 메시지는 다시 안 그리기** | 이미 끝난 메시지는 `React.memo`로 감싸서 **지금 받는 메시지 하나만** 다시 그림 |
| **급하지 않은 일은 뒤로** | 마크다운 변환 같은 무거운 일은 `useDeferredValue` · `startTransition`으로 입력·스크롤보다 뒤로 미룸 |
| **긴 목록은 보이는 것만** | 대화가 길면 화면에 보이는 메시지만 그림 (`FlatList` · 가상화) |
| **필요한 것만 구독** | 상태 관리 도구에서 메시지 전체가 아니라 **필요한 조각만 골라 구독** |

**이렇게 답하세요** `📁 내 경험` 연결
> 토큰마다 setState하면 1초에 수십 번 **메시지 목록 전체가 다시 그려지고**, 마크다운 변환도 매번 처음부터 돕니다.
> 저라면 세 가지를 하겠습니다.
> ① 토큰은 **ref에 모아두고 화면 주기마다 한 번만** 반영합니다.
> ② **끝난 메시지는 memo로 고정**해서 지금 받는 메시지 하나만 다시 그립니다.
> ③ 마크다운 변환처럼 무거운 건 **급하지 않은 업데이트로 미뤄서** 스크롤과 입력이 먼저 돌게 합니다.
>
> 메이크델타 차트에서 비슷한 문제를 겪었습니다. 시세가 계속 들어오는데 캔들을 DOM으로 그리면 버벅였습니다.
> 그래서 **React가 다시 그리지 않게 Canvas에 직접** 그렸고, 줌·이동 상태도 ref에 두었습니다.
> 루티너리에서도 Zustand에서 **필요한 값만 골라 구독**하게 바꿔서 다시 그리는 범위를 줄였습니다.

### Q21. React의 렌더링 시점을 우회하려고 DOM을 직접 조작해본 적 있나요? useRef는 왜 그렇게 동작할까요? (1:08:49 · 1:09:56) ❌

**실제 답변** — "해본 적은 있는데 맞는지는 모르겠다. 메이크델타 차트 코드를 useRef로 분리한 경험이 있다." → "useRef는 왜 그렇게 동작할까요?" → **답하지 못함**

**문제점** — 경험은 맞게 꺼냈습니다. **"왜"** 가 비었습니다.

**개념 정리** `🌐` — 쉬운 말로

`useRef`는 **React가 지켜보지 않는 상자**입니다.

| | `useState` | `useRef` |
|---|---|---|
| 값을 바꾸면 | React가 알아채고 **다시 그림** | React가 **모름**. 안 그림 |
| 다시 그려져도 값이 | 유지됨 | 유지됨 |
| 쓰는 곳 | 화면에 보여야 하는 값 | 화면과 상관없는 값, **DOM 요소 자체**, 타이머 번호, 쌓아두는 버퍼 |

**왜 그렇게 동작하나**
- `useState`의 값을 바꾸는 유일한 길은 `setState`이고, React는 **`setState`가 불렸을 때만** "다시 그려야겠다"고 판단합니다.
- `useRef`는 `{ current: 값 }` 모양의 **평범한 객체 하나**를 돌려줍니다. React는 처음 한 번 만들어서 컴포넌트 옆에 보관하고, **매번 같은 객체를 돌려줄 뿐**입니다.
- 그래서 `.current`를 바꾸는 건 **그냥 객체 속성을 바꾸는 것**이라 React가 알 길이 없습니다. 다시 그리지 않고, 값은 남습니다.

**이렇게 답하세요**
> useRef는 React가 처음 한 번 만든 **같은 객체를 매번 돌려줄 뿐**이고, 값을 바꿔도 setState를 부르지 않으니 React가 모릅니다.
> 그래서 다시 그리지 않으면서 값은 계속 남습니다.
> 메이크델타 차트에서 Canvas 요소와 줌 상태를 ref에 둔 것도 그래서입니다.
> 시세가 들어올 때마다 React가 다시 그리면 느려서, **React는 틀만 그리고 그 안의 그림은 Canvas에 직접** 그렸습니다.

### Q22. 리렌더는 왜 생기나요? 상태가 바뀔 때마다 무조건 리렌더해야 하나요? (1:10:17 · 1:10:33)

**실제 답변** — "상태가 바뀌어서" → "무조건은 아닐 것 같다. 세 개가 한 번에 바뀌면 1, 2, 3번 각각이 아니라 마지막에 한 번 바꾼다. 최근 업데이트에서 바뀌었다." → 어떻게 가능하냐 → "React 엔진이 이벤트 콜백에 모아놓고 한 번에."

**평가** — **배칭을 정확히 짚었습니다.** 이름만 붙이면 됩니다.

**개념 정리** `🌐`

**리렌더가 일어나는 경우** — 세 가지입니다.
1. 내 **state**가 바뀌었을 때
2. **부모**가 다시 그려졌을 때 (props가 같아도 기본적으로 같이 그려짐)
3. 구독하는 **context** 값이 바뀌었을 때

**무조건은 아닌 이유**
- **같은 값이면 건너뜁니다.** `setCount(3)`인데 이미 3이면 다시 그리지 않습니다.
- **자동 배칭** — React 18부터, 같은 순간에 일어난 `setState` 여러 개를 **모아서 한 번만** 그립니다.
  React 17까지는 클릭 이벤트 안에서만 모아줬고, `setTimeout`이나 `fetch` 응답 안에서는 하나하나 따로 그렸습니다.
- **`React.memo`** 를 쓰면 props가 같은 자식은 부모가 그려져도 건너뜁니다.

**어떻게 모으나 (쉬운 버전)**
`setState`를 부르면 React는 바로 그리지 않고 **"할 일 목록"에 적어만 둡니다.**
지금 돌고 있는 코드가 끝나면 목록을 한꺼번에 보고 **최종 값으로 한 번** 그립니다.

**이렇게 답하세요**
> 같은 값이면 건너뛰고, 여러 번 바뀌어도 React 18의 **자동 배칭**으로 한 번만 그립니다.
> setState는 바로 그리는 게 아니라 할 일로 적어두고, 지금 코드가 끝난 뒤 모아서 처리하기 때문입니다.
> 다만 **스트리밍처럼 토큰이 따로따로 다른 시점에 오면** 각각이 별개의 일이라 배칭으로 묶이지 않습니다.
> 그래서 Q20처럼 **직접 모아서** 반영해야 합니다.

**포인트** — 마지막 두 줄이 Q20과 Q22를 잇는 답입니다. 면접관이 노린 연결이 이것입니다.
