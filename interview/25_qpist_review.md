### Q2. 백엔드가 없었다면 서버 쪽은 어떻게 했나요? (31:08)

**실제 답변** — "Firestore로 DB를 관리했고, 정합성 문제는 따로 폴더 관리를 했다. 데이터를 Async Storage에서 관리하고 업데이트할 때 확인하는 전략."

**문제점**
- **질문의 전제를 바로잡지 않았습니다.** 루티너리는 서버가 없던 게 아니라, **Firebase가 서버 대부분을 대신하고 꼭 필요한 기능만 별도 API 서버**를 쓰는 구조였습니다. 이 구조를 먼저 말해야 "서버 쪽은 어떻게"에 대한 답이 됩니다.
- **저장소 이름이 틀렸습니다.** 앱 로컬 저장소는 Async Storage가 아니라 **MMKV**입니다.
- "폴더 관리"는 무슨 뜻인지 전달이 안 됩니다. 실제로는 이력서에 있는 **위젯 동기화 설계**입니다.

**루티너리 서버 구성 — 코드 기준으로 다시 확인한 것**

| 영역 | 실제로 쓴 것 | 맡은 일 |
|---|---|---|
| 인증 | **Firebase Auth** (Google·Facebook 로그인) | 로그인·계정 |
| 메인 데이터 | **Firestore** — 루틴·기록·체크리스트·친구·챌린지 등 도메인별 서비스 파일 21개(`src/database/`) | 앱이 서버를 거치지 않고 DB에 바로 읽고 씀 |
| 별도 API 서버 | **REST API** — Axios 인스턴스를 용도별 5개로 분리 (메인 30초, 채팅·구독 10초 타임아웃) | 채팅·웹 구독·기프트 코드·푸시·위치처럼 **서버에서 처리해야 하는 기능만** |
| 결제 | **Adapty** + 스토어 결제 | 구독 상태 관리 |
| 운영 | **Remote Config**(기능 플래그) · Analytics · Crashlytics · Sentry | 배포 없이 기능 켜고 끄기, 장애 추적 |
| 앱 로컬 | **Zustand + MMKV** (persist) · iOS App Groups / Android 공유 저장소 | 오프라인에서도 바로 뜨는 화면, 위젯과 데이터 공유 |

**다시 쓴 답변** `📁 내 경험`

**→ 서버가 없던 게 아니라, 서버 대부분을 Firebase가 대신하는 구조였습니다.**

**→ 로그인은 Firebase Auth, 핵심 데이터는 Firestore입니다.** 루틴·기록 같은 데이터는 **앱이 Firestore에 직접** 읽고 썼습니다.

**→ 서버 검증이 필요한 기능만 별도 API 서버로 뺐습니다.** 채팅·웹 구독·기프트 코드·푸시입니다. 앱에서는 **용도별로 API 클라이언트를 나눠 타임아웃을 따로** 걸었습니다.

**→ 대신 앱이 할 일이 많았습니다.** 루틴 앱은 오프라인에서도 바로 열려야 해서, **기기 저장소(MMKV)에 먼저 저장하고 Firestore로 올리는 로컬 우선 구조**였습니다. 서버 데이터는 **React Query**, 앱 안 상태는 **Zustand**로 역할을 나눴습니다.

**→ 정합성이 제일 어려운 곳은 위젯이었습니다.** 앱과 홈 화면 위젯이 같은 루틴을 동시에 고칠 수 있었습니다. 그래서 **항목마다 마지막으로 고친 시각을 저장**하고, 부딪히면 **더 늦게 고친 쪽**을 살렸습니다.

**→ 흐름은 네 단계입니다.** 앱 스토어 변경 → 위젯과 같이 쓰는 저장소에 기록 → 앱을 열 때 합치기 → Firestore에 순서대로 반영.

**→ "클라이언트가 DB에 직접 쓰면 보안은요?"** 결제·기프트처럼 **클라이언트를 믿으면 안 되는 일은 API 서버로 보냈다**는 점을 먼저 말합니다. Firestore 쪽은 보안 규칙으로 로그인한 본인 문서만 접근하게 막는 게 원칙인데, 규칙 파일을 직접 고쳤는지는 기억나는 만큼만 말하세요.

**→ "API 서버는 직접 만들었나요?"** 서버 코드를 짠 건 아니라고 분명히 말하고, **앱 쪽 API 계층(인스턴스 분리·타임아웃·에러 처리)**과 Firestore 서비스 계층을 맡았다고 답합니다. 서버 경험은 Q3처럼 개인 프로젝트의 Supabase로 잇습니다.

**→ 포인트.** "서버 의존도가 낮은 서비스였냐"는 다음 질문에도 이 답이 그대로 이어집니다.

### Q4. Peak Memory 958MB는 무엇이 차지하고 있었나요? (32:27) ❌

**실제 답변** — "어떤 것들이 차지했는지는 솔직히 잘 모른다. 애니메이션 관련 메모리였다. 978 정도… 298 정도로 줄었다."

- 숫자가 틀렸습니다. 이력서는 **958.5 → 297.4MB** 입니다.

**다시 쓴 답변** `📁 내 경험`

**→ 화면이 사라져도 정리되지 않던 Reanimated 애니메이션 값이 쌓인 게 원인이었습니다.**

**→ 958MB는 Xcode Organizer 숫자입니다.** Organizer는 **최고치만 보여주고 무엇이 차지했는지는 안 보여줍니다.** 그래서 내역은 기기에서 따로 쟀습니다.

**→ 화면을 드나들 때마다 메모리가 계단처럼 올라가고 안 내려갔습니다.** 원인은 **Reanimated 애니메이션 값**이었습니다. 화면이 사라져도 정리되지 않고 남아 있었습니다.

**→ 정리 안 되던 값은 24개였습니다.** 온보딩 슬라이드 14개, 타이머 원 6개, 비교 애니메이션 4개입니다.

**→ 공용 정리 훅으로 고쳤습니다.** 화면이 사라질 때 애니메이션을 한꺼번에 멈추는 훅입니다.

**→ 결과는 두 숫자입니다.** Android 네이티브 힙(Debug 빌드) 할당량 **101.9MB → 31.2MB**, 실사용자 Peak Memory(P95) **958.5MB → 297.4MB**입니다.

**→ "그럼 958 중에 애니메이션이 몇 MB였어요?"** **정확한 비율은 못 쟀다**고 솔직히 말합니다. 대신 고친 뒤 **같은 화면을 반복해 드나들어도 더는 올라가지 않는 것**으로 원인을 확인했다고 답합니다.

**→ "101.9 → 31.2와 958 → 297은 왜 숫자가 다르죠?"** 재는 대상이 다릅니다. 앞은 **Android Debug 빌드의 네이티브 힙 할당 총량**, 뒤는 **iOS 실사용자 기기에서 나온 최고 메모리의 P95(나쁜 쪽 상위 5%)** 입니다.

### Q14. 입력 텍스트가 토큰이 되고, 모델을 거쳐 출력 토큰으로 나오는 사이에 무슨 일이? 토큰은 문자열과 뭐가 다른가요? (52:43 · 53:44) ❌

**실제 답변** — "LangChain으로 설명하는 게 맞나 싶은데" → "왜 토큰이라고 부를까요?" → **"그 부분은 모르겠습니다."**

**평가** — 면접관이 "관심 가져 보면 재밌다"로 넘겼습니다. AI 챗 앱 포지션에서 **기본기로 보는 질문**입니다.
LangChain은 LLM을 **바깥에서 감싸서 쓰는 도구**라 이 질문과는 층이 다릅니다.

**개념 정리** `🌐` — 쉬운 말로

**① 토큰이란** — 모델이 읽는 **글자 조각**입니다.
컴퓨터는 글자를 그대로 이해하지 못하니 문장을 조각으로 자르고, 조각마다 **번호**를 붙입니다.
조각은 글자 하나일 수도, 단어 하나일 수도, 단어의 일부일 수도 있습니다.

```
"안녕하세요 반갑습니다"
 → ["안녕", "하세요", " 반", "갑", "습니다"]   ← 조각으로 자르기 (토큰화)
 → [15921, 8820, 1033, 4471, 2210]             ← 번호로 바꾸기
```

**왜 문자열이 아니라 토큰인가**
- 글자 하나씩이면 너무 길어지고, 단어 단위면 처음 보는 단어를 못 다룹니다. **그 중간**이 토큰입니다.
- 모델이 한 번에 볼 수 있는 길이(**컨텍스트 창**)와 **요금**이 전부 토큰 수로 계산됩니다.
- 한국어는 영어보다 같은 뜻에 토큰이 더 많이 드는 편입니다. 그래서 **같은 대화도 비용이 더 나올 수 있습니다.**

**② 모델 안에서 일어나는 일**

```
입력 토큰 번호들
  → 각 번호를 "의미를 담은 숫자 묶음"으로 바꿈 (임베딩)
  → 여러 층을 거치며 "어떤 토큰이 어떤 토큰과 관련 있는지" 계산 (어텐션)
  → 다음에 올 토큰 후보마다 확률을 냄  예: "반"이 40%, "좋"이 25% …
  → 그중 하나를 고름 (temperature가 높을수록 덜 뻔한 걸 고름)
  → 고른 토큰을 입력 끝에 붙이고 → 처음부터 다시 → 끝 토큰이 나올 때까지 반복
  → 나온 번호들을 다시 글자로 바꿈
```

**핵심은 한 줄입니다 — "LLM은 다음 토큰 하나를 맞히는 일을 계속 반복한다."**
그래서 답이 **한 번에 오지 않고 한 조각씩** 옵니다. 이게 Q20 스트리밍의 이유입니다.

**다시 쓴 답변** `🌐 개념 정리`

**→ 토큰은 번호가 붙은 글자 조각이고, 모델은 다음 토큰 하나를 고르는 일을 반복합니다.**

**→ 토큰은 모델이 읽는 글자 조각입니다.** 조각마다 **번호**가 붙습니다. 모델은 글자가 아니라 **숫자만** 다루니까요.

**→ 모델은 다음 토큰의 확률을 계산해서 하나를 고릅니다.** 그걸 **입력 끝에 붙여서 다시 계산**하고, 이걸 반복합니다.

**→ 그래서 응답이 조각조각 옵니다.** 한 번에 볼 수 있는 길이(컨텍스트)와 **비용도 토큰 수로** 정해집니다.

**→ 앱의 과제는 끊김 없이 그리는 것입니다.** **한 조각씩 오는 응답을 어떻게 끊김 없이 그리느냐**가 앱 입장의 과제입니다.

**→ "그럼 문자열 길이와 토큰 수는 같나요?"** 다릅니다. 조각이 글자 하나일 수도, 단어 하나일 수도 있고, **한국어는 같은 뜻에 토큰이 더 많이 드는 편**이라 비용이 더 나올 수 있다고 답합니다.

**→ "LangChain과는 무슨 관계죠?"** LangChain은 모델을 **바깥에서 감싸서 쓰는 도구**라 층이 다르다고 짧게 정리합니다.

### Q24. 어느 날 모든 에이전트가 스트리밍 리렌더 처리를 이상하게 짜기 시작했다. 알고 보니 모델 버전이 바뀌었다. 원인은? LLM은 왜 그렇게 많은 질문에 답할 수 있나? (1:12:45 · 1:14:29)

**① 내가 만든 배포 구조** `📁 내 경험`

**→ 오픈소스 CodePush 클라이언트에 S3·CloudFront를 붙여, 서버 없이 직접 만들었습니다.**

**→ App Center가 종료돼서 직접 만들었습니다.** 앱 쪽은 **오픈소스 CodePush 클라이언트를 그대로** 씁니다. **번들 파일과 배포 기록은 S3에 두고 CloudFront로 내려줍니다.** 따로 돌아가는 서버는 없습니다.

**→ 배포와 롤백은 버튼 하나입니다.** **GitHub Actions 워크플로**로 돌게 했습니다.

**② 급히 되돌린 경험** — `[ ]`를 실제 사실로 채우세요.

**→ 입사 초기에 스테이징용 번들이 실사용자에게 나간 적이 있습니다.**

**→ 원인은 배포 설정이었습니다.** 스테이징과 프로덕션 배포 설정이 **나뉘어 있지 않았습니다.**

**→ 되돌린 방법입니다.** **[ 어떻게 되돌렸는지 / 영향 범위 ]**

**→ 이후 배포 대상을 환경별로 분리했습니다.** **[ 실제로 바꾼 것 ]**

**③ 되돌리기로 했는데 바로 적용되지 않는다** `🌐 개념 정리`

CodePush는 **앱이 서버에 "새 거 있어요?" 하고 물어볼 때만** 바뀝니다. 보통 앱을 켜거나 다시 열 때 묻습니다.

```
롤백 버튼을 누름
  → 앱을 다시 연 사람부터 하나씩 이전 번들을 받음
  → 이미 잘못된 번들을 받은 사람은 "다음에 물어볼 때까지" 그대로
  → 앱을 안 여는 사람은 계속 잘못된 번들
```

그래서 예상할 수 있는 상황은:
- **한동안 두 버전이 섞여 있습니다.** 크래시 리포트도 섞여서 들어옵니다.
- 서버로 가는 요청 모양이 바뀐 번들이었다면, **서버는 옛 모양과 새 모양을 둘 다 받아야** 합니다.
- **완전히 사라지기까지 며칠**이 걸릴 수 있습니다.

**④ 잘못된 번들 때문에 CodePush 자체가 고장 난다면** `🌐 개념 정리`

가장 무서운 경우입니다. **"업데이트를 받아오는 코드"도 번들 안에 있기 때문**입니다.

| 상황 | 결과 |
|---|---|
| 새 번들이 **켜자마자 죽음** | CodePush는 앱이 "정상으로 켜졌다"(`notifyAppReady`)는 신호를 보내기 전에 죽으면 **다음 실행 때 자동으로 이전 번들로 돌아갑니다** |
| 켜지긴 했는데 **업데이트 확인 코드가 망가짐** | 새 번들을 다시는 못 받습니다. **스토어에 새 버전을 올리는 것만** 답입니다 |
| 정상 신호를 보낸 **뒤에** 죽음 | 자동 롤백이 안 됩니다. 잘못된 번들에 갇힙니다 |

**막는 방법**
- **업데이트 확인 코드를 앱 시작 가장 앞, 가장 단순하게** 둡니다. 다른 기능이 망가져도 이건 돌아가게요.
- "정상으로 켜졌다" 신호는 **핵심 화면이 실제로 뜬 다음에** 보냅니다. 그래야 자동 롤백이 넓게 작동합니다.
- **일부 사용자에게만 먼저** 내보냅니다(단계적 배포). 크래시가 늘면 멈춥니다.
- 네이티브 코드가 바뀐 배포는 **대상 앱 버전을 지정**해서 맞지 않는 앱에는 안 가게 합니다.
- 최악을 대비해 **스토어 긴급 배포 경로**(빌드 자동화)를 항상 살려둡니다. → 루티너리 Fastlane 자동화가 바로 이 역할입니다.

**다시 쓴 답변 (③·④ 합쳐서)** `🌐 개념 정리` + `📁 내 경험`

**→ 롤백해도 한동안 두 버전이 섞이고, CodePush가 망가지면 스토어 배포만 남으니 미리 대비해둡니다.**

**→ 되돌려도 바로 사라지지 않습니다.** **앱이 다음에 업데이트를 확인할 때까지는** 잘못된 번들이 남습니다. 한동안 두 버전이 섞이니, **서버도 둘 다 받을 수 있어야** 합니다.

**→ CodePush 자체가 망가지면 OTA로는 못 고칩니다.** **스토어 배포만 남습니다.** 그래서 미리 세 가지를 해둡니다.

**→ 첫째, 업데이트 확인 코드는 앱 시작 맨 앞에 단순하게 둡니다.**

**→ 둘째, "정상 실행" 신호는 핵심 화면이 뜬 뒤에 보냅니다.** 그래야 **자동 롤백**이 걸립니다.

**→ 셋째, 일부에게 먼저 내보냅니다.** 크래시가 늘면 **멈춥니다.**

**→ 마지막 보험은 스토어 긴급 배포입니다.** 그래서 루티너리에서는 **빌드·업로드를 명령 하나로** 돌게 해뒀습니다.

**→ "루티너리에서 롤백은 실제로 어떻게 했나요?"** 롤백 워크플로에서 **앱 버전과 문제 번들 버전을 고르면 그 번들을 비활성화**하는 방식이었다고 답합니다. 실제 답변의 "지워서 돌린다"를 이렇게 정확히 말합니다.

**→ "단계적 배포는 해봤나요?"** 배포 워크플로에 **롤아웃 비율과 강제 업데이트 여부를 고르는 입력**이 있었습니다. 실제로 비율을 낮춰 내보낸 적이 있는지는 **기억나는 만큼만** 말하세요.

### Q17. 새 서비스 출시 후 안드로이드에서 원인 모를 크래시가 난다. 어떤 순서로 보나요? (1:00:44) ❌

**→ "빌드 로그는 언제 보나요?"** 빌드 로그는 **출시 전, 빌드가 깨졌을 때** 봅니다. 사용자 폰에서 나는 크래시는 Crashlytics와 logcat이라고 선을 긋습니다.

**→ "ANR은 크래시와 뭐가 달라요?"** 앱이 죽지는 않지만 **메인 스레드가 막혀서 응답이 없는 상태**입니다. 그래서 스택보다 **"그 순간 메인 스레드가 무엇을 하고 있었나"** 를 봤다고 답합니다.

### Q20. 응답이 스트리밍으로 오는데 앱이 갑자기 너무 느려진다. 무엇을 의심하나요? 한 글자씩 오면 React에서는 무슨 일이? (1:06:39 · 1:07:50)

**무슨 일이 일어나나** `🌐 개념 정리`

```
토큰 하나 도착 → setState → 화면 전체 다시 그리기
                    ↑ 1초에 30~50번
```

하나씩 보면 문제가 안 되는데, 겹치면 무거워집니다.

- **메시지 목록 전체**가 매번 다시 그려집니다. 새 메시지 하나만 바뀌었는데도요.
- 답변을 **마크다운으로 바꾸는 작업**이 토큰마다 처음부터 다시 돕니다. 답이 길수록 점점 느려집니다.
- **자동 스크롤**이 토큰마다 화면 크기를 다시 계산합니다.
- React Native라면 JS 스레드가 이걸로 꽉 차서 **터치·스크롤까지 밀립니다.**

**해결 방법** `🌐 개념 정리`

| 방법 | 쉬운 설명 |
|---|---|
| **모아서 그리기** | 토큰을 `useRef`에 쌓아두고, **화면 주기(약 16ms)마다 한 번** 또는 50ms마다 한 번만 state에 반영 |

| **긴 목록은 보이는 것만** | 대화가 길면 화면에 보이는 메시지만 그림 (`FlatList` · 가상화) |
| **필요한 것만 구독** | 상태 관리 도구에서 메시지 전체가 아니라 **필요한 조각만 골라 구독** |

**다시 쓴 답변** `🌐 개념 정리` + `📁 내 경험`

**→ 토큰마다 setState해서 메시지 목록 전체가 1초에 수십 번 다시 그려지는 걸 의심합니다.** 마크다운 변환도 **매번 처음부터** 돕니다.

**→ ① 토큰은 ref에 모아두고, 화면 주기마다 한 번만 반영합니다.**

**→ ② 끝난 메시지는 memo로 고정합니다.** **지금 받는 메시지 하나만** 다시 그립니다.

**→ ③ 무거운 건 급하지 않은 업데이트로 미룹니다.** 마크다운 변환 같은 걸 미뤄서, **스크롤과 입력이 먼저** 돌게 합니다.

### Q21. React의 렌더링 시점을 우회하려고 DOM을 직접 조작해본 적 있나요? useRef는 왜 그렇게 동작할까요? (1:08:49 · 1:09:56) ❌

**실제 답변** — "해본 적은 있는데 맞는지는 모르겠다. 메이크델타 차트 코드를 useRef로 분리한 경험이 있다." → "useRef는 왜 그렇게 동작할까요?" → **답하지 못함**

**문제점** — 경험은 맞게 꺼냈습니다. **"왜"** 가 비었습니다.

**개념 정리** `🌐` — 쉬운 말로

`useRef`는 **React가 지켜보지 않는 상자**입니다.

| | `useState` | `useRef` |
|---|---|---|
| 값을 바꾸면 | React가 알아채고 **다시 그림** | React가 **모름**. 안 그림 |
| 다시 그려져도 값이 | 유지됨 | 유지됨 |
| 쓰는 곳 | 화면에 보여야 하는 값 | 화면과 상관없는 값, **DOM 요소 자체**, 타이머 번호, 쌓아두는 버퍼 |

**왜 그렇게 동작하나**
- `useState`의 값을 바꾸는 유일한 길은 `setState`이고, React는 **`setState`가 불렸을 때만** "다시 그려야겠다"고 판단합니다.
- `useRef`는 `{ current: 값 }` 모양의 **평범한 객체 하나**를 돌려줍니다. React는 처음 한 번 만들어서 컴포넌트 옆에 보관하고, **매번 같은 객체를 돌려줄 뿐**입니다.
- 그래서 `.current`를 바꾸는 건 **그냥 객체 속성을 바꾸는 것**이라 React가 알 길이 없습니다. 다시 그리지 않고, 값은 남습니다.

**다시 쓴 답변** `🌐 개념 정리` + `📁 내 경험`

**→ useRef는 React가 처음 만든 같은 객체를 매번 돌려줄 뿐이라, 바꿔도 React가 모르고 다시 그리지 않습니다.**

**→ `.current`를 바꿔도 setState를 부르지 않습니다.** 그래서 **React는 바뀐 줄 모릅니다.**

**→ 다시 그리지 않으면서, 값은 계속 남습니다.**

**→ 메이크델타 차트에서 Canvas 요소와 줌 상태를 ref에 둔 것도 그래서입니다.** 시세가 들어올 때마다 React가 다시 그리면 느려서, **React는 틀만 그리고 그 안의 그림은 Canvas에 직접** 그렸습니다.

**→ "그럼 ref 값을 화면에 보여주면요?"** 값이 바뀌어도 화면은 **다음에 다른 이유로 다시 그려질 때까지 옛 값**입니다. 그래서 화면에 보여야 하는 값은 state, 아닌 값은 ref로 나눈다고 답합니다.

**→ "DOM을 직접 만지면 위험하지 않나요?"** React가 관리하는 부분과 겹치면 서로 덮어씁니다. 그래서 **React는 Canvas 요소까지만**, 그 안의 그림은 직접 — 이렇게 **경계를 나눴다**고 답합니다.

### Q22. 리렌더는 왜 생기나요? 상태가 바뀔 때마다 무조건 리렌더해야 하나요? (1:10:17 · 1:10:33)

**실제 답변** — "상태가 바뀌어서" → "무조건은 아닐 것 같다. 세 개가 한 번에 바뀌면 1, 2, 3번 각각이 아니라 마지막에 한 번 바꾼다. 최근 업데이트에서 바뀌었다." → 어떻게 가능하냐 → "React 엔진이 이벤트 콜백에 모아놓고 한 번에."

**평가** — **배칭을 정확히 짚었습니다.** 이름만 붙이면 됩니다.

**개념 정리** `🌐`

**리렌더가 일어나는 경우** — 세 가지입니다.
1. 내 **state**가 바뀌었을 때
2. **부모**가 다시 그려졌을 때 (props가 같아도 기본적으로 같이 그려짐)
3. 구독하는 **context** 값이 바뀌었을 때

**무조건은 아닌 이유**
- **같은 값이면 건너뜁니다.** `setCount(3)`인데 이미 3이면 다시 그리지 않습니다.
- **자동 배칭** — React 18부터, 같은 순간에 일어난 `setState` 여러 개를 **모아서 한 번만** 그립니다.
  React 17까지는 클릭 이벤트 안에서만 모아줬고, `setTimeout`이나 `fetch` 응답 안에서는 하나하나 따로 그렸습니다.
- **`React.memo`** 를 쓰면 props가 같은 자식은 부모가 그려져도 건너뜁니다.

**어떻게 모으나 (쉬운 버전)**
`setState`를 부르면 React는 바로 그리지 않고 **"할 일 목록"에 적어만 둡니다.**
지금 돌고 있는 코드가 끝나면 목록을 한꺼번에 보고 **최종 값으로 한 번** 그립니다.

**다시 쓴 답변** `🌐 개념 정리`

**→ 무조건은 아닙니다. 같은 값이면 건너뛰고, 여러 번 바뀌어도 자동 배칭으로 한 번만 그립니다.**

**→ 자동 배칭은 React 18부터입니다.** 여러 번 바뀌어도 **한 번만** 그립니다.

**→ setState는 바로 그리지 않고 할 일로 적어둡니다.** 지금 코드가 **끝난 뒤 모아서** 처리합니다.

**→ 다만 스트리밍은 배칭으로 묶이지 않습니다.** **토큰이 따로따로 다른 시점에 오면**, 각각이 별개의 일이기 때문입니다.

**→ 그래서 Q20처럼 직접 모아서 반영해야 합니다.**

**→ "React 17까지는 어땠나요?"** 클릭 같은 **React 이벤트 안에서만** 모아줬고, `setTimeout`이나 `fetch` 응답 안에서는 하나씩 따로 그렸습니다.

**→ "부모가 다시 그려지면 자식도 그려지나요?"** 기본은 그렇습니다. props가 같으면 건너뛰게 하려면 **`React.memo`** 를 씁니다.

**→ 포인트.** 마지막 두 줄이 Q20과 Q22를 잇는 답입니다. 면접관이 노린 연결이 이것입니다.

### Q23. 이런 지식을 동료들과 어떻게 나눴나요? (1:12:05)

**실제 답변** — "2주에 한 번 개발팀 회의 때 10분 정도 이야기했다."

**다시 쓴 답변** `📁 내 경험`

**→ 회의에서 짧게 공유하고, 반복되는 건 문서와 규칙으로 남겼습니다.**

**→ 2주마다 개발팀 회의에서 10분 정도 공유했습니다.**

**→ AI 하네스는 온보딩 문서와 PR 리뷰를 거쳐 팀에 들였습니다.** 그 뒤로는 **다른 팀원들이 규칙을 추가하면서 같이 운영**했습니다.

**→ 규칙으로 남긴 건 잊히지 않습니다.** 말로 한 공유는 잊히지만, **규칙은 AI가 매번 읽고 따르니까요.**

**→ "팀원들이 실제로 썼다는 근거는요?"** **다른 팀원들이 직접 규칙을 추가했다**는 것, 즉 저 혼자 쓰는 도구가 아니라 **팀이 고치는 공용 설정**이 됐다는 점을 말합니다.

### Q25. 아쉽게 전달된 부분을 다듬어 보세요 · 역질문 · 입사일 (1:14:59 ~)

**실제 답변**
- 정정 기회 → "아닙니다. 하나 배운 것 같아서 좋았다."
- 역질문 → "AI 서비스를 만들 때 Claude 같은 걸 바탕으로 만드는지" (면접관이 되물어서 정리함) → 면접관이 회사의 AI 역사를 설명 → "다른 질문 없습니다"
- 입사일 → 11월 1일 가능

**문제점**
- 면접관이 **45분짜리 질문을 준비하고, 남은 시간을 정정용으로 열어줬습니다.** 드문 기회인데 "없습니다"로 넘겼습니다.
- 역질문도 하나로 끝났고, 면접관 설명을 들은 뒤 **"다른 질문 없습니다"** 로 마쳤습니다.

**다시 쓴 답변 — 정정 기회** `📁 내 경험` + `🌐 개념 정리` (하나만 골라서 1분 안에)

**→ git push 질문과 토큰 질문, 두 가지를 다시 말씀드리고 싶습니다.**

**→ 첫째, git push는 규칙 문서가 아니라 권한으로 막아야 합니다.** 규칙 문서는 **부탁일 뿐**입니다.

**→ 루티너리에서 실제로 그렇게 했습니다.** 되돌릴 수 없는 명령 9개를 **도구 권한에서 차단**했고, 빌드 진단 에이전트에는 **파일을 고치는 도구 자체를 주지 않았습니다.**

**→ 우회까지 막으려면 인증 키를 안 줍니다.** 에이전트 환경에 **push 권한이 있는 인증 키를 안 주는 게** 맞다고 생각합니다.

**→ 둘째, 모델은 다음 조각 하나를 예측하는 걸 반복합니다.** 글을 조각으로 잘라 번호로 다루고, **다음 조각 하나를 예측하는 걸 반복**합니다.

**→ 그래서 앱에서는 모아서 그리는 게 중요합니다.** 응답이 조각조각 오니, 앱에서는 그걸 **모아서 한 번에 그리는 게** 중요하다고 이해했습니다.

**다시 쓴 역질문** — 오늘 들은 정보로 만드세요.

**→ ① 앱마다 코드베이스가 따로인가요, 하나의 틀에서 갈라져 나가나요?** 새 앱이 여러 개 동시에 나간다고 하셨으니 묻습니다.

**→ ② 잘 굴러간다는 건 어떤 지표로 보시나요?** 출시한 앱의 **운영과 개선**을 맡는다고 하셨으니 묻습니다. (리텐션, 대화 수, 결제 전환 등)

**→ ③ 스트리밍 응답은 지금 SSE로 받으시나요, WebSocket으로 받으시나요?**

**→ "입사는 언제 가능하세요?"** 실제로 답한 대로 **11월 1일 가능**하다고 말합니다. 한 번 말한 날짜는 바꾸지 않습니다.

**→ 역질문에 면접관이 길게 답하면?** "다른 질문 없습니다" 대신, 들은 내용에 **한 줄 꼬리 질문**을 붙입니다. 예: "그럼 자체 모델과 외부 API는 지금 어떻게 나눠 쓰시나요?"

**→ 포인트.** ③은 오늘 질문 흐름을 그대로 이어받는 질문이라, **"면접에서 들은 걸 소화했다"** 는 인상을 줍니다.
