# 제출용 PDF 이력서 수정 문구

> **1차 면접에서 실제로 걸렸던 두 문장**을 고치기 위한 문서입니다.
>
> ⚠️ **PDF는 제가 고칠 수 없습니다.** 원본을 만든 도구(리멤버 커리어 등)에서
> 아래 문구로 직접 교체하셔야 합니다.
>
> `resume-reviewed.md`와 포트폴리오 사이트는 **이미 수정 완료**된 상태입니다.
> PDF만 남았습니다.

---

## 왜 고쳐야 하나

CJ푸드빌 1차 면접에서 면접관이 이 두 줄을 정확히 짚었습니다.

> **"이력서에 써주신 셀렉터 패턴이라는 게 따로 설계를 하신 게 아니고,
> 그냥 리액트 쿼리에서 제공하는 API를 사용했다고 볼까요?"**

> **"지연 초기화를 하면 오히려 런치 타임이 더 늦어질 것 같은데,
> 어떻게 감소할 수 있었던 건지 궁금합니다."**

두 질문 다 답하지 못했습니다. 그리고 **코드 검증 결과 두 표현 모두 근거가 없습니다.**

- React Query의 `select` 옵션 — **코드에서 사용된 곳 0건**
- `onRehydrateStorage` 등 hydration 완료 콜백 — **사용 흔적 없음**

같은 회사 2차든 다른 회사든, **이 문장이 남아 있는 한 같은 질문이 또 나옵니다.**

---

## 수정 ① — 셀렉터 패턴

### 현재 (PDF 31~32줄)

```
React Query 구독 구조 재설계 및 Selector 패턴 적용으로 불필요한 리렌더링
제거
```

### 바꿀 문구

```
서버 상태를 스토어로 복사하던 구조를 제거해 React Query가 서버 상태를
단독 소유하도록 정리, Zustand는 구독 범위를 필요한 값으로 좁혀 리렌더링 감소
```

**무엇이 달라졌나**
- `Selector 패턴 적용` 이라는 **하지 않은 일**을 뺐습니다.
- 대신 **실제로 한 일** 두 가지를 넣었습니다 — 서버 상태 소유권 분리, Zustand 구독 범위 축소.
- 이 둘은 코드로 확인되는 내용이라 **되물어도 설명할 수 있습니다.**

---

## 수정 ② — 지연 초기화

### 현재 (PDF 33~34줄)

```
Zustand 스토어 중복 통합, computed 기반 파생 상태 최적화, hydration
완료 후 지연 초기화 구조로 전환
```

### 바꿀 문구

```
Zustand 스토어 21개 중복 통합 및 computed 기반 파생 상태 최적화,
스토어별 version·migrate로 저장 구조 변경 대응
MobX → Zustand 마이그레이션 — 완료 플래그로 1회만 실행하고
실패 시 앱이 중단되지 않도록 예외를 격리해 리포팅만 수행
```

**무엇이 달라졌나**
- `hydration 완료 후 지연 초기화` 를 통째로 뺐습니다. **근거가 없고, 질문받으면 막힙니다.**
- 대신 **실재하는 마이그레이션 작업**을 넣었습니다.
  스토어별 `version`·`migrate`와 MobX→Zustand 전환은 코드에 있습니다.
- **"실패해도 앱이 죽지 않게 했다"** 가 들어간 게 중요합니다.
  운영 중 서비스를 다뤄본 사람이라는 신호라, 오히려 원래 문장보다 강합니다.

## 수정 후 전체 모습

`앱 전반 성능 개선` 항목이 이렇게 됩니다.

```
앱 전반 성능 개선
  서버 상태를 스토어로 복사하던 구조를 제거해 React Query가 서버 상태를
  단독 소유하도록 정리, Zustand는 구독 범위를 필요한 값으로 좁혀 리렌더링 감소
  Zustand 스토어 21개 중복 통합 및 computed 기반 파생 상태 최적화,
  스토어별 version·migrate로 저장 구조 변경 대응
  MobX → Zustand 마이그레이션 — 완료 플래그로 1회만 실행하고
  실패 시 앱이 중단되지 않도록 예외를 격리해 리포팅만 수행
  Xcode Organizer 실사용자 지표(P50/P95) 기반으로 개선 전후 직접 측정 및
  검증
     Peak Memory(P95): 958.5MB -> 297.4MB (-69%)
     Launch Time(P50): 540ms -> 400ms (-140ms, -26%)
```

**수치는 건드리지 않았습니다.** P50/P95 측정값은 실사용자 지표라 그대로 두는 게 맞습니다.

---

## ⚠️ 남은 문제 하나 — Launch Time

문장은 고쳤지만, **"왜 26% 줄었나"에 대한 답은 여전히 준비가 필요합니다.**

지연 초기화를 뺐으니 면접관이 이렇게 물을 수 있습니다.

> **"그럼 Launch Time은 뭘 해서 줄인 건가요?"**

### 준비할 답변

> 시작할 때 하던 일을 줄인 게 아니라, **시작 경로에서 재는 구간을 먼저 나눴습니다.**
> 어디서 시간이 걸리는지 모르는 상태에서는 고칠 데를 못 정하니까요.
>
> 단계별로 표시를 남기는 측정 스크립트를 만들어서 **열 번 재고 가운데 값**으로 비교했고,
> 그렇게 보니 특정 구간이 유독 길다는 게 드러났습니다.
> [ 실제로 줄인 항목 — 확인 후 채우세요 ]

**⚠️ 이 부분은 제가 대신 채울 수 없습니다.**
코드에서 확인된 건 **측정 체계(`measure-cold-start.sh`, Amplitude telemetry)** 까지이고,
실제로 무엇을 줄여서 140ms가 빠졌는지는 기록이 남아 있지 않습니다.

**기억나지 않으면 이렇게 답하세요.**
> 정확히 어떤 항목이었는지는 지금 바로 말씀드리기 어렵습니다.
> 다만 측정 체계를 먼저 만들고 그 지표로 판단했다는 건 확실합니다.

**억지로 답하지 마세요.** 1차에서 막힌 것도 억지로 답하려다 막힌 것입니다.
