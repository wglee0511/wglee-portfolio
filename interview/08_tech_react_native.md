# 기술 면접 — React Native

> RN 포지션 면접의 핵심 질문입니다. 본인 주력 분야이므로 **답변 깊이를 가장 두껍게 준비**해야 합니다.
> `▶ 내 경험`은 이력서와 연결하는 문장입니다.
>
> 답변은 두 종류로 나눴습니다.
> - **`📁 내 경험`** — 이력서·실제 프로젝트(루티너리 등)에서 꺼낸 답입니다. 이 답을 먼저 말하세요.
> - **`🌐 개념 정리`** — 일반 개념 설명입니다. 외우기보다 **이해해서 내 말로** 하고, `▶ 내 경험`으로 이어 붙이세요.

## 아키텍처

### Q1. React Native는 어떻게 동작하나요? 구조를 설명해 주세요.

**답변 (구조 먼저, 그다음 변화)** `🌐 개념 정리`
> **→ 세 갈래 스레드가 나눠 일하고, 그 사이 연결이 Bridge에서 JSI로 바뀌었습니다.** 구조 먼저, 변화는 그다음입니다.
>
> **→ 일하는 갈래는 셋입니다.** **내 코드가 도는 JS 스레드**, **실제로 화면을 그리는 네이티브(UI) 스레드**, **크기와 위치를 계산하는 백그라운드(Shadow) 스레드**입니다.
>
> **→ 레이아웃은 Yoga가 계산합니다.** JS에서 만든 화면 구조를 Yoga — 레이아웃 계산 엔진 — 가 "어디에 얼마 크기로"를 계산하고, 그 결과를 네이티브 뷰로 그립니다.
>
> **→ 구 아키텍처는 Bridge가 이었습니다.** 문제는 **비동기인 데다 오갈 때마다 JSON 직렬화** — 데이터를 문자열로 바꿔 주고받는 것 — 를 거친다는 점입니다. 서로 기다릴 수 없으니, 스크롤처럼 **매 프레임 바로 답이 와야 할 때 끊김**이 생겼습니다.
>
> **→ 새 아키텍처는 JSI로 바꿨습니다.** JS가 **C++ 객체를 직접 붙잡고** 써서, 문자열로 바꾸는 과정 없이 답을 그 자리에서 받습니다.
>
> **→ 그 위에 TurboModules와 Fabric이 올라갑니다.** **TurboModules**는 네이티브 기능을 쓸 때 올리는 것, **Fabric**은 새 화면 그리기 엔진입니다.

**30초 버전** — "JS 스레드, UI 스레드, 레이아웃 계산 스레드 셋으로 나뉩니다. 예전엔 Bridge가 비동기·JSON 직렬화로 이어서 느렸고, 새 아키텍처는 JSI로 직접 호출하고 그 위에 TurboModules와 Fabric을 올렸습니다."

**꼬리 질문 대비**

**→ "그래서 뭐가 좋아지나요?"** ① 앱 켤 때 네이티브 기능을 전부 올리지 않아 **처음 뜨는 게 가벼워지고**, ② 답을 그 자리에서 받으니 **크기를 재야 하는 화면이나 손가락을 따라가는 동작이 자연스러워집니다.**

### Q2. Reanimated는 왜 빠른가요?

**답변** `🌐 개념 정리`
> **→ 애니메이션을 worklet으로 UI 스레드에서 직접 돌리기 때문입니다.** worklet은 화면 그리는 쪽으로 떼어 보내서 거기서 실행되는 함수입니다.
>
> **→ `setState` 방식은 JS를 매 프레임 들릅니다.** JS가 바쁘면 **그만큼 화면이 밀립니다.**
>
> **→ Reanimated는 JS를 거치지 않습니다.** SharedValue — 양쪽이 같이 보는 값 — 를 화면 그리는 쪽에서 바로 읽고 써서 **JS가 막혀 있어도 애니메이션은 계속 돕니다.**

**▶ 내 경험 (이 질문이 나오면 반드시 이어붙이세요)**
> **→ 바로 그 구조 때문에 생긴 OutOfMemoryError를 잡은 적이 있습니다.** 메모리가 모자라 앱이 죽는 문제였습니다.
>
> **→ 원인은 SharedValue 정리 누락입니다.** 정리가 빠져서 **네이티브 쪽 메모리가 계속 늘어나는** 상황이었습니다.
>
> **→ 정리해주는 공용 훅을 만들었습니다.** 각 화면은 SharedValue 목록만 넘기면 됩니다. ① 화면이 사라질 때 `isMounted`를 false로 내리고, ② 넘겨받은 값들에 **`cancelAnimation`을 한꺼번에 걸어** 끕니다. ③ 콜백을 한 겹 감싸 **worklet 안에서 `isMounted`를 확인한 다음에만 JS로 넘기게** 해, 화면이 사라진 뒤 콜백이 실행되는 걸 막았습니다.
>
> **→ 핵심은 사람이 기억해서 챙기는 구조를 없앤 것입니다.** 그건 언젠가 반드시 빠지니까요.
>
> **→ 24개를 등록하고 전후를 직접 쟀습니다.** 온보딩 슬라이드 14개, 타이머 서클 6개, 비교 애니메이션 4개 등 **SharedValue 24개**를 훅에 등록했고, Android Native Heap으로 재서 **Total Allocations 101.9MB → 31.2MB (-69%), Remaining Size 31.2MB → 11.0MB (-65%)** 를 확인했습니다.

> ⚠️ 제출용 PDF에는 같은 작업이 **Xcode Organizer 실사용자 Peak Memory(P95) 958.5MB → 297.4MB (-69%)** 로 적혀 있습니다.
> 면접관이 PDF를 들고 있으면 **PDF 숫자로 통일**하세요. → [17_pdf_resume_qa.md](./17_pdf_resume_qa.md) 맨 위 대조표 · Q2

**30초 버전** — "애니메이션을 worklet으로 UI 스레드에서 직접 돌려서 JS가 막혀도 안 끊깁니다. 대신 정리 시점이 어긋나기 쉬워서, 실제로 SharedValue 정리 누락으로 OOM이 났고 공용 cleanup 훅으로 24개를 묶어 해결했습니다."

**꼬리 질문 대비**

**→ "그럼 단점은 없나요?"** 있습니다. **화면 그리는 쪽에서 따로 도는 코드라, 치우는 시점이 JS 쪽 화면 생명주기와 어긋나기 쉽습니다.** 컴포넌트는 사라졌는데 worklet이 SharedValue를 계속 붙들고 있으면 그대로 메모리가 샙니다. 바로 위 경험으로 잇습니다.

**→ "69%면 너무 많이 줄어든 것 아닌가요?"** 정리 안 되던 값이 **24개**였고, **화면을 오갈수록 쌓이는 구조**라 효과가 컸다고 답합니다. (→ 17번 Q2)

### Q3. 브리지를 직접 만들어 본 적 있나요?

**답변** `📁 내 경험`
> **→ 있습니다. 루티너리에서 Android Geofence 기반 위치 알림 모듈을 만들었습니다.** 요구사항은 **"앱이 완전히 종료돼도 특정 장소에 도착하면 루틴 알림이 떠야 한다"** 였습니다.
>
> **→ 문제는 앱이 꺼져 있으면 JS 코드가 돌 자리 자체가 없다는 것입니다.**
>
> **→ BroadcastReceiver와 Headless JS로 풀었습니다.** **BroadcastReceiver** — 앱이 꺼져 있어도 OS가 깨워 알려주는 수신기 — 로 진입·이탈 이벤트를 받고, **Headless JS**로 화면 없이 JS만 잠깐 띄워 처리했습니다.
>
> **→ 설정이 바뀌면 바로 반영합니다.** 사용자가 설정을 바꾸면 그때그때 지오펜스를 **등록·해제**하도록 했습니다.

**30초 버전** — "루티너리에서 앱이 종료돼도 동작하는 Android 지오펜스 알림을 네이티브 모듈로 만들었습니다. BroadcastReceiver로 이벤트를 받고 Headless JS로 처리했고, 재부팅 재등록과 배터리 최적화 예외까지 챙겼습니다."

**꼬리 질문 대비**

**→ "어려웠던 점은?"** (거의 확실히 따라옵니다) **"앱이 없는 상태"의 종류가 생각보다 많다는 것**입니다. ① **재부팅하면 등록한 지오펜스가 전부 사라집니다.** 그래서 부팅 완료 이벤트를 받는 리시버를 따로 두고 **재등록**하게 했습니다. 이건 문서가 아니라 **실기기를 재부팅해보고 알았습니다.** ② **배터리 최적화** — 제조사마다 백그라운드 제약이 달라 콜백이 늦거나 안 옵니다. 그래서 **최적화 예외 상태를 확인하고 요청하는 경로**를 네이티브 모듈에 같이 넣었습니다.

**포인트** — ①의 *"실기기를 재부팅해보고 알았다"* 가 핵심입니다.
**문서로는 안 잡히는 걸 직접 확인해봤다**는 신호입니다.

## 성능

### Q4. RN 앱의 성능 문제는 어떻게 진단하나요?

**답변 (레이어를 나눠서 말하는 게 핵심)** `🌐 개념 정리`
> **→ 먼저 어느 층의 문제인지부터 가릅니다.** 안 나누면 **엉뚱한 곳을 고치게** 됩니다.
>
> **→ ① JS 쪽.** 너무 자주 다시 그리거나 무거운 계산이 있는 경우입니다. **Profiler**로 봅니다.
>
> **→ ② 화면 그리는 쪽(UI 스레드).** 레이아웃이나 애니메이션 문제입니다. 화면이 **뚝뚝 끊기는 걸로** 나타납니다.
>
> **→ ③ 네이티브 메모리.** 메모리가 계속 늘어나는 경우입니다. **JS 쪽 도구로는 아예 안 보입니다.**

**▶ 내 경험**
> **→ ③을 직접 겪어서, 고치기 전후로 Android Native Heap 메모리를 재는 습관이 생겼습니다.**
>
> **→ 시작 시간도 n=10 중앙값으로 비교했습니다.** 시작 단계마다 시간 표시를 남기는 스크립트를 따로 만들었습니다. **한 번만 재고 좋아졌다고 말하면 신뢰가 안 가서요.**

**30초 버전** — "JS, UI 스레드, 네이티브 메모리 세 층으로 먼저 나눕니다. 저는 네이티브 메모리 누수를 겪어서 전후로 직접 재고, 시작 시간도 n=10 중앙값으로 비교합니다."

**꼬리 질문 대비**

**→ "왜 중앙값인가요?"** 한 번 재면 그때그때 **튀는 값이 섞여서**, 여러 번 재고 가운데 값을 봐야 비교가 된다고 답합니다. 실사용자 기준은 **P50/P95**로 본다고 이어갑니다. (→ 17번 Q1)

### Q4-1. ANR을 잡아본 경험이 있나요? (강력 추천 카드)

**답변** `📁 내 경험`
> **→ 있습니다. 이벤트 로그를 남기는 함수 하나가 ANR을 만들고 있었습니다.** ANR은 앱이 멈춰서 안드로이드가 "응답 없음"을 띄우는 상태입니다.
>
> **→ 로그 함수가 SDK 6개와 저장소 읽고 쓰기 2개를 전부 순서대로 기다렸습니다.** Sentry·Amplitude·기타 분석 도구에 차례로 보내고, 로컬 저장소도 읽고 썼습니다.
>
> **→ 합치면 메인 스레드에서 0.5~2초였습니다.** 각각은 짧지만, 팝업이 뜨거나 루틴을 추가하는 것처럼 **화면이 그려지는 순간과 겹치면 ANR**이 났습니다.
>
> **→ 일을 나눠서 고쳤습니다.** 가벼운 것만 바로 실행하고, 무거운 건 **`InteractionManager.runAfterInteractions`로 화면이 다 그려진 뒤에** 돌게 미뤘습니다. 네이티브 쪽 호출은 **`Promise.all`로 한꺼번에** 보냈습니다.

**30초 버전** — "로그 함수 하나가 분석 SDK 6개와 저장소 I/O 2건을 메인 스레드에서 순서대로 기다려 0.5~2초를 잡고 있었습니다. 무거운 건 InteractionManager로 화면이 다 그려진 뒤로 미루고, 네이티브 호출은 병렬로 바꿔 ANR을 없앴습니다."

**꼬리 질문 대비**

**→ "왜 처음부터 비동기로 안 짜여 있었나요?"** 하나씩 추가될 때는 각각 가벼웠기 때문이라고 봅니다. SDK가 늘 때마다 조금씩 무거워졌는데 **한 번에 확 넘어간 순간이 없어서** 아무도 몰랐습니다. 그래서 **쌓인 총합을 재보지 않으면 못 찾습니다.**

**포인트** — 이 사례가 좋은 이유는 **"성능 문제가 성능 코드에 있지 않았다"** 는 점입니다.
분석 로깅은 보통 성능 관점에서 아무도 안 보는 영역인데, 거기가 원인이었습니다.

### Q5. 콜드 스타트를 줄이려면?

**답변** `🌐 개념 정리`
> **→ RN에서는 대개 켤 때 읽어들이는 JS 양을 줄이는 게 가장 효과가 큽니다.** 콜드 스타트는 앱이 완전히 꺼진 상태에서 처음 켜질 때까지의 시간입니다.
>
> **→ 방법은 크게 둘입니다.** **① 켤 때 읽어들이는 JS 양 줄이기**, **② 네이티브 쪽 준비 작업 뒤로 미루기**입니다.
>
> **→ 흔한 원인은 화면을 한꺼번에 불러오는 것입니다.** 화면 이동을 정의하는 파일이 모든 화면을 맨 위에서 불러오면, **첫 화면 하나 띄우려고 앱 전체 화면의 코드를 다 읽게** 됩니다.

**▶ 내 경험 (⚠️ 결말까지 말해야 하는 사례입니다)**
> **→ 루티너리가 정확히 그 상태여서 lazy로 바꿨다가, 실측을 보고 되돌렸습니다.**
>
> **→ 화면 62개를 React.lazy로 바꿨습니다.** 그 화면에 들어갈 때 불러오게 했고, Debug 빌드 n=10 중앙값 기준 **Splash 초기화 -24.4%, JS 총 로딩 -21.8%** 가 나왔습니다.
>
> **→ 노트북 수치라 실사용자 telemetry를 따로 만들었습니다.** 시작 단계마다 걸린 시간을 **Amplitude로 보내는 telemetry** — 앱이 스스로 지표를 보고하게 하는 장치 — 입니다.
>
> **→ 비교 기준을 재려고 lazy를 걷어냈다가, 결국 되돌리는 쪽으로 결정했습니다.** lazy로 나눈 자리마다 로딩 화면이 끼면서 **화면 전환이 답답해지는 비용**이 시작 시간에서 얻는 것보다 크다고 판단했습니다.
>
> **→ 지금은 전부 처음부터 불러오는 방식으로 통일돼 있습니다.**

**⚠️ 반드시 결말까지 말하세요.**
"50개 화면을 지연 로딩했습니다"에서 끊으면 **현재 코드와 다릅니다.**
코드를 확인당하는 순간 앞의 수치까지 전부 의심받습니다.

> ⚠️ 제출용 PDF에는 지연 로딩 항목이 **아예 없고**, 시작 시간은 **Launch Time(P50) 540ms → 400ms (-26%)** 로만 적혀 있습니다.
> PDF 기준 면접이면 이 숫자로 말하고, 지연 로딩은 물어볼 때만 위 흐름으로 꺼내세요. → 17번 대조표

**30초 버전** — "켤 때 읽는 JS를 줄이는 게 핵심이라 화면 62개를 lazy로 바꿔 Debug 기준 Splash -24.4%를 봤습니다. 그런데 실사용자 telemetry로 확인해보니 화면 전환 비용이 더 커서, 측정 체계만 남기고 lazy는 되돌렸습니다."

**꼬리 질문 대비**

**→ "그럼 그 작업은 실패한 건가요?"** 결과물은 되돌렸지만 **측정 체계와 telemetry는 남았고**, 그걸로 판단을 데이터로 할 수 있게 됐다고 답합니다. 커밋 히스토리에 과정이 남아 있습니다.

**포인트** — 오히려 **"측정하고 내 작업을 되돌렸다"** 가 더 강한 카드입니다.
telemetry를 남겼다는 것과 합치면 **"감이 아니라 데이터로 판단하는 사람"** 이 됩니다.

### Q6. FlatList 성능 최적화는 어떻게 하나요?

**답변** `🌐 개념 정리`
> **→ key·memo·getItemLayout을 먼저 챙기고, 범위 옵션은 재보고 조정하고, 그래도 안 되면 FlashList입니다.**
>
> **→ ① `keyExtractor`로 안정적인 key를 줍니다.**
>
> **→ ② renderItem 컴포넌트는 memo로 감싸되, 콜백을 그 자리에서 새로 만들어 넘기지 않습니다.** 매번 새 함수를 넘기면 memo가 "달라졌다"고 보고 **다시 그립니다.**
>
> **→ ③ 항목 높이가 일정하면 `getItemLayout`을 줍니다.** 각 항목 위치를 일일이 재지 않아도 돼서 **체감 차이가 큽니다.**
>
> **→ ④ `windowSize`, `maxToRenderPerBatch`는 기본값으로 먼저 재보고 조정합니다.** 무작정 늘리면 **메모리가 같이 늡니다.**
>
> **→ ⑤ 그래도 안 되면 FlashList를 검토합니다.** 화면 밖 항목을 다시 쓰는 다른 구현입니다.

**30초 버전** — "안정적인 key, memo와 고정된 콜백, 높이가 일정하면 getItemLayout을 먼저 챙기고, 렌더링 범위 옵션은 재보고 조정합니다. 그래도 안 되면 FlashList를 검토합니다."

**꼬리 질문 대비**

**→ "windowSize를 줄이면 뭐가 나빠지나요?"** 미리 그려두는 범위가 줄어서 **빨리 스크롤할 때 빈 칸이 잠깐 보일 수** 있습니다. 메모리와 빈 칸 사이의 교환이라 **재보고 정한다**고 답합니다.

### Q7. 메모리 누수를 어떻게 찾았나요? (심화)

**답변 (과정으로 말하세요)** `📁 내 경험`
> **→ 재현 조건을 좁히고, 반복하며 재고, 남는 객체를 거슬러 올라갑니다.**
>
> **→ ① 재현 조건을 좁힙니다.** 특정 화면을 **반복 진입할 때만** 늘어나는지 확인합니다.
>
> **→ ② 같은 동작을 반복하면서 메모리를 잽니다.** 돌아오지 않고 **계단처럼 계속 오르면 누수**입니다.
>
> **→ ③ 남는 객체를 거슬러 올라갑니다.** 어떤 종류의 객체가 안 지워지는지 보고, **그걸 붙들고 있는 게 뭔지** 찾습니다.

**▶ 내 경험 (두 번째 사례 — 첫 번째와 원인이 다릅니다)**
> **→ 타임라인 토글을 누를 때마다 20MB씩 안 돌아왔고, 원인은 리마운트 churn이었습니다.** SharedValue가 아니라 **화면을 통째로 없앴다 다시 만드는 걸 반복**하는 게 문제였습니다.
>
> **→ 삼항 연산자 하나가 원인이었습니다.** `isTimelineMode ? 타임라인 : 리스트` 형태라, 누를 때마다 **애니메이션·제스처·스크롤이 얽힌 무거운 화면이 통째로 사라졌다 새로 만들어졌고**, 제대로 안 지워지고 쌓였습니다.
>
> **→ 처음 필요할 때만 만들고, 한 번 만든 건 안 없앱니다.** 들어갈 때는 **지금 보는 쪽만** 만들고(안 그러면 반대쪽 화면이 잠깐 비칩니다), 한 번 켜진 화면은 **그대로 두고 투명도로만 보였다 숨겼다** 합니다.

> ⚠️ 이 수정은 **아직 `dev`에 머지되지 않은 브랜치**에 있습니다.
> "해결했습니다"보다 **"수정해서 올려둔 상태"** 로 말하는 게 안전합니다.

**30초 버전** — "재현 조건을 좁히고, 같은 동작을 반복하며 메모리가 계단처럼 오르는지 봅니다. 타임라인 토글은 삼항 연산자로 무거운 화면이 매번 리마운트되며 20MB씩 쌓여서, 한 번 만든 화면은 유지하고 투명도로만 숨기게 수정해 올려둔 상태입니다."

**꼬리 질문 대비**

**→ "계속 띄워두면 메모리를 더 먹지 않나요?"** 한 화면 몫은 계속 들고 있지만, **누를 때마다 쌓이는 것보다는 상한이 정해져 있다**는 점이 차이라고 답합니다. 처음 필요할 때만 만드는 이유도 그겁니다.

**포인트** — **"메모리 누수 = 항상 cleanup 문제"가 아니라는 걸 아는 사람**으로 보입니다. 강한 답변입니다.
"삼항 연산자 하나가 20MB를 만들었다"는 구체성이 이 답변을 살립니다.

### Q8. 위젯은 어떻게 구현했나요?

**답변 (RN 면접에서 가장 차별화되는 항목입니다)** `📁 내 경험`
> **→ Android · iOS · Wear OS 세 플랫폼을 했고, 가장 어려운 건 화면이 아니라 앱과 값을 맞추는 일이었습니다.**
>
> **→ 위젯은 앱과 따로 도는 프로그램입니다.** 그래서 **앱의 JS 상태를 그대로 쓸 수 없습니다.**
>
> **→ 동기화 흐름을 설계했습니다.** **Zustand 스토어가 바뀌면 → 양쪽이 같이 보는 저장소에 쓰고 → 앱에 다시 들어올 때 합치고 → Firestore로 차례차례 올립니다.**
>
> **→ 진짜 문제는 앱과 위젯에서 같은 걸 동시에 고쳤을 때입니다.** 통째로 덮어쓰면 한쪽 변경이 사라지니까, **언제 고쳤는지 시각을 보고 항목 하나하나 단위로 합치게** 했습니다.

**30초 버전** — "위젯은 앱과 따로 도는 프로그램이라, 스토어 변경 → 공유 저장소 → 앱 진입 시 병합 → Firestore 순차 반영 흐름을 만들었습니다. 동시 수정은 항목별 수정 시각으로 합쳐서 한쪽이 사라지지 않게 했습니다."

**꼬리 질문 대비**

**→ "왜 item 단위인가요?"** 사용자가 위젯에서 체크리스트 항목 A를 체크하고 앱에서 항목 B를 고쳤다면 **둘 다 살아야 정상**이기 때문입니다. 묶음 전체를 통으로 비교하면 **늦게 저장된 쪽이 앞의 걸 통째로 밀어냅니다.**

### Q9. 기존 사용자를 깨뜨리지 않고 위젯을 교체한 방법은?

**답변 (마이그레이션 감각을 보여주는 항목)** `📁 내 경험`
> **→ 위젯 5종을 Jetpack Glance로 재작성하면서, 클래스 이름과 패키지 경로는 그대로 두고 안쪽만 갈아끼웠습니다.** Grid · Calendar · Weekly · Streak · CheckList입니다.
>
> **→ 문제는 이미 홈 화면에 위젯을 올려둔 사용자였습니다.** Android는 위젯을 클래스 이름으로 찾아가서, **이름을 바꾸면 기존 위젯이 그냥 사라집니다.** 그래서 사용자가 눈치채지 못하게 옮겼습니다.
>
> **→ 파일은 옮겨도 패키지 선언은 예전 경로를 유지했습니다.** 파일은 `widget/` 디렉토리로 옮겼지만, Manifest의 `android:name=".Widget"` 이 **그대로 찾아가야** 하니까요.
>
> **→ 코드에 *"패키지 유지 필수"* 주석을 남겼습니다.** 나중에 누가 무심코 정리하면 위젯이 사라지거든요.
>
> **→ 저장 방식은 DataStore로 바꿨습니다.** 위젯이 종료됐다 다시 떠도 **상태가 남고**, 사용자가 늘리고 줄인 **크기에 레이아웃이 따라가게** 했습니다. **같은 종류 위젯을 여러 개 놓아도 상태가 섞이지 않게** 인스턴스별로 저장 파일을 분리했습니다.

**30초 버전** — "위젯 5종을 Glance로 다시 썼는데, Android는 클래스 이름으로 위젯을 찾아서 이름과 패키지는 그대로 두고 안쪽만 교체했습니다. 그래서 이미 홈 화면에 둔 사용자 위젯이 안 사라졌고, DataStore로 상태 유실과 인스턴스 간 간섭도 없앴습니다."

**꼬리 질문 대비**

**→ "그 규칙을 다른 사람이 모르고 깨면요?"** 그래서 코드에 *"패키지 유지 필수"* 주석을 남겼다고 답합니다. **사람이 기억하는 데 기대지 않으려는** 의도입니다.

**포인트** — **"사용자를 깨뜨리지 않는 것"을 제약으로 먼저 인식했다**는 게 이 답변의 핵심입니다.

### Q10. iOS와 Android 위젯 구현의 차이는?

**답변** `📁 내 경험`
> **→ 갱신 모델이 달라서, 플랫폼이 허용하는 갱신 모델에 맞춰 UX를 다르게 설계했습니다.**
>
> **→ iOS는 시스템이 갱신 시점을 정합니다.** 앱은 "언제 뭘 보여줄지" 목록만 미리 제출하고, **실제 갱신 시점은 시스템이 정해진 몫 안에서 정합니다.**
>
> **→ iOS 17+는 AppIntents로 위젯에서 바로 동작을 실행합니다.** 눌러서 바로 처리되는 위젯을 그걸로 만들었습니다.
>
> **→ Android는 상대적으로 자유롭습니다.** **suspend 함수로 뼈대를 먼저 그리고 데이터가 오면 다시 그리는 식**으로 단계를 나눴습니다.

**30초 버전** — "iOS는 시스템이 갱신 시점을 정하고, Android는 앱이 비교적 자유롭게 갱신합니다. 그래서 iOS는 AppIntents 인터랙티브 위젯으로, Android는 suspend 기반 단계형 갱신으로 UX를 따로 설계했습니다."

**꼬리 질문 대비**

**→ "iOS에서 즉시 반영이 필요하면요?"** **AppIntents로 위젯 안에서 동작을 실행하면** 그 결과는 바로 반영된다고 답합니다. (→ [11_tech_swift_ios.md](./11_tech_swift_ios.md) Q5·Q6)

### Q11. Wear OS는 어떻게 연동했나요?

**답변** `📁 내 경험`
> **→ 워치 UI는 Compose로 옮기고, 데이터는 DataClient로 이어서 폰 앱이 바뀌면 워치가 자동 갱신됩니다.**
>
> **→ UI는 XML 레이아웃에서 Jetpack Compose로 마이그레이션했습니다.**
>
> **→ 데이터는 WearDataLayer(DataClient)로 이었습니다.** 폰과 워치가 데이터를 주고받는 통로입니다. **메인 앱 데이터가 바뀌면 워치 UI가 자동으로 갱신**되는 구조입니다.

**30초 버전** — "워치 UI를 XML에서 Compose로 옮기고, DataClient로 폰 앱 데이터가 바뀌면 워치가 자동 갱신되게 연결했습니다."

**꼬리 질문 대비**

**→ "워치 쪽에서 바꾼 건 어떻게 올라오나요?"** [ 워치→폰 방향 동기화를 실제로 구현했는지 채우세요 ] 기억나는 범위만 말하고, 확실치 않으면 **"폰→워치 방향이 주였다"고 선을 긋습니다.**

### Q13. RN에서 크래시는 어떻게 대응하나요?

**30초 버전** — "Sentry로 JS 에러와 네이티브 크래시를 나눠 봅니다. OOM처럼 터진 자리가 원인이 아닌 경우는 메모리가 어떻게 늘어왔는지를 추적합니다."

**꼬리 질문 대비**

**→ "OOM 원인은 결국 어떻게 찾았나요?"** **Q2의 SharedValue 정리 누락 사례**로 바로 넘어갑니다.

>

**30초 버전** — "실제로 크래시를 냈던 패턴과 성능 안티패턴을 검사 항목으로 만든 RN 코드 리뷰 서브에이전트를 두고 자동으로 봅니다. 애니메이션 cleanup 누락이 대표적입니다."

**꼬리 질문 대비**

**→ "사람 리뷰는 그럼 뭘 보나요?"** [ 실제로 사람이 리뷰할 때 중점으로 본 것 — 예: 설계 의도·상태 소유 위치 ] 를 채우세요. **자동 검사는 반복되는 실수를 맡고, 사람은 판단이 필요한 부분을 본다**는 방향으로 말합니다.
