### Q1. 간단히 자기소개 부탁드립니다.

**답변** `📁 내 경험`

**→ AI로 개발 속도를 올리면서도 품질을 기계로 지키는 4년 차 React Native 개발자 이원교입니다.**

**→ 루티너리(500만 사용자 습관 앱)에서 팀의 AI 개발 환경을 만들었습니다.** 편집한 파일은 자동 검사하고, 타입 에러가 있으면 작업이 안 끝나게 막는 하네스입니다. 지금은 **팀원들이 규칙을 더하며 같이 운영**합니다.

**→ 성능을 숫자로 잡습니다.** 실사용자 지표로 메모리 문제를 찾아 **Peak Memory P95를 958MB에서 297MB로** 줄였습니다.

**→ AI로 혼자서도 끝까지 갑니다.** 2026년 상반기에 **앱·웹 3개를 기획부터 출시까지** 완주했고, 그중 하나가 **GLP-1 복약 기록 앱**입니다.

**→ 회사 순서는 페이히어(POS) → 메이크델타(트레이딩) → 루티너리입니다.** 순서를 틀리면 이력서와 다르게 들립니다([27번](./27_wrtn_review.md) Q1).

### Q2. 왜 메라키플레이스인가요?

**답변** `📁 내 경험`

**→ 제가 개인적으로 만들던 헬스케어 앱을, 100만 명이 쓰는 규모에서 만들고 싶어서입니다.**

**→ GLP-1 복약 기록 앱을 직접 만들면서, 환자의 기록이 진료로 이어지는 게 핵심이라고 느꼈습니다.** 그래서 **의사에게 보여줄 PDF 리포트**를 만들었습니다. 나만의닥터는 그 연결을 **진료 · 처방 · 약국까지** 실제로 하는 서비스입니다.

**→ 일하는 방식이 제가 해온 방식과 같습니다.** AI를 쓰는 데서 그치지 않고 **팀이 같이 쓰는 검증 장치**를 만들었고, 레거시 위에서 **새 코드만 깨끗하게 유지하는 방법**을 고민했습니다. 공고가 말하는 "AI로 레거시를 공격적으로 해결"과 같은 방향입니다.

**→ 스택이 루티너리와 거의 같습니다.** CodePush · Fastlane · Remote Config · MMKV · Sentry. **바로 운영에 들어갈 수 있습니다.**

**→ "나만의닥터 써 보셨나요?"** **[ 실제로 써 봤는지 · 써 본 흐름 하나 ]** 써 보지 않았다면 **면접 전에 반드시** 진료 예약 → 결제 → 처방 수령 흐름을 한 번 따라가 보고, **불편했던 점 하나**를 정리해 가세요.

### Q4. 최근 6개월~1년간 AI로 생산성이 어떻게 달라졌나요? 숫자로 말할 수 있나요?

**답변** `📁 내 경험`

**→ 혼자서 앱·웹 3개를 기획부터 출시까지 5개월 안에 끝냈고, 처음 써 보는 영역도 혼자 설계할 수 있게 됐습니다.**

**→ 결과물로 말씀드리면:** 2026년 상반기에 **Cadence · 스팟 스테이플러 · 찍고가** 세 개를 출시했습니다. **[ 각 프로젝트 기간 — 예: 기획~출시 n주 ]**

**→ 범위가 넓어졌습니다.** 예전에는 프론트엔드만 했는데, 지금은 **Supabase로 인증·DB 권한(RLS)·서버 함수**, Next.js Route Handler로 **API 프록시**, Expo config plugin으로 **네이티브 설정**까지 혼자 합니다.

**→ 회사에서는 낯선 네이티브 영역을 혼자 맡았습니다.** Android 위젯 5종을 **Jetpack Glance로 다시 짰고**, Wear OS를 Compose로 옮겼습니다. Kotlin을 주로 쓰던 사람이 아닌데도 **코드 분석 → 계획 → 구현 → 검증** 순서로 끝냈습니다.

**→ 숫자로 재지 못한 부분은 정직하게:** "AI 전후 개발 속도를 측정한 적은 없습니다. 대신 **혼자 끝낸 범위**로 말씀드립니다." [27번](./27_wrtn_review.md) 위험 발언 4번처럼 **근거 없는 퍼센트는 말하지 않습니다.**

### Q5. AI가 만든 코드의 품질은 어떻게 보장하나요? 사람이 계속 봐야 하는 부담은요?

**답변** `📁 내 경험`

**→ 사람이 매번 확인하던 걸 기계가 강제하게 만들어서 부담을 줄였습니다.**

**→ 훅으로 막습니다.** 파일을 고치면 **ESLint가 자동으로** 돌고, 작업을 끝낼 때 **타입 검사를 통과 못 하면 작업이 안 끝납니다.**

**→ 레거시 코드베이스에 맞췄습니다.** 기존 타입 에러가 **367개**라 전체를 막으면 아무것도 못 합니다. 그래서 **편집한 파일의 에러만** 걸러 막았습니다. 새 코드는 깨끗하게, 옛 에러는 그 파일을 건드릴 때 같이 고쳤습니다.

**→ 리뷰 에이전트는 우리 앱에서 실제로 났던 크래시 패턴을 검사합니다.** 리뷰·진단 에이전트에는 **고치는 도구(Edit·Write)를 주지 않았습니다.** 보고만 하고, 고칠지는 사람이 정합니다.

**→ 그래서 제가 보는 건 두 가지로 줄었습니다.** **"내가 이 코드를 설명할 수 있나"** 와 **"실제 기기에서 맞나"** 입니다. 결제처럼 되돌릴 수 없는 코드는 PR에 **따로 표시해서** 리뷰를 모았습니다.

**→ "규칙(rules)과 훅을 나눈 기준은요?"** 규칙은 **"가능하면 지키는 것"** 이라 에이전트가 무시할 수 있습니다. **반드시 지켜야 하는 건 훅으로** 옮겼습니다.

### Q6. Prompt / Context Engineering은 어떻게 하나요? MCP는 어떻게 썼나요?

**답변** `📁 내 경험`

**→ 에이전트가 매번 같은 걸 묻지 않도록, 필요한 맥락이 자동으로 들어가게 만들었습니다.**

**→ 규칙 문서를 한 파일에 몰지 않고 8개로 나눴습니다.** 컴포넌트·상태·네이티브처럼 **주제별로** 나눠서 필요한 것만 읽게 했습니다. 다만 **적용 범위를 좁게 잡은 건 컴포넌트 규칙 하나**였고, 나머지는 거의 늘 같이 읽혔다는 한계도 말합니다.

**→ MCP로 티켓과 디자인을 바로 읽게 했습니다.** **Linear MCP**로 티켓 내용을 자동으로 불러오고, **Figma MCP**로 디자인을 보고 구현합니다. 사람이 티켓을 복사해 붙이는 단계가 없어졌습니다.

**→ 긴 로그는 별도 에이전트에 맡겼습니다.** Xcode·Gradle 빌드 로그는 수천 줄이라 메인 대화에 넣으면 맥락을 다 씁니다. **빌드 진단 서브에이전트가 따로 읽고 원인만** 돌려줍니다.

**→ 도구에 묶이지 않게 했습니다.** 같은 하네스를 **Codex 환경으로도 옮겼습니다.** Cursor·Claude·Gemini 어느 걸 써도 **규칙과 검증은 같아야** 한다고 봤습니다.

### Q7. AI가 틀린 코드를 낸 걸 잡은 사례가 있나요?

## 3. 기술 선택 — "왜 그렇게 했나, 대안은?" 꼬리 질문 대비

> 후기: **"그렇게 결정하고 진행한 이유, 다른 대안은 없었을지에 대해 굉장히 깊숙하게 질문한다."**

### Q9. 메모리 누수를 왜 공용 훅으로 고쳤나요? 다른 방법은 없었나요?

**답변** `📁 내 경험`

**→ 문제:** Xcode Organizer 실사용자 **Peak Memory P95가 958.5MB**까지 올랐습니다. 원인은 화면이 사라져도 취소되지 않던 **Reanimated SharedValue**였습니다.

**→ 고른 것:** 언마운트 때 `cancelAnimation`을 한꺼번에 부르고, 사라진 뒤에는 콜백이 안 돌게 막는 **공용 훅**. 값 **24개**(온보딩 14 · 타이머 6 · 비교 4)에 적용해 **297.4MB**로 줄였습니다.

**→ 버린 대안 ① 화면마다 각자 useEffect cleanup** — 지금 고쳐도 **다음 사람이 빠뜨립니다.** 원래 구조가 그거였고, 그래서 샌 겁니다.

**→ 버린 대안 ② 애니메이션 라이브러리 교체** — 원인은 라이브러리가 아니라 **정리 누락**이었습니다. 교체 비용만 크고 같은 실수가 반복됩니다.

**→ 버린 대안 ③ 이미지 캐시 축소** — 처음엔 의심했지만 **줄여도 그래프가 그대로**였습니다. 측정으로 버렸습니다.

**→ 지금 다시 한다면:** 리뷰 에이전트에 **"SharedValue를 만들고 정리 훅에 등록 안 하면 경고"** 항목을 넣어서 **다시는 안 생기게** 합니다. **[ 실제로 넣었는지 ]**

### Q10. 콜드 스타트를 줄이려고 넣은 지연 로딩을 왜 다시 뺐나요?

**답변** `📁 내 경험` — **"측정이 내 판단을 뒤집은" 사례라 이 회사에 특히 좋습니다.**

**→ 문제:** 앱 시작이 느렸습니다. 시작 단계마다 마커를 찍어 **n=10 중앙값·p95**로 쟀습니다.

**→ 고른 것:** 화면 **62개를 React.lazy**로 바꿔 시작 때 JS가 덜 읽게 했습니다. Debug 기준 **Splash 초기화 -24.4%, JS 총 로딩 -21.8%** 였습니다.

**→ 그런데 뺐습니다.** 프로덕션 단계별 시간을 **Amplitude로 보내는 telemetry**를 같이 만들었는데, 실사용 데이터를 보니 **화면 전환마다 Suspense·스켈레톤 비용**이 생겼고, 그게 시작 시간 이득보다 컸습니다.

**→ 남긴 것:** 측정 체계와 telemetry는 그대로 뒀습니다. **다음 최적화도 같은 자로 재기 위해서**입니다.

**→ "다른 대안은?"** 화면 전체가 아니라 **무거운 화면 몇 개만** 지연 로딩하거나, 첫 화면 이후 **유휴 시간에 미리 불러오는(prefetch)** 방식이 있습니다. **[ 검토했는지 ]**

### Q11. CodePush 서버를 왜 직접 안 띄우고 S3 + CloudFront로 했나요?

**답변** `📁 내 경험`

**→ 문제:** App Center가 종료되면서 **CodePush를 대신할 배포처**가 필요했습니다.

**→ 고른 것:** 오픈소스 CodePush **클라이언트는 그대로**, 번들과 배포 정보는 **S3에 올리고 CloudFront로** 내려줬습니다. **돌아가는 서버가 없습니다.**

**→ 버린 대안 ① CodePush 서버 직접 운영** — 서버를 띄우면 **장애·보안·업데이트를 계속 돌봐야** 합니다. 작은 팀에 운영 부담이 컸습니다.

**→ 버린 대안 ② Expo Updates(EAS Update)로 이전** — bare RN 앱이라 **[ 이전 비용 — 예: 네이티브 설정 변경, 유료 요금 ]** 이 컸습니다.

**→ 만들다가 막은 구멍:** 배포 정보를 **CloudFront 캐시에서 읽으면** 오래된 캐시 때문에 기록이 비어 보일 수 있습니다. 그래서 **항상 S3 원본에서 읽고, 기존 기록이 빠지면 쓰지 않게** 했습니다.

**→ 배포·롤백은 GitHub Actions 버튼 하나**입니다. 롤아웃 비율과 강제 업데이트 옵션이 있습니다.

**→ "사용자가 S3에 직접 접근하나요?"** 아닙니다. **S3는 원본, 사용자는 CloudFront에서만** 받습니다. ([27번](./27_wrtn_review.md) Q11 — 이번엔 **"서버 없음"으로 끝까지** 일관되게)

### Q12. 상태 관리 — 왜 MobX에서 Zustand로, 왜 서버 상태는 React Query로 옮겼나요?

**답변** `📁 내 경험`

**→ 같은 데이터가 두 곳에 있어서 생기는 버그를 없애려고, 서버 데이터는 React Query가, 앱 안 상태는 Zustand가 갖게 나눴습니다.**

**→ 서버 상태를 스토어로 복사하던 구조를 걷어냈습니다.** 복사본이 있으면 **어느 쪽이 최신인지** 맞추는 코드가 따로 필요해집니다.

**→ 구독 상태 판단을 selector 하나로 모았습니다.** **60개 호출 지점**이 각자 조건을 쓰다 보니 **화면마다 결과가 달랐습니다.**

**→ MobX → Zustand 마이그레이션은 안전장치부터 만들었습니다.** **완료 플래그로 한 번만** 실행하고, 실패해도 앱이 멈추지 않게 **예외를 격리하고 리포팅만** 했습니다.

**→ "왜 Redux가 아니라 Zustand?"** 스토어가 **21개**였고 대부분 작은 단위였습니다. Redux는 액션·리듀서 구조가 무겁고, Zustand는 **필요한 값만 구독**해서 리렌더가 적습니다. **[ 팀이 Zustand를 고른 실제 이유 ]**

**→ "Redux는 써 봤나요?"** 페이히어에서 **Redux Thunk · Saga · Toolkit**을 썼습니다. 공고 스택에 Redux도 있으니 **둘 다 써 봤고 차이를 안다**고 말합니다.

### Q13. 앱과 위젯의 데이터 동기화는 왜 그렇게 설계했나요?

```
[앱에서 바꿀 때]
Zustand 변경 → Shared Storage(App Group / DataStore) → 위젯 다시 그리기 → Firestore 순차 반영

[위젯에서 바꿀 때]
위젯 체크 → Shared Storage(항목별 수정 시각) → 앱 열 때 병합 → Firestore 순차 반영
```

**→ 왜 위젯이 Firestore에 직접 안 쓰나.** 위젯은 **실행 시간이 짧고 네트워크가 보장되지 않습니다.** 기기 저장소에만 쓰고 서버 반영은 **앱이 맡게** 나눴습니다.

**→ 충돌은 항목 단위 수정 시각으로 풀었습니다.** 앱과 위젯이 같은 항목을 동시에 고치면 **더 늦게 고친 쪽**을 살립니다.

**→ 버린 대안:** 문서 단위로 통째 덮어쓰기 — **다른 항목의 변경까지 지워집니다.** 그래서 **항목 단위**로 내렸습니다.

**→ 같은 계정의 다른 기기는?** Firestore가 원본이고 같은 수정 시각 규칙으로 병합합니다([27번](./27_wrtn_review.md) Q15).

### Q16. 앱 배포가 위험할 때 기능을 어떻게 안전하게 내보내나요? (Feature Flag · Versioning)

**→ 의료 서비스라면 더 중요합니다.** 진료·결제 흐름은 **플래그로 바로 끌 수 있어야** 합니다.

### Q17. 레거시 시스템을 분석하고 개선한 경험은요? 레거시에서 AI를 어떻게 쓰나요?

**→ 한 번에 갈아엎지 않고, 새로 쓰는 코드부터 깨끗하게 지키면서 건드린 곳만 고쳤습니다.**

**→ ① 품질 게이트:** 기존 타입 에러 **367개**는 그대로 두고 **편집한 파일 에러만** 막았습니다. 레거시가 **조금씩 줄어드는** 구조입니다.

**→ ② 상태 구조:** 서버 상태를 스토어에 복사하던 걸 **React Query로**, 구독 판단 **60곳을 selector 하나로** 모았습니다.

**→ ③ MobX → Zustand:** 완료 플래그 + 예외 격리로 **한 번만, 실패해도 앱이 안 멈추게** 옮겼습니다.

**→ ④ 위젯 무중단 교체:** Android 위젯 5종을 RemoteViews에서 Glance로 다시 짰는데, **Receiver 클래스명과 패키지 경로는 그대로** 둬서 **사용자 홈 화면의 위젯이 깨지지 않게** 했습니다.

**→ AI는 "읽기"에 먼저 씁니다.** 낯선 레거시는 **AI에게 구조를 설명하게 하고 → 내가 계획을 세우고 → 구현 → 검증** 순서입니다. 계획에서 이해가 안 되면 다음으로 안 넘어갑니다.

**→ "Python/Django 레거시도 볼 수 있나요?"** Django 실무는 없습니다. Python은 **자동매매 시스템(pandas·Docker·GCP)** 을 직접 운영해 봤고, API 계약을 읽고 **클라이언트에 필요한 변경을 제안하는 수준**은 바로 가능하다고 말합니다.

### Q18. 운영 중 장애는 어떻게 감지하고 대응했나요? (Sentry · Crashlytics)

**답변** `📁 내 경험`

**→ 크래시는 Crashlytics, JS 에러는 Sentry, 성능은 Xcode Organizer와 직접 만든 telemetry로 나눠 봤습니다.**

**→ Sentry에 CodePush 번들 버전을 같이 기록했습니다.** 그래야 **어느 OTA 번들에서 난 에러인지** 구분됩니다. catch 블록의 에러를 `captureException`으로 모으는 정리도 했습니다.

**→ 사례 ① Release에서만 앱 시작 4초 후 죽던 SIGABRT.** Sentry 스택에서 `facebook::jni`를 보고 **ProGuard가 JNI 클래스를 지운 것**을 찾아 keep 규칙으로 고쳤습니다.

**→ 사례 ② 콜드 스타트 크래시.** 시작 속도 때문에 SDK 초기화를 미뤘는데, **어트리뷰션 SDK가 첫 화면보다 늦게 초기화**되며 죽었습니다. 그 SDK만 `Application.onCreate()`로 당겼습니다.

**→ 사례 ③ ANR.** 이벤트 로깅 하나가 **분석 SDK 6개 + 저장소 작업 2개**를 동기로 돌려 메인 스레드를 **0.5~2초** 붙잡았습니다. `InteractionManager`로 화면을 다 그린 뒤로 미뤘습니다.

**→ "모니터링 자동화는요?"** **[ Slack 알림 연동 여부 ]**. 지금이라면 **새 릴리스에서 크래시 없는 사용자 비율이 기준 아래로 떨어지면** 알림이 오게 하겠습니다.

### Q19. 헬스케어 앱을 만들어 본 경험이 있나요?

**답변** `📁 내 경험` — **이 회사에서 가장 강한 카드입니다. 먼저 꺼내세요.**

**→ GLP-1 약물(위고비·마운자로 등) 사용자를 위한 복약 기록 앱 Cadence를 혼자 만들어 출시했습니다.**

**→ 약물을 데이터로 모델링했습니다.** **13종 약물**의 표준 증량 단계(예: 위고비 0.25 → 2.4mg)와 투여 주기를 데이터로 두고, **지금 단계와 다음 증량 시점**을 자동으로 계산합니다.

**→ 진료와 이어지게 만들었습니다.** 기간별 주사·체중·증상 기록을 **의사용 PDF 리포트**로 내보내 공유합니다.

**→ 건강 앱과 연동했습니다.** **Apple HealthKit · Android Health Connect**에서 체중·걸음 수·심박수·수면을 **사용자가 고른 것만** 읽습니다.

**→ 오프라인 우선입니다.** **SQLite가 원본**이고, 클라우드 동기화(Supabase)는 **사용자가 켤 때만** 합니다. 건강 기록은 **기기 밖으로 나가는 걸 사용자가 정하게** 했습니다.

**→ 조심한 점:** 약물 농도 곡선은 **교육용 근사치**라고 화면에 밝혔습니다. 의료 정보처럼 보이는 숫자는 **오해를 막는 문구**가 같이 가야 한다고 봤습니다.

### Q20. 의료 데이터처럼 민감한 정보를 앱에서 다룰 때 무엇을 조심하나요?

**답변** `🌐 개념 정리` + `📁 내 경험`

**→ 저장 · 전송 · 로그 세 곳에서 새지 않게 막습니다.**

**→ ① 저장:** 기기에 남기는 건 **최소한**만. 토큰·민감 값은 **Keychain / Keystore**(iOS·Android 보안 저장소)에, MMKV에 둔다면 **암호화 옵션**을 켭니다.

**→ ② 로그:** Sentry · Crashlytics · Mixpanel에 **이름·진단명·처방 내용이 섞여 들어가지 않게** 합니다. Sentry는 `beforeSend`에서 **민감 필드를 지우고**, 분석 이벤트에는 **ID만** 보냅니다. 의외로 **에러 메시지·요청 본문**으로 새는 경우가 많습니다.

**→ ③ 화면:** 앱 전환기 미리보기에 **진료 내용이 보이지 않게** 가리고, 필요하면 **스크린샷을 막습니다**(Android `FLAG_SECURE`).

**→ ④ 권한:** 건강 데이터는 **필요한 항목만, 필요한 순간에** 요청합니다. Cadence에서 HealthKit을 **선택 항목별로** 읽게 한 이유입니다.

**→ 법적 기준은 아는 만큼만:** 국내 개인정보보호법상 **건강 정보는 민감정보**라 별도 동의가 필요합니다. 세부 기준은 **회사 보안·법무 가이드를 따르겠다**고 말합니다.

### Q21. 비대면 진료 앱에서 프론트엔드가 가장 어려운 부분은 뭐라고 보나요?

**답변** `🌐 개념 정리` — **써 보고 가면 이 답이 훨씬 강해집니다.**

**→ 여러 사람(환자 · 의사 · 약사)의 상태가 실시간으로 바뀌는 흐름을, 끊김 없이 한 화면에 보여주는 것이라고 봅니다.**

**→ ① 상태가 많은 흐름:** 접수 → 대기 → 진료 → 처방 → 결제 → 약국 → 배송. **중간에 앱을 꺼도** 다시 열면 **정확한 단계로 돌아와야** 합니다. 서버를 원본으로 두고 앱은 **다시 받아 그리는** 구조가 맞다고 봅니다.

**→ ② 실시간 알림:** 의사가 호출하면 **앱이 꺼져 있어도** 알아야 합니다. 푸시 → 탭 → **정확한 화면으로 이동**(딥링크)이 끊기면 진료를 놓칩니다. 루티너리에서 **Android 12·13의 알림 조건** 때문에 탭 이동이 안 되던 걸 고친 경험이 있습니다([26번 Q12](./26_wrtn_interview.md)).

**→ ③ 결제:** 진료비·약값은 **진료가 끝난 뒤** 확정되기도 합니다. 결제 실패 · 중복 결제를 막으려면 **서버 기준 상태**와 **같은 요청을 두 번 보내도 한 번만 처리되는 구조(멱등)** 가 필요합니다.

**→ ④ 앱 · 웹 · 데스크톱:** 환자는 앱, 의사·약사는 **웹이나 데스크톱**을 쓸 가능성이 큽니다. **[ 커피챗에서 데스크톱(Electron)을 누가 쓰는지 확인 ]**

**→ "실시간은 어떻게 연결하나요?"** 페이히어에서 **Pusher 실시간 채널로 매장 앱과 고객 앱의 결제 이벤트를 맞춘** 경험이 있습니다. 연결이 끊겼다 붙으면 **놓친 이벤트를 서버에서 다시 받아** 맞추는 게 핵심입니다.

### Q22. MAU 100만 앱에서 대규모 이벤트·마케팅 트래픽에 프론트엔드는 무엇을 준비하나요?

**답변** `🌐 개념 정리` + `📁 내 경험` — **공고 우대사항입니다.**

**→ 몰릴 때 서버를 덜 부르고, 실패해도 앱이 멈추지 않게 합니다.**

**→ ① 덜 부르기:** React Query **캐시와 staleTime**으로 같은 요청을 반복하지 않습니다. 정적인 건 **CDN**(CloudFront · Cloud CDN)으로 내립니다.

**→ ② 한꺼번에 몰리지 않게:** 푸시를 한 번에 보내면 **모든 앱이 같은 순간에** 서버를 부릅니다. 재시도는 **간격을 늘리고 무작위로 흩어서**(exponential backoff + jitter) 합니다.

**→ ③ 실패해도 동작:** 이벤트 배너가 안 떠도 **진료 흐름은 막히지 않게** 영역을 나눕니다. 루티너리에서 **광고 로딩 실패 시 팝업이 무한 대기하던 걸** 타임아웃·취소 버튼으로 고친 게 같은 원칙입니다.

**→ ④ 끄는 스위치:** 이벤트 기능은 **Remote Config로 바로 끌 수 있게** 내보냅니다(Q16).

**→ 정직하게:** 루티너리는 사용자는 많았지만 **이벤트 트래픽 대응을 제가 주도한 적은 없습니다.** 위 내용은 **설계 원칙**으로 말합니다.

## 6. 시스템 디자인 · 데이터

### Q23. "실험 친화적 아키텍처 — 만들기 쉽고 없애기도 쉬운 모듈"을 어떻게 설계하겠습니까?

**답변** `🌐 개념 정리` + `📁 내 경험` — **공고 문장 그대로라 나올 가능성이 큽니다.**

**→ 실험 기능은 한 폴더 안에 가두고, 입구는 플래그 하나로만 열리게 합니다. 지울 때 폴더 하나와 플래그 하나만 지우면 끝나야 합니다.**

**→ ① 경계:** 실험 기능은 **자기 폴더**(화면 · 훅 · API · 상태)에만 코드가 있습니다. 공통 코드가 실험 코드를 **import하지 않게** 합니다 — 반대 방향만 허용.

**→ ② 입구 하나:** 내비게이션 등록, 홈 배너 같은 **입구는 플래그로 감싼 한 곳**에만 둡니다.

**→ ③ 측정 내장:** 실험마다 **노출 · 클릭 · 전환 이벤트**를 같이 넣어, 결과를 보고 **남길지 지울지** 정합니다.

**→ ④ 지우는 날짜:** 플래그에 **주인과 만료일**을 적어 둡니다. 안 지운 플래그가 쌓이면 **그게 다음 레거시**입니다.

**→ 비슷한 경험:** 루티너리 **콜드 스타트 지연 로딩**을 넣었다가 데이터를 보고 **깔끔하게 뺀** 경험이 있습니다(Q10). 측정 체계는 남기고 기능만 걷어냈습니다.

### Q24. 데이터 모델링을 직접 해 본 경험이 있나요?

**답변** `📁 내 경험`

**→ 개인 프로젝트에서 SQLite · Postgres 스키마를 직접 설계했고, 회사에서는 Firestore 문서 구조와 동기화 규칙을 설계했습니다.**

**→ Cadence — SQLite를 원본으로, 테이블별 리포지토리로 접근을 격리했습니다.** Zustand는 **파생 상태만** 들고 있어서 같은 데이터가 두 곳에 생기지 않습니다.

**→ 스팟 스테이플러 — Supabase Postgres에 RLS를 걸었습니다.** 위치·구독·설정 **3개 테이블**에 "본인 행만 보이게" 규칙을 걸고, **pgTAP으로 정책을 테스트**했습니다. 신규 유저 설정은 **트리거로 자동 생성**합니다.

**→ 오프라인 큐 — 클라이언트가 만든 UUID로 멱등하게** 했습니다. 네트워크가 끊겼다 붙으면서 같은 요청이 두 번 가도 **한 번만 반영**됩니다.

**→ 루티너리 — 항목 단위 수정 시각**으로 앱·위젯·여러 기기의 충돌을 풀었습니다(Q13).

**→ "대용량 DB 최적화는요?"** **직접 해 본 적은 없습니다.** 인덱스·쿼리 계획(EXPLAIN)을 보는 수준의 개념은 알고, 실무에서는 **백엔드와 같이 보겠다**고 말합니다.

### Q25. 풀스택으로 문제를 푼 경험이 있나요?

**답변** `📁 내 경험`

**→ 개인 프로젝트에서는 인증 · DB · 서버 함수 · 배포까지 혼자 했습니다.**

**→ 회사에서는:** 루티너리 앱이 **Firestore에 직접** 읽고 쓰는 구조라, **DB 구조와 동기화 규칙**을 프론트엔드가 같이 설계했습니다.

## 7. 코드 리뷰 라운드 대비 — 실제 코드를 주고 리뷰시킵니다

> 후기: **"회사에서 사용 중인 코드를 주고 리뷰 + 개선점 토론. 이 과정에서 개념 질문도 같이."**
> **"시간이 굉장히 부족하므로 핵심 비즈니스 로직과 아키텍처 위주로 빠르게."**

### 리뷰 순서 — 5분 안에 이 순서로 말하세요

**→ ① 이 코드가 하는 일을 한 문장으로.** "진료 예약 목록을 불러와서 상태별로 보여주는 화면이네요." 이해했다는 걸 먼저 보여줍니다.

**→ ② 돈 · 데이터가 걸린 버그부터.** 결제 중복, 상태 꼬임, 경쟁 상태(race condition). **가장 비싼 문제**를 먼저 말합니다.

**→ ③ 구조.** 서버 상태와 클라이언트 상태가 섞였는지, 한 컴포넌트가 너무 많은 일을 하는지.

**→ ④ 성능.** 불필요한 리렌더, 리스트, 정리(cleanup) 누락.

**→ ⑤ 나머지(이름 · 타입 · 스타일)는 "작은 것들"로 묶어서** 한 문장으로 넘깁니다.

### React / React Native 코드에서 먼저 볼 것

| 볼 것 | 문제 신호 | 고치는 방향 |
|---|---|---|
| **useEffect 정리** | 구독·타이머·애니메이션·리스너를 만들고 return이 없음 | cleanup 반환. **루티너리 메모리 누수가 이것** |
| **경쟁 상태** | 비동기 응답이 늦게 와서 **옛 결과가 새 결과를 덮음**, 언마운트 뒤 setState | 취소 플래그 · AbortController · React Query로 이전 |
| **서버 상태 복사** | API 결과를 useState·스토어에 복사해 들고 있음 | React Query가 원본. **복사본은 동기화 버그** |
| **의존성 배열** | 빠졌거나, 매 렌더마다 새 객체·함수가 들어가 무한 실행 | 값으로 넣기 · useCallback · 로직을 effect 밖으로 |
| **파생 상태를 state로** | `filtered`, `total`을 따로 state로 관리 | 렌더 중 계산(필요하면 useMemo) |
| **결제 · 제출 버튼** | 두 번 누르면 두 번 요청 | 진행 중 잠금 + **서버 멱등 키** |
| **에러 처리** | `catch {}`로 삼킴, 사용자에게 아무것도 안 보임 | Sentry 기록 + **사용자에게 다음 행동** 안내 |
| **리스트** | ScrollView에 map, key가 index, renderItem 인라인 | FlatList/FlashList · 안정 key · memo |
| **타입** | `any`, `as` 남발, API 응답을 검증 없이 신뢰 | 응답 타입 정의 · 경계에서 검증(zod 등) |
| **민감 정보** | 로그·Sentry·분석 이벤트에 개인 정보 | 마스킹 · ID만 전송 (Q20) |

### 연습 — 이 코드를 2분 안에 리뷰해 보세요

```tsx
function ReservationScreen({ id }: { id: string }) {
  const [reservation, setReservation] = useState<any>(null);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    setLoading(true);
    api.getReservation(id).then((res) => {
      setReservation(res.data);
      setLoading(false);
    });
  }, []);

  const onPay = async () => {
    await api.pay(reservation.id, reservation.price);
    Alert.alert('결제 완료');
    navigation.goBack();
  };

  return (
    <View>
      {loading && <Spinner />}
      <Text>{reservation?.doctorName} · {reservation?.price}원</Text>
      <Button title="결제하기" onPress={onPay} />
    </View>
  );
}
```

**모범 답 — 비싼 순서로**

**→ ① 결제를 두 번 할 수 있습니다.** 버튼을 빨리 두 번 누르면 `api.pay`가 두 번 갑니다. **진행 중 버튼 잠금**과 **서버 멱등 키**가 필요합니다.

**→ ② 결제 금액을 앱이 보냅니다.** `price`를 클라이언트에서 넘기면 **조작될 수 있습니다.** 서버는 **예약 ID만 받고 금액은 서버가** 정해야 합니다.

**→ ③ 실패 처리가 없습니다.** `pay`가 실패하면 예외가 그냥 터지고 사용자는 **결제됐는지 모릅니다.** 실패 안내 + Sentry 기록 + **결과 재확인**이 필요합니다.

**→ ④ `id`가 바뀌어도 다시 안 불러옵니다.** 의존성 배열이 비어 있습니다. 그리고 응답이 늦게 오면 **화면을 떠난 뒤에도 setState**가 돕니다.

**→ ⑤ 구조:** 서버 데이터를 useState로 들고 있습니다. **`useQuery(['reservation', id])` + `useMutation`** 으로 바꾸면 ①의 잠금(`isPending`), ③의 에러, ④의 경쟁 상태가 같이 풀립니다.

**→ ⑥ 작은 것들:** `any` 타입, 로딩 중에도 버튼이 눌림, 가격 포맷.

### Q26. 메라키스럽게(열과 성을 다해) 일했던 프로젝트는 무엇인가요?

**→ 왜 했나:** 체크리스트가 앱 안에만 있어서, **앱을 열지 않고 홈 화면에서 바로 체크하게** 하자고 제안했습니다. 위젯은 **구독자 기능**이라 매출과도 바로 이어졌습니다.

**→ 어려웠던 것:** 앱과 위젯이 **같은 데이터를 동시에 고칠 수** 있었습니다. 그래서 **항목마다 수정 시각**을 두는 동기화 규칙을 직접 설계했습니다.

**→ 끝까지 간 것:** iOS는 **위젯에서 바로 체크되는 AppIntents**로, Android는 Glance로 만들었고, 그 김에 **기존 Android 위젯 5종도 사용자 위젯이 안 깨지게** 새 방식으로 옮겼습니다.

**→ "열과 성"을 보여줄 한 문장:** **[ 이 프로젝트에서 남들이 안 해도 될 걸 내가 한 것 하나 — 예: 주말 실기기 테스트, 엣지 케이스 정리 문서 ]**

### Q27. 일처리 속도는 어느 정도인가요? 빠르게 일하기 위해 무엇을 하나요? (3번 나올 수 있음)

**답변** `📁 내 경험` — **같은 질문이 각도를 바꿔 세 번 나옵니다. 세 가지 답을 다 준비하세요.**

**→ ① 결과로:** **2026년 상반기 5개월 동안 앱·웹 3개를 기획부터 출시까지** 끝냈습니다. **[ 가장 빨랐던 것 — 예: 찍고가 n주 ]**

**→ ② 방법으로:** 빠른 비결은 **되돌아오는 일을 없애는 것**입니다. AI로 코드를 빨리 쓰는 것보다, **타입·린트를 기계가 막아서 리뷰에서 돌아오는 횟수**를 줄이는 게 더 빨랐습니다.

**→ ③ 판단으로:** 처음부터 완벽하게 안 만듭니다. **먼저 작게 내고, 측정하고, 고칩니다.** 콜드 스타트 지연 로딩도 **넣고 → 재고 → 뺐습니다.**

**→ "빠르게 하다가 품질이 떨어지면요?"** 그래서 **빠르게 가도 되는 곳과 아닌 곳을 나눕니다.** 실험 기능은 빠르게, **결제·진료 데이터는 느리더라도 확실하게** 갑니다.

**→ "구체적으로 하루에 몇 개 PR?"** **[ 실제 숫자 ]** — 모르면 지어내지 말고 **"PR 수를 센 적은 없습니다. 대신 이번 주에 끝낸 걸 말씀드리면…"** 으로 바꿉니다.
