### Q4. 메모리를 69% 줄였다는데 어떻게 하셨나요?

> 근거: 후기 2023/09 · 2024/03 · 이력서 "Peak Memory(P95): 958.5MB → 297.4MB (-69%)"

**→ 실사용자 지표에서 튀는 구간을 찾고, 원인을 고친 뒤 같은 지표로 다시 쟀습니다.**

```
찾기  : Xcode Organizer 실사용자 지표에서 Peak Memory P95가 높은 걸 확인
고치기: 원인 수정 (보충: SharedValue 정리 누락 → 언마운트 때 정리하는 공용 훅)
확인  : 같은 지표로 재측정 → P95 958.5 → 297.4MB (-69%)
```

**→ 배운 점은 "재고, 고치고, 같은 방법으로 다시 잰다"입니다.** P95는 "사용자 20명 중 19명이 이 값 이하"라서 평균에 안 보이는 무거운 사용자를 봅니다.

**→ 한계:** 이력서에는 원인이 적혀 있지 않습니다. 위 "보충" 줄은 코드로 확인한 저장소 이력서 기준이니 면접에서 원인을 물으면 이쪽으로 답합니다.

# 3. 이력서 확인 — 프로젝트 · AI

### Q12. LLM 자동매매는 어떤 시스템이고, 왜 LLM에 거부권만 줬나요?

> 근거: 이력서 "LLM 검증형 암호화폐 선물 자동매매 시스템 (OKX), 2026.08~09" · 공고(AI-Native) · 추정(회의론자 질문)

**→ 돈이 걸린 판단이라 LLM이 틀리거나 응답하지 않아도 손실이 나지 않게, LLM의 권한을 "이 진입이 유효한가"로 줄였습니다.**

```
지표 신호(코드가 생성) → 있을 때만 LLM 호출 → 유효? 확신도 기준 이상?
   → 아니면 진입 취소 / 응답 실패·형식 오류도 "진입 안 함"
방향·손절가·목표가·주문 금액은 전부 코드가 결정
```

**→ 실패 방향을 정해 뒀습니다.** 진입 판단이 실패하면 진입하지 않고, 보유 중 재평가가 실패하면 강제 청산하지 않고 유지합니다. 주문에 손절 · 익절을 함께 걸어 거래소가 마지막 방어선을 맡습니다. 일일 손실 한도에 닿으면 kill-switch로 신규 진입을 막습니다.

**→ 한계:** 개인 프로젝트이고 사용자 제품이 아닙니다. 수익 성과는 이력서에 없어서 말하지 않습니다. **[ 실제 운용 여부 · 결과 ]**

# 부록. 이력서 한 줄 깊이 파기

### Q23. FCM과 Notifee 기반 전략 알림을 구현하셨다고 했는데, 구체적으로 설명해 주세요.

> 근거: 이력서 "FCM + Notifee 기반 전략 트리거 알림 구현, 앱 상태(포그라운드/백그라운드/종료)에 관계없이 일관된 알림 수신 보장" (메이크델타 · TraderKat 코드로 확인) · 후기 2025/10 (기술 선택 꼬리 질문)

**→ FCM으로 받은 푸시를 Notifee로 직접 그려서, 앱 상태 세 가지가 같은 표시 함수를 타게 했습니다.**

```
FCM 수신 ─ 포그라운드: onMessage ───────┐
         ─ 백그라운드·종료: setBackgroundMessageHandler ─┤→ 표시 함수
                                         │   (권한 → 채널 생성 → Notifee로 표시)
알림 탭 ─ 포그라운드: onForegroundEvent → 사용자가 고른 화면으로 이동
        ─ 백그라운드: onBackgroundEvent → 딥링크로 앱 열기
```

**→ 수신 경로를 하나로 합쳤습니다.** 백그라운드 핸들러는 앱 화면보다 먼저 실행되는 초기화에서 등록하고, 화면 없이 JS만 깨어날 때(headless)는 UI를 그리지 않습니다. 세 상태 모두 같은 표시 함수를 거쳐서 소리 · 중요도 설정이 상태마다 달라지지 않습니다.

**→ 사용자 설정을 알림에 반영했습니다.** 소리 4종을 고를 수 있고, 소리 이름을 채널 ID로 써서 채널을 소리별로 만듭니다(Android는 채널 생성 후 소리를 바꿀 수 없어서). 알림을 누르면 알림 내역 · 거래소 · 차트 · 홈 중 사용자가 고른 곳으로 가며, 알림 데이터의 `market`과 `code`로 해당 종목에 연결합니다. 토큰은 온보딩 · 로그인에서 권한을 요청한 뒤 받아 로그인 때 서버에 보냅니다.

**→ 실제로 부딪힌 문제 둘:** ① Notifee와 Firebase를 함께 쓰면 Android에서 알림을 지울 때 빈 알림이 뜨는 알려진 이슈가 있어, `sentTime`과 `ttl`이 모두 0이면 무시하는 임시 조치를 넣었습니다(코드 주석에 이슈 링크). ② Android에서 표시 중인 알림이 24개를 넘으면 한꺼번에 지웁니다.

**→ 한계를 먼저 말합니다. 이력서의 "일관된 알림 수신 보장"은 과장으로 읽힙니다.** 사용자가 앱을 강제 종료하면 FCM이 앱을 깨우지 못하는 경우가 있고, 전달 실패 재시도나 수신율 측정 코드는 없습니다. "세 상태에서 같은 표시 경로를 쓰도록 통일했다"까지만 말하고 "보장"은 쓰지 마세요. 푸시 payload가 `notification` 필드인지 data 전용인지도 서버 쪽 확인이 필요합니다. **[ 서버가 보내는 payload 형태 ]**

**→ 꼬리 질문 셋:**
- **"종료 상태에서 알림을 눌러 앱을 열면요?"** 시작 때 `getInitialNotification()`을 호출하지만 결과를 쓰지 않고 에러만 로그로 남깁니다. 종료 상태 탭 후 정확한 화면으로 이동하는 처리는 코드로 확인되지 않으니 모르면 그렇게 말합니다.
- **"왜 FCM 기본 표시를 안 쓰고 Notifee로 다시 그렸나요?"** 소리 · 채널 · 탭 데이터를 앱이 통제하려는 선택입니다. **[ 당시 실제 이유 ]**
- **"개선한다면?"** 알림 탭 리스너와 FCM 수신 리스너 둘 다 정리(해제) 코드가 없어서, 설정이나 권한 상태가 바뀔 때마다 리스너가 쌓여 이동이 두 번 일어날 수 있다고 의심합니다. 코드만 보고 한 추정이며 재현은 못 했습니다.
