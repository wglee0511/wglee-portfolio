**→ 대안 질문에는 "비교해 봤다"와 "이 상황에선 이유가 있어 택하지 않았다"를 구분해서 답합니다.** 실제로 해 본 비교만 "해 봤다"고 말하고, 나머지는 "이런 이유로 맞지 않았다"로 말합니다. 이 문서의 대안은 대부분 후자이고, 실제로 비교한 것은 `[ ]`로 비워 뒀습니다.

# 2. 루티너리 — 왜 그렇게 정했나, 대안은, 어려움은

### Q2. 메모리(P95)를 69% 줄였다는데 어떻게 하셨나요?

> 근거: 이력서 "Peak Memory(P95): 958.5MB → 297.4MB (-69%)" · 코드(커밋 기록 2025-12-31) · 후기 2023/09 · 2024/03

**→ 메모리 누수의 원인인 "애니메이션 값 정리 누락"을 공용 훅으로 고쳤고, 효과는 Android 네이티브 힙으로 확인했습니다. 이력서의 -69%는 iOS 실사용자 지표(P95)입니다.**

```
고친 것: 화면이 사라진 뒤에도 남는 애니메이션 값(SharedValue)을 공용 훅 하나로 정리 (24개 등록)
확인   : Android 네이티브 힙 계측 101.9 → 31.2MB (-69%)
이력서 : Xcode Organizer 실사용자 지표 P95 958.5 → 297.4MB (-69%)
```

**→ 한계:** 두 숫자는 서로 다른 측정입니다. 같은 -69%라 면접관이 먼저 짚을 수 있고, iOS P95가 이 수정으로 줄었는지는 **[ 확인한 근거 ]**. 근거가 없으면 "두 측정이고, iOS 쪽 인과는 확인 중"이라고 말합니다.

**↳ 꼬리 1. 왜 그게 원인이라고 판단했나요?**

**→ Android 네이티브 힙 계측으로 좁혔습니다.** 애니메이션 값이 많은 화면(온보딩 슬라이드 · 타이머 · 비교 애니메이션)부터 고쳤고, 같은 계측에서 남은 크기가 31.2 → 11.0MB로 줄어 원인이 맞았다고 확인했습니다.

**↳ 꼬리 2. 다른 방법은 없었나요?**

**→ 화면마다 따로 정리하던 기존 방식이 문제였습니다.** 정리 코드가 화면마다 있으면 하나만 빠져도 새는데, 훅 하나로 통일하면 새 화면도 같은 규칙을 씁니다. 애니메이션을 줄이거나 라이브러리를 올리는 방법도 있지만 이번엔 정리 누락이 원인이라 맞지 않았습니다. **[ 실제로 비교해 본 다른 방법 ]**

**↳ 꼬리 3. 가장 어려웠던 점은요?**

**→ 시간이 지나며 서서히 늘고, 특정 동작에서만 새는 것을 분리하는 일이었습니다.** 타임라인 뷰를 켤 때마다 약 20MB가 돌아오지 않았는데, 무거운 화면을 삼항 분기로 매번 통째로 다시 만들고 있었습니다. 필요할 때만 만들고 계속 살려 두는 방식(lazy mount + keep-alive)으로 고쳤습니다. (PDF에는 없고 저장소 이력서에 있는 내용이니 말하려면 근거 숫자를 준비하세요.)

**↳ 꼬리 4. 다시 한다면?**

**→ 플랫폼별로 측정 기록을 따로 남기겠습니다.** 지금은 iOS 지표와 Android 계측이 섞여 보이는데, 처음부터 구분해 두면 어느 수정이 어느 숫자를 움직였는지 바로 답할 수 있습니다.

### Q3. 앱 초기 실행 시간(P50) 540ms → 400ms는 무엇을 바꿔서 줄었나요?

> 근거: 이력서 "Launch Time(P50): 540ms → 400ms (-26%)" · 코드(커밋 2025-11-21 초기화 정리 = 팀원 작업, 2025-11-25 루트 구조 정리 = 본인 · 지연 로딩 2026-05 도입 → 2026-06 제거) · 후기 2025/10

**→ 앱 시작 때 하던 초기화를 정리해서 줄었다고 봅니다. 다만 어느 변경이 몇 ms인지는 나눠서 재 보지 않았습니다.**

```
전: 초기화(버전 확인·언어 설정·보정 작업 등)가 App과 별도 컴포넌트 여러 곳에 흩어짐
후: 단계별 훅으로 나눠 필요한 때만 실행, 스플래시를 먼저 내리고 언어 설정은 뒤로
    + 루트 화면 구조를 한 겹 줄임
```

**→ 두 단계였고, 앞은 팀 작업, 뒤는 제 작업입니다.** 팀원이 초기화를 훅으로 나눴고(11/21), 저는 이어서 초기화 전용 컴포넌트를 걷어내고 App에서 바로 화면을 그리게 정리했습니다(11/25).

**→ 한계:** 두 변경이 들어간 릴리스의 Organizer 수치를 분리해서 재지 않았습니다. **[ 두 변경이 들어간 릴리스 버전의 Organizer 수치 ]**

**↳ 꼬리 1. 지연 로딩은 왜 넣었다가 뺐나요?**

**→ 측정해서 넣었고, 더 큰 측정을 보고 뺐습니다.** 화면 62개를 지연 로딩(React.lazy)으로 바꿔 Debug 빌드에서 Splash 초기화 -24.4%, JS 로딩 -21.8%를 확인했습니다(워밍업 제외 10회 중앙값 · p95). 그런데 프로덕션 시작 단계별 시간을 Amplitude로 보내 보니 화면 전환 때 Suspense · 스켈레톤이 드는 비용이 시작에서 번 시간보다 크다고 판단해 제거했습니다. 측정 체계와 telemetry는 남겼습니다.

**↳ 꼬리 2. 다른 대안은 없었나요?**

**→ 일부 화면만 지연 로딩하는 방법과, 번들 자체를 줄이는 방법이 있습니다.** 이번에는 전체를 바꿔 보고 지표로 거둬들였습니다. **[ 일부 화면만 해 보는 걸 검토했는지 ]**

**↳ 꼬리 3. 가장 어려웠던 점은요?**

**→ Debug 빌드 수치와 프로덕션 수치가 다르다는 점이었습니다.** 그래서 개발 중 계측과 별개로 실사용자 단계별 telemetry를 만들었고, 이 telemetry가 "되돌리자"는 판단의 근거가 됐습니다.

**↳ 꼬리 4. 그럼 540→400은 무엇 때문인가요?**

**→ 시기상 가장 유력한 후보까지만 말합니다.** 지연 로딩은 이 숫자보다 뒤에 넣고 뺐으므로 원인이 아닙니다. 초기화 정리 두 건 중 무엇이 얼마인지는 분리해서 재지 않았습니다.

### Q4. 상태 관리 구조를 바꿨다고 했는데, 왜 그렇게 하셨나요?

> 근거: 이력서 "React Query가 서버 상태를 소유, Zustand는 구독 단위를 필요한 값으로 좁혀… 스토어 21개의 중복 통합 및 computed 기반 파생 상태" · 저장소 이력서(MobX→Zustand 마이그레이션, 구독 판단 selector 60곳 중앙화)

**→ 서버에서 온 데이터는 React Query가, 기기 안 상태는 Zustand가 맡게 나눠서, 같은 데이터가 두 곳에 있어 어긋나던 구조를 없앴습니다.**

```
전: 서버 데이터를 스토어에 복사해서 보관 (서버 값과 스토어 값이 따로 놂)
후: 서버 상태 = React Query 한 곳 / 기기 상태 = Zustand, 필요한 값만 구독
    스토어 21개의 중복 통합, 정렬·전개 목록은 저장하지 않고 계산 (목록 갱신 set 3회 → 1회)
```

**→ 한계:** 리렌더링이 몇 % 줄었는지 숫자는 없습니다. 구조 정리의 결과로 말합니다.

**↳ 꼬리 1. 왜 서버 상태를 스토어에서 걷어냈나요?**

**→ 복사본은 반드시 어긋나기 때문입니다.** 서버가 바뀌면 스토어도 따로 고쳐야 하고, 하나라도 빠지면 화면마다 다른 값이 보입니다. 원본이 한 곳이면 갱신도 한 곳입니다.

**↳ 꼬리 2. 왜 MobX를 두고 Zustand로 옮겼나요? 다른 대안은요?**

**→ 이 질문은 이력서에 이유가 없어서 본인 답이 필요합니다.** 이력서의 사용 기술에 MobX와 Zustand가 같이 있어 일부만 옮긴 것으로 보입니다. **[ 옮긴 이유 한 문장 + 옮기지 않은 부분과 그 이유 ]** 대안은 MobX 유지, Redux Toolkit(페이히어에서 써 본 것), Jotai가 있고, 어느 것을 실제로 비교했는지도 **[ ]**.

**↳ 꼬리 3. 마이그레이션에서 가장 무서웠던 건요?**

**→ 사용자 기기에 이미 저장된 데이터가 깨지는 것이었습니다.** 마이그레이션은 완료 표시로 한 번만 실행하고, 실패해도 앱이 멈추지 않게 예외를 막아 리포팅만 하게 했습니다. 스토어마다 저장 구조의 버전을 두어 앞으로 바뀌어도 이어 받게 했습니다.

### Q5. 앱과 위젯 데이터가 어긋나지 않게 어떻게 하셨나요?

> 근거: 이력서 "Zustand 스토어 변경 → Shared Storage → 앱 진입 시 데이터 병합 → Firestore 순차 동기화" · "수정 시각 기반 item 단위 충돌 해결" · 코드(커밋 기록 2026-03-17 race condition 수정)

**→ 위젯은 기기 저장소에만 쓰고, 서버 반영은 앱이 맡게 나눴습니다. 동시에 고치면 항목별로 수정 시각이 늦은 쪽이 이깁니다.**

```

```

**↳ 꼬리 2. 충돌 해결은 왜 "수정 시각이 늦은 쪽"인가요? 다른 대안은요?**

**→ 체크리스트는 항목 하나를 켜고 끄는 단순한 변경이라 마지막 수정이 이기면 충분하다고 봤습니다.** 목록 전체를 덮어쓰면 한쪽이 고친 다른 항목이 사라져서 항목 단위로 비교합니다. 대안은 서버 시각 기준 또는 충돌을 합치는 구조(CRDT)인데, 이 규모엔 과하다고 말합니다.

**↳ 꼬리 4. 다시 한다면?**

**→ 앱이 꺼져 있어도 서버에 반영되게 하겠습니다.** 지금은 앱을 열어야 병합되는데, 푸시로 앱을 잠깐 깨우거나(Android FCM data 메시지, iOS 조용한 푸시) 서버가 병합하는 방식을 검토하겠습니다. 루티너리에서 이걸 실제로 쓰는지는 **[ ]**.

**↳ 꼬리 2. 가장 어려웠던 점은요?**

**→ 디자이너와 개발자의 약속을 만드는 일이었습니다.** 토큰 정의 → 컴포넌트 스펙 → 코드 구현 순서를 정해 놓고 진행했습니다. **[ 디자이너와 의견이 갈렸던 한 건과 정한 방법 ]**

# 5. 개인 프로젝트 — 설계 문서가 근거입니다

> 아래 네 프로젝트는 설계 문서(spec · ADR)가 저장소에 남아 있어, "왜 정했는지"를 문서로 증명할 수 있습니다.

### Q13. LLM 자동매매는 어떤 시스템이고, 왜 LLM에 거부권만 줬나요?

> 근거: 이력서 "LLM 검증형 암호화폐 선물 자동매매 시스템 (OKX), 2026.08~09" · 설계문서(`okx-trade` 2026-08-17 설계 확정표, 2026-08-18 라이브 전략 교체) · 공고(AI-Native)

**→ 돈이 걸린 판단이라 LLM이 틀리거나 응답하지 않아도 손실이 나지 않게, LLM의 권한을 "이 진입이 유효한가"로 줄였습니다.**

```
지표 신호(코드가 생성) → 있을 때만 LLM 호출 → 유효? 확신도 기준 이상?
   → 아니면 진입 취소 / 응답 실패·형식 오류도 "진입 안 함"
방향·손절가·목표가·주문 금액은 전부 코드가 결정
```

**→ 한계:** 개인 프로젝트이고 사용자 제품이 아닙니다. **[ 실제 운용 여부 · 결과 ]**

**↳ 꼬리 1. 왜 코드 신호 + LLM의 하이브리드인가요?**

**→ 설계 문서에 적은 이유 그대로 "규칙의 객관성 + LLM의 맥락 판단"입니다.** 규칙만으로는 맥락을 못 보고, LLM만으로는 검증이 안 됩니다. 그래서 신호는 코드가 만들고, LLM은 마지막에 걸러 내는 역할만 맡습니다.

**↳ 꼬리 2. 왜 파이프라인 구조인가요? 다른 대안은요?**

**→ 설계 문서의 이유는 "단계별 독립 검증 · 차단이 자동 실거래에 필수"입니다.** 모든 주문은 위험 관리 단계를 반드시 거치는 유일한 문이 있고, 데이터 수집과 분석을 분리해 데이터 소스가 바뀌어도 분석이 흔들리지 않게 했습니다. 대안은 LLM이 전부 결정하는 에이전트 한 덩어리이지만, 틀렸을 때 어디서 막을지가 없어서 택하지 않았습니다.

**↳ 꼬리 3. LLM 쪽에서 가장 어려웠던 점은요?**

**→ LLM의 출력 형식을 믿을 수 없다는 점이었습니다.** 제공자 4종을 설정 하나로 바꾸게 하고 JSON 스키마로 출력을 강제했으며, 스키마를 제대로 지원하지 않는 로컬 모델은 대체 방식을 쓰고 설명이 섞이면 필요한 부분만 뽑습니다. 형식이 틀려도 "진입 안 함"입니다.

**↳ 꼬리 4. 전략은 실제로 돈이 됐나요?**

**→ 솔직히 아직 입증하지 못했습니다.** 설계 문서에 "극적 개선 기대 어려움"이라고 적었고, 백테스트에서 새 전략은 5일에 2건, 기존 전략은 0건으로 신호가 거의 안 나왔습니다. 그래서 전략을 설정 하나로 되돌릴 수 있게 만들었습니다. 이 프로젝트의 가치는 수익이 아니라 "LLM이 틀려도 안전한 구조"입니다. **[ 실제 운용 결과 ]**

**↳ 꼬리 5. 테스트는 어떻게 했나요?**

**→ 464개 테스트에서 LLM 대신 가짜 응답과 예외를 넣었습니다.** 신호가 없으면 LLM을 부르지 않는지, 방향이 다르면 취소하는지, 오류가 나면 진입하지 않는지를 확인합니다. LLM의 똑똑함이 아니라 LLM 주변 로직을 검증하는 방식입니다.

### Q14. Cadence(복약 기록 앱)의 구조를 왜 그렇게 설계하셨나요?

> 근거: 이력서 "오프라인 퍼스트: SQLite를 진실의 원천 · 클라우드 동기화 last-write-wins · 옵트인" · 설계문서(`cadence` 인증·동기화 설계, 수익화 설계) · 후기 2024/03 · 공고(헬스케어)

**→ 기록의 원본은 기기의 SQLite이고, 서버 동기화는 사용자가 켤 때만 합니다. 로그인하지 않아도 모든 기능이 됩니다.**

```
기록(SQLite가 원본) → 증량 단계·다음 증량 시점 자동 계산 → 의사용 PDF 리포트
클라우드 동기화(Supabase)는 옵트인, 충돌은 수정 시각이 큰 쪽(last-write-wins)
```

**→ 한계:** 혼자 만든 앱이라 실제 의료진과 일한 경험은 아닙니다. **[ 사용자 수 · 다운로드 ]** 없으면 말하지 않습니다.

**↳ 꼬리 1. 왜 서버가 아니라 기기 DB가 원본인가요?**

**→ 설계 문서에 "로그인은 선택, 로그인 안 해도 전 기능 로컬 동작"으로 정했습니다.** 약 투여와 체중은 민감한 건강 기록이라, 서버에 올릴지를 사용자가 정하게 하는 쪽이 맞다고 봤습니다(이유는 문서의 결정과 연결한 설명). 오프라인에서도 기록이 되는 이점도 있습니다.

**↳ 꼬리 2. 동기화는 어떻게 설계했고, 다른 대안은 없었나요?**

**→ 바뀐 기록만 올리고, 마지막 동기화 이후 바뀐 서버 기록을 받고, 충돌은 수정 시각이 늦은 쪽을 씁니다.** 삭제는 지우지 않고 삭제 표시를 남겨 다른 기기에 전합니다. 설계 문서는 "로컬에 서버 아이디 열을 추가"와 "별도 매핑 테이블"을 비교해 열 추가를 택했습니다.

**→ 약점:** 같은 기록을 두 기기에서 동시에 고치면 한쪽이 사라집니다. 동시 수정이 드물어 단순한 방식으로 충분하다고 설명합니다(제 설명이지 문서의 이유는 아님). **[ 실제 이유 ]**

**↳ 꼬리 3. 메이크델타에서는 결제를 직접 붙였는데 여기선 왜 RevenueCat인가요?**

**→ 이유는 본인 답이 필요한 질문입니다.** 확인되는 것은 로그인하면 RevenueCat 사용자와 Supabase 사용자 ID를 묶어 기기를 바꿔도 구독이 이어지게 설계했다는 점입니다. **[ 직접 통합 대신 RevenueCat을 고른 이유 ]**

**↳ 꼬리 4. 광고는 왜 안 넣었나요?**

**→ 설계 문서의 가드레일에 "건강 앱 광고 리스크"를 적고 광고 SDK를 도입하지 않기로 확정했습니다.** 무료 사용자에게는 업셀 스트립만 둡니다. 게임인 Code Slugger에서는 광고를 쓴 것과 구분해서 설명합니다. 이 판단은 헬스케어 회사에서 신뢰를 주는 포인트입니다.

### Q15. 찍고가에서 지도 스택을 어떻게 골랐고, 직접 만든 건 무엇인가요?

> 근거: 이력서 "런타임 의존성 제로 · 경로→주유소 매칭 알고리즘 자체 구현 · KATEC→WGS84 변환 직접 구현" · 설계문서(`zzikgoga` ADR-001 지도 스택, 수익화 문서)

**→ 지도 · 경로 · 유가는 외부 API 4개를 조합했고, 직접 만든 건 "경로 위에서 200m 안 주유소를 찾는" 알고리즘입니다.**

```
경로 폴리라인을 8지점 샘플링 → 반경 검색 → 중복 제거
  → 폴리라인 최단거리 200m 이내만 (부족하면 500m) → 경로 이탈 시간·절약액 계산
```

**→ 한계:** 사용자 수 · 트래픽은 이력서에 없습니다.

**↳ 꼬리 1. 왜 카카오맵 + TMAP인가요?**

**→ ADR에 이유를 적었습니다.** 카카오맵은 무료 쿼터가 넉넉(지도 일 30만 건)하고 국내 레퍼런스가 많으며, TMAP은 경로 무료 쿼터가 일 1,000건으로 명시돼 있어 예측 가능합니다.

**↳ 꼬리 2. 다른 대안은 없었나요?**

**→ ADR의 "검토한 대안" 4개가 그대로 답입니다.** 카카오 단일은 길찾기 쿼터가 비공개, 네이버는 결제수단 등록 필요, Google은 한국 자동차 길찾기 미지원, MapLibre + OSRM은 서버를 직접 운영해야 해서 규모 대비 과함.

**↳ 꼬리 3. "런타임 의존성 제로"인데 지도 SDK는 쓰지 않나요?**

**→ npm 의존성이 next · react · react-dom 세 개뿐이라는 뜻입니다.** 카카오맵은 npm 패키지가 아니라 브라우저용 SDK입니다. 지도 · 차트 · 상태관리 · CSS 프레임워크 라이브러리를 쓰지 않았다는 의미로 말하고, 지도 SDK는 외부 서비스라고 먼저 밝힙니다.

**↳ 꼬리 4. 좌표 변환은 왜 직접 구현했나요?**

**→ 의존성을 없애려고 proj4와 같은 변환 정의를 직접 구현했습니다.** 코드 머리말에 "외부 의존성 없이 순수 구현(proj4 정의와 동일)"이라 적혀 있습니다. 다만 ADR에는 카카오 좌표변환 API(또는 proj4)를 쓰기로 적었으니, 면접관이 문서와 코드가 다르다고 물으면 바꾼 경위를 **[ 실제 이유 ]**로 답합니다.

**↳ 꼬리 5. 가장 어려웠던 점은요?**

**→ 무료 쿼터입니다.** 검색 한 번에 경로 대안 4종을 부르면 TMAP이 4건 소모되고 오피넷도 일 1,500건 제한이라 트래픽이 커지면 대안 수를 줄이거나 유료로 가야 합니다(수익화 문서에 적음). 광고 슬롯은 환경변수로 켜고 끄되 가격 정렬에는 개입하지 않게 분리했습니다.

### Q16. 앱 종료 상태의 알림과 서버 검증은 어떻게 설계하셨나요? (스팟 스테이플러 · Code Slugger)

> 근거: 이력서 "오프라인 큐: 클라이언트 생성 UUID 기반 멱등 · Supabase RLS + pgTAP · Edge Function에서 실제 코인 차감" · "앱 종료 상태 지오펜싱은 순수 함수로 분리해 단위 테스트"

**→ 클라이언트를 믿지 않는 부분은 서버(DB)가 막게 했고, 검증이 어려운 부분은 순수 함수로 떼어 테스트했습니다.**

```
오프라인 큐 : 네트워크 끊김 → 요청을 로컬에 쌓음 → 복귀 시 순서대로 전송 (UUID로 중복 실행 안전)
서버 검증   : 코인 차감은 Edge Function이 처리, 앱은 먼저 반영 후 실패하면 되돌림
접근 제어   : 테이블 3개에 행 단위 보안(RLS), pgTAP으로 정책 검증
```

**→ 한계:** 사용자 규모 · 실제 공격 사례는 없습니다.

**↳ 꼬리 1. 왜 UUID를 클라이언트가 만드나요?**

**→ 같은 요청이 두 번 가도 한 번만 반영되게 하려는 것입니다.** 오프라인에서는 서버가 아이디를 줄 수 없고, 재전송이 일어나면 서버가 같은 아이디를 보고 중복을 걸러냅니다. 대안은 서버가 아이디를 발급하는 방식인데, 오프라인에서 만든 항목에는 아직 아이디가 없습니다.

**↳ 꼬리 2. 왜 클라이언트 말고 서버에서 코인을 차감하나요?**

**→ 앱 코드는 사용자가 조작할 수 있기 때문입니다.** 화면에서 먼저 반영하는 낙관적 업데이트는 속도를 위한 것이고, 진짜 차감은 서버 함수가 하며 실패하면 앱이 되돌립니다.

**↳ 꼬리 3. 앱이 직접 DB를 부르는 구조에서 왜 RLS인가요?**

**→ 앱이 DB에 직접 요청하는 구조(Supabase)라 DB 자신이 마지막 방어선이어야 하기 때문입니다.** 사용자는 자기 행만 읽고 쓰게 정책을 걸고, pgTAP으로 정책이 실제로 막는지 테스트했습니다.

**↳ 꼬리 4. 앱 종료 상태 지오펜싱은 어떻게 검증했나요?**

**→ 실제 기기에서 재현하기 어려운 부분은 순수 함수로 떼어 단위 테스트했습니다.** 판단 로직은 함수로 분리해 테스트하고, OS가 앱을 깨우는 부분은 기기에서 확인해야 한다고 구분합니다. **[ 실기기 검증 방법 ]**

# 6. 공통 — AI 활용, 지원 동기, 역질문

### Q17. AI를 어떻게 쓰시나요? AI가 틀렸을 땐 어떻게 바로잡나요?

> 근거: 후기 2025/10 (AI 활용 질문) · 이력서 "AI 협업 워크플로: 17화면 → 7개 서브프로젝트, spec → plan → 구현 → 검증" · "코드 분석 → 계획 수립 → AI 피드백 사이클" · 추정(회의론자 질문)

**→ 믿지 않고 기계로 확인합니다.** 타입 검사 Hook, 크래시 패턴 리뷰 에이전트, 순수 함수 단위 테스트가 그 장치이고, 자동매매는 LLM 쪽을 "틀려도 손실이 안 나게" 설계했습니다.

**→ 사례로 답합니다.** **[ 시킨 일 → AI의 첫 답 → 내가 의심한 이유 → 확인 방법 → 실제 원인 ]** 안 떠오르면 iOS 알림 사례를 쓰세요. AI는 JS 렌더를 의심했지만 프로파일러에 문제가 없었고, 원인은 라이브러리가 메인 스레드에서 알림을 동기로 예약하던 것이었습니다([26번 Q8](./26_wrtn_interview.md)).

**→ 책임은 커밋한 사람에게 있습니다.** 설명 못 하는 코드는 넣지 않습니다. 그래서 Q2~Q16의 "왜"를 모두 제 말로 설명할 수 있어야 합니다.

**↳ 꼬리 1. 왜 문서(spec → plan)로 쪼개서 시키나요? 다른 방법은요?**

**→ 한 번에 시키면 AI가 중간에 방향을 잃고, 저도 검증할 단위가 없어서입니다.** 화면 17개를 서브프로젝트 7개로 나눠 각각 설계 문서 → 구현 계획 → 구현 → 검증으로 갔고(Cadence는 설계 11건 · 계획 10건, 스팟 스테이플러는 설계 14건 · 계획 13건), 문서가 저장소에 남아 AI가 매번 같은 기준을 봅니다. 대안은 대화로 바로 시키는 방식인데 빠르지만 근거가 남지 않습니다. 속도가 몇 배 빨라졌는지는 측정하지 않았습니다. **[ 문서 덕분에 막은 실수 한 건 ]**

**↳ 꼬리 2. 위젯 · Wear OS 같은 낯선 영역은 어떻게 단독으로 했나요?**

**→ 먼저 코드를 읽어 구조를 이해하고, 계획을 세운 뒤 AI에게 피드백을 받으며 구현했습니다. AI는 설계 파트너였습니다.** 결과물로 확인됩니다(Wear OS UI를 XML에서 100% Jetpack Compose로 전환). 네이티브 전문가는 아니라서 막힌 곳은 플랫폼 문서와 AI로 풀었다고 말합니다. **[ 가장 막혔던 순간 하나 ]**

### Q18. 왜 메라키플레이스인가요? 걱정되는 점은요?

> 근거: 후기 2025/10 (CTO가 지원을 신중히 고민해 달라고 당부) · 공고

**→ 지금 이 팀이 겪는 문제를 제가 해온 일로 바로 풀 수 있다고 봐서입니다.** 공고에 적힌 대로 MAU 100만에 매출이 약 7배로 크면서 레거시 위에서 속도를 유지해야 하는 시기이고, 저는 그 기반(크래시 · 성능 · 배포 · AI 검증 장치)을 실사용자 지표로 맡아 본 사람입니다. **[ 나만의닥터를 써 본 흐름과 불편했던 점 하나 ]**

**→ 걱정은 두 가지이고, 둘 다 메우는 방법까지 말합니다.** ① 의료 도메인 실무가 없습니다. Cadence로 복약 데이터를 다뤄 봤고 입사하면 진료 흐름을 따라가며 배우겠습니다. ② Django 실무가 없습니다. API 계약을 읽고 클라이언트에 필요한 변경을 제안하는 일은 바로 하지만, 서버 코드를 고치는 속도는 처음엔 느릴 것입니다. Supabase · Edge Function · Route Handler · Python 자동매매 경험을 근거로 듭니다.

### Q20. 입사 후 목표와 속도 대 품질, 그리고 성격은요? (짧게)

> 근거: 후기 2023/09 · 2024/04 · 2024/06 · 공고

**→ 목표:** 첫 3개월은 배포 · 모니터링 체계를 손에 익히고 그 안에 AI 검증 장치를 깔고, 1년 안에는 핵심 화면의 크래시 없는 사용자 비율 같은 지표를 팀이 같이 보게 하겠습니다.

**→ 속도 대 품질:** 되돌리기 쉬운 건 빨리 내고, 되돌리기 어려운 건(결제 · 데이터 이전 · 네이티브 변경) 느려도 확인합니다. 서버 검증(Q16)과 앱 종료 상태 테스트(Q16)가 그 예입니다.

**→ 성격:** 장점은 원인을 끝까지 측정하는 것(Q2~Q3), 단점은 긴장하면 말이 빨라지는 것이라 첫 문장에 결론 하나를 말합니다. **[ 최근 본 책 · 영화 하나 + 일에 가져온 생각 한 줄 ]**
