### Q5. AI가 만든 코드의 품질은 어떻게 보장하나요? 사람이 계속 봐야 하는 부담은요?

**→ 사람이 매번 확인하던 걸 기계가 강제하게 만들어서 부담을 줄였습니다.**

```
파일 수정 → ESLint 자동 수정
작업 종료 → 타입 검사 실패 시 못 끝남 (기존 에러 367개라 "편집한 파일"만 검사)
리뷰 에이전트 → 실제 났던 크래시 패턴 검사 (고치는 도구는 안 줌, 보고만)
```

**→ 규칙은 "가능하면", 훅은 "반드시"입니다.** 반드시 지킬 것만 훅으로 옮겼습니다.

**→ 제가 보는 건 둘로 줄었습니다.** "이 코드를 내가 설명할 수 있나"와 "실제 기기에서 맞나". 결제처럼 되돌리기 어려운 코드는 PR에 따로 표시했습니다.

### Q6. Prompt / Context Engineering은 어떻게 하나요? MCP는요?

**→ 에이전트가 매번 같은 걸 묻지 않도록 필요한 맥락이 자동으로 들어가게 만들었습니다.**

**→ 규칙 문서를 주제별 8개로 나눠 필요한 것만 읽게 했습니다.** 다만 적용 범위를 좁게 잡은 건 컴포넌트 규칙 하나였고 나머지는 거의 늘 같이 읽혔다는 한계가 있습니다. Linear MCP로 티켓을, Figma MCP로 디자인을 바로 읽게 했습니다.

**→ 긴 로그는 별도 에이전트에 맡겼습니다.** Xcode · Gradle 로그는 빌드 진단 서브에이전트가 따로 읽고 원인만 돌려줍니다. 같은 하네스를 Codex에도 옮겨 특정 도구에 묶이지 않게 했습니다.

**→ 한계:** LLM을 앱 기능으로 넣어(RAG 등) 운영한 경험은 없습니다. 묻는다면 "개발 도구로 써 왔고, 제품 기능으로는 아직"이라고 말합니다.

## 3. 기술 선택 — "왜 그렇게 했나, 대안은?"

> 모든 답을 **문제 → 고른 것 → 버린 대안과 이유 → 지금이라면(+ 바꿀 신호)** 순서로 준비하세요.

### Q9. 메모리 누수를 왜 공용 훅으로 고쳤나요? 다른 방법은 없었나요?

**→ 화면마다 정리하는 방식은 다음 사람이 빠뜨려서, 빠뜨릴 수 없게 훅 하나로 묶었습니다.**

```
문제: 실사용자 Peak Memory P95 958.5MB (SharedValue 정리 누락)
고름: 언마운트 때 cancelAnimation을 한꺼번에 부르는 공용 훅, 값 24개 적용 → 297.4MB
버림: ① 화면마다 cleanup(빠뜨림) ② 라이브러리 교체(원인이 아님) ③ 이미지 캐시 축소(줄여도 그래프 그대로)
```

**→ 지금이라면:** 리뷰 에이전트에 "SharedValue를 만들고 훅에 등록 안 하면 경고" 항목을 넣겠습니다. **[ 실제로 넣었는지 ]** 바꿀 신호는 "같은 누수가 한 번 더 나는 것"입니다.

### Q10. 콜드 스타트용 지연 로딩을 왜 다시 뺐나요?

**→ 실사용 데이터를 보니 화면 전환마다 생기는 비용이 시작 시간 이득보다 커서 뺐습니다. 측정이 제 판단을 뒤집은 사례입니다.**

**→ 62개 화면을 React.lazy로 바꿔 Debug 기준 Splash 초기화 -24.4%, JS 로딩 -21.8%를 확인했지만,** 프로덕션 telemetry에서 Suspense·스켈레톤 비용이 더 컸습니다. 측정 체계는 남겼습니다.

**→ 다른 대안:** 무거운 화면 몇 개만 지연 로딩하거나 첫 화면 뒤 유휴 시간에 미리 불러오기. **[ 검토했는지 ]**

### Q11. CodePush 서버를 왜 직접 안 띄우고 S3 + CloudFront로 했나요?

**→ App Center 종료 뒤 서버를 직접 운영하면 장애·보안·업데이트를 계속 돌봐야 해서, 정적 파일만으로 동작하게 만들었습니다.**

```
앱 시작 → CloudFront의 최신 배포 정보 읽음(원본은 S3)
  → 내 네이티브 버전용 새 번들이 있으면 zip 내려받음 → 다음 실행에 교체
```

**→ 사용자는 S3에 직접 접근하지 않고 CloudFront에서만 받습니다.** 만들다가 막은 구멍: 캐시에서 배포 기록을 읽으면 빈 것처럼 보여서, 쓸 때는 항상 S3 원본을 읽고 기존 기록이 빠지면 쓰지 않게 했습니다.

**→ 버린 대안:** Expo Updates는 bare RN 앱이라 이전 비용이 컸습니다. **[ 실제 이유 ]** ([27번 Q11](./27_wrtn_review.md) — "서버 없음"으로 끝까지 일관되게)

### Q12. 왜 MobX에서 Zustand로, 서버 상태는 왜 React Query로 옮겼나요?

**→ 같은 데이터가 두 곳에 있어서 생기는 버그를 없애려고, 서버 데이터는 React Query가, 앱 안 상태는 Zustand가 갖게 나눴습니다.**

**→ 서버 상태를 스토어로 복사하던 구조를 걷어냈고, 구독 판단 60곳을 selector 하나로 모았습니다.** 마이그레이션은 완료 플래그로 한 번만, 실패해도 앱이 안 멈추게 예외를 격리하고 리포팅만 했습니다.

**→ "왜 Redux가 아닌가"**: 스토어가 21개로 작았고 Zustand는 필요한 값만 구독해 리렌더가 적습니다. 페이히어에서 Redux(Thunk · Saga · Toolkit)도 써서 둘의 차이는 압니다. **[ 팀이 Zustand를 고른 실제 이유 ]**

### Q13. 앱과 위젯의 데이터 동기화는 왜 그렇게 설계했나요?

**→ 위젯은 기기 저장소에만 쓰고, 서버 반영은 앱이 맡게 나눴습니다.**

```
[앱에서] Zustand 변경 → Shared Storage → 위젯 다시 그리기 → Firestore 순차 반영
[위젯에서] 위젯 체크 → Shared Storage(항목별 수정 시각) → 앱 열 때 병합 → Firestore 반영
```

**→ 위젯은 실행 시간이 짧고 네트워크가 보장되지 않아서, 기기 저장소에만 쓰고 서버 반영은 앱이 맡게 나눴습니다.**

**→ 충돌은 항목 단위 수정 시각으로 풀었습니다.** 버린 대안은 문서 단위 덮어쓰기인데, 다른 항목의 변경까지 지워집니다. 같은 계정의 다른 기기는 [27번 Q15](./27_wrtn_review.md)의 답을 따릅니다.

## 4. 배포 · 운영 · 레거시

### Q15. 배포 자동화는 어떻게 구성했나요? 그려 주세요.

**→ 테스트 트랙까지 자동이고 출시는 사람이 합니다.** 네이티브 빌드는 Actions에서 돌지 않아서 "CI에서 빌드했다"고 말하면 틀립니다.

**→ "왜 네이티브는 CI에 안 올렸나요?"** **[ 실제 이유 ]** 지금이라면 macOS 러너와 서명 인증서 관리로 옮기겠습니다. 한계: Fastlane lane에는 실패 알림이 없었습니다. 그림 자세히는 [27번 Q12](./27_wrtn_review.md).

**→ "성과는요?"** 시간을 잰 적은 없다면, 사람이 하던 배포 단계가 **[ n ]** 개에서 0개가 됐고 빌드 번호 충돌이 없어졌다고 말합니다. **[ 이전 배포 방식과 걸리던 시간 ]**

### Q17. 레거시를 분석하고 개선한 경험은요? 레거시에서 AI를 어떻게 쓰나요?

### Q19. 0→1, 1→10, 10→100 단계는 일하는 방식이 어떻게 다르다고 보나요?

**→ 0→1은 "작게 내서 맞는지 보기", 1→10은 "반복되는 고통 없애기", 10→100은 "안 깨지게 지키기"입니다.**

**→ 제 경험으로 하나씩:** 0→1은 페이히어 고객 대면 앱 출시와 개인 앱 3개, 1→10은 Fastlane 배포 자동화와 공용 훅, 10→100은 500만 사용자 앱의 실사용자 메모리 지표 관리입니다.

**→ 10→100에서는 측정과 끄는 스위치가 먼저입니다.** 0→1에서 같은 방식을 쓰면 느려지니 단계를 구분해 씁니다.

### Q20. 운영 중 장애는 어떻게 감지하고 대응했나요?

### Q23. 비대면 진료 앱에서 프론트엔드가 가장 어려운 부분은 무엇이라고 보나요?

### Q24. 이벤트·마케팅으로 트래픽이 몰릴 때 프론트엔드는 무엇을 준비하나요? (우대사항)

**→ 정직하게:** 이벤트 트래픽 대응을 제가 주도한 적은 없고, 설계 원칙으로 말합니다.

### Q27. 풀스택으로 문제를 푼 경험이 있나요? (개인 프로젝트를 "주말 튜토리얼"이라고 하면?)

**→ Code Slugger는 코인 차감을 서버(Edge Function)에서 처리해 클라이언트 조작을 막았고, 낙관적 업데이트 실패 시 되돌립니다.** 찍고가는 API 4개(카카오맵 · 카카오 로컬 · TMAP · 오피넷)를 Route Handler 프록시 뒤에 묶어 키를 숨기고, 좌표계 변환(KATEC ↔ WGS84)을 직접 구현했으며 오피넷 EUC-KR 응답을 방어 처리했습니다.

**→ 자동매매는 Python 시스템을 Docker로 묶어 GCP에서 24시간 돌렸습니다.** 회사에서는 Firestore에 앱이 직접 읽고 쓰는 구조라 DB 구조와 동기화 규칙을 프론트가 같이 설계했습니다.

### Q28. [설계] "비대면 진료 대기 → 진료 → 결제" 화면의 프론트엔드를 설계해 보세요.

> 후기에 따르면 이 회사는 설계 정답보다 **대안과 이유**를 봅니다. 요구사항을 먼저 되묻는 걸로 시작하세요: "앱만인가요, 의사 화면도 범위인가요?"

**→ 서버를 원본으로 두고, 앱은 상태를 받아 그리고, 끊기면 다시 받아 맞추는 구조로 설계하겠습니다.**

```
화면 = f(진료 상태)  [접수 → 대기 → 진료중 → 처방 → 결제 → 완료]
실시간: 연결(WebSocket/푸시) → 끊기면 재연결 시 서버에서 현재 상태 다시 조회
결제: 요청마다 멱등 키 → 두 번 눌러도 한 번만, 결과는 서버 상태로 확인
```

**→ 핵심 결정과 바꿀 신호:** 서버 상태는 React Query가 소유(복사본 금지), 화면 상태는 서버 상태에서 파생합니다. 폴링으로 시작해도 되지만 **호출 지연이 사용자에게 보이면** 푸시/WebSocket으로 올립니다.

**→ 먼저 깨지는 곳:** 앱을 껐다 켰을 때 단계 복구와 결제 중복입니다. 둘 다 "서버 기준 + 멱등"으로 막습니다.

## 7. 코드 리뷰 라운드 — 실제 코드를 주고 리뷰시킵니다

**→ 5분 안에 이 순서로 말하세요.** ① 이 코드가 하는 일 한 문장 ② 돈 · 데이터가 걸린 버그 ③ 구조 ④ 성능 ⑤ 나머지는 "작은 것들"로 한 문장.

| 볼 것 | 문제 신호 | 고치는 방향 |
|---|---|---|
| **useEffect 정리** | 구독·타이머·애니메이션을 만들고 return이 없음 | cleanup 반환 (루티너리 누수가 이것) |
| **경쟁 상태** | 늦게 온 옛 응답이 새 결과를 덮음 | 취소 플래그 · React Query |
| **서버 상태 복사** | API 결과를 useState에 복사 | React Query가 원본 |
| **결제·제출 버튼** | 두 번 누르면 두 번 요청 | 진행 중 잠금 + 서버 멱등 키 |
| **리스트** | ScrollView에 map, key가 index, renderItem 인라인 | FlashList · 안정 key · memo |
| **민감 정보** | 로그·Sentry에 개인 정보 | 마스킹 · ID만 전송 |

### 연습 1 — 2분 안에 리뷰해 보세요

```tsx
function ReservationScreen({ id }: { id: string }) {
  const [reservation, setReservation] = useState<any>(null);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    setLoading(true);
    api.getReservation(id).then((res) => {
      setReservation(res.data);
      setLoading(false);
    });
  }, []);

  const onPay = async () => {
    await api.pay(reservation.id, reservation.price);
    Alert.alert('결제 완료');
    navigation.goBack();
  };

  return (
    <View>
      {loading && <Spinner />}
      <Text>{reservation?.doctorName} · {reservation?.price}원</Text>
      <Button title="결제하기" onPress={onPay} />
    </View>
  );
}
```

**→ ① 결제를 두 번 할 수 있습니다.** 진행 중 버튼 잠금과 서버 멱등 키가 필요합니다.

**→ ② 금액을 앱이 보냅니다.** 서버는 예약 ID만 받고 금액은 서버가 정해야 합니다.

**→ ③ 실패 처리가 없고, `id`가 바뀌어도 다시 안 불러옵니다.** 응답이 늦으면 화면을 떠난 뒤에도 setState가 돕니다. `useQuery(['reservation', id])` + `useMutation`으로 바꾸면 ①의 잠금, 에러, 경쟁 상태가 같이 풀립니다. 작은 것: `any` 타입.

### 연습 2 — 리스트 성능

```tsx
<ScrollView>
  {doctors.map((d, i) => (
    <DoctorCard key={i} doctor={d} onPress={() => open(d.id)} style={{ margin: 8 }} />
  ))}
</ScrollView>
```

**→ ScrollView에 `map`은 전부 한 번에 그립니다.** 길어지면 FlashList로 바꿉니다.

**→ `key={i}`는 순서가 바뀌면 엉뚱한 항목에 상태가 남습니다.** 안정된 id를 씁니다.

**→ 인라인 `onPress`·`style`은 매번 새로 만들어져 항목 `memo`를 무력화합니다.** 측정으로 확인한 뒤 고정합니다.
